# Releases

The coordinator's release procedure. It lived in `CLAUDE.md` → "The coordinator manages releases" until the owner asked for a smaller `CLAUDE.md` (owner, 2026-11-24, among the token savers offered: "Do all 6 token savers"); `CLAUDE.md` keeps a short summary that points here. Nothing in it changed in the move.

- **The coordinator manages releases, and prepares or publishes one only when the owner says so** (owner, 2026-11-07: "I want you to manage the releases"; then "Release when I say so. PRs must be assigned a release to be considered complete, and PRs cannot be merged to main with no release. Roll back on your own. v3.0.0. I keep DNS cutover."). Every release has a GitHub milestone named for its version (`v3.0.0`, then `v3.0.1` for fixes only or `v3.1.0` when it adds something fans can see). Every pull request into `stage` is assigned to the open milestone of the next release when it is opened (`gh api -X PATCH repos/<repo>/issues/<n> -F milestone=<number>`), and CI's `milestone` job fails `ci-passed` until it is (#47; owner, 2026-11-13: "Yes, build it that way"); a story is complete only once its pull request's release is published, not when it merges into `stage`, and a run's summary says which release each story is waiting for. A release is prepared (checked) at one time and published later, each on the owner's word, so the owner can hold a checked release back from production while `stage` keeps moving and ship it afterwards (owner, 2026-11-13: "no, the release rule was based on the idea that I might want to prepare a release, but not deploy it to production, then continue to iterate on stage for a while, then deploy that earlier release"; shown this prepare-then-publish flow: "sounds good"). **Prepare**, when the owner says to prepare a release: (1) read the commit staging serves (`https://stage.baseball.theater/bt-commit.txt`) and record it as the release commit (its full sha), or a later `stage` commit (the candidate) only if it builds what staging serves, and in either case a commit whose `.github/workflows/deploy.yml` has the production job's Release order step (a release runs the workflow at its tag, so one targeting an older commit would deploy without that check). A later candidate qualifies in one of two ways (owner, 2026-11-16, asked whether a release may target a `stage` commit staging skipped deploying because its build inputs were unchanged, or only the one staging serves: "(a) Release may target Y"). First, the input check (S146): fetch staging's record, the newest unexpired `build-inputs-staging` Actions artifact (`gh api "repos/<repo>/actions/artifacts?name=build-inputs-staging&per_page=100" --jq '[.artifacts[] | select(.expired | not)] | sort_by(.created_at) | last | .workflow_run.id'`, then `gh run download <run id> --repo <repo> --name build-inputs-staging --dir <dir>`); require the record's commit (`pnpm build:inputs get <record> commit`) to be the one staging serves (after a `wrangler rollback`, or when an older run landed last, they differ, and the check isn't used); check out the candidate in a worktree and run `pnpm build:inputs check <record> --served <served sha>` there, with `BT_RELEASE` set to the candidate's own label (`scripts/build-release.sh merged <candidate sha>`, its pull request's milestone); `unchanged` means the candidate builds what staging serves, so step (2)'s smoke test still tests the release's code. Run it at the latest candidate, whatever lies between it and the served commit (code pushes whose inputs were unchanged, docs-only pushes, or both). Second, whenever the check can't be used (no record, or a record of another commit), a candidate whose every commit after the served one is docs (`scripts/ci-changes.sh push <served sha> <release sha>` prints `code=false`; a docs-only commit deploys nothing). Production builds at the release's tag, so its version line names the release commit, not the served one. Decide this from the served sha, not from run statuses, since a run whose staging job finds its commit already served (or its inputs unchanged) skips its deploy and still passes; check that CI passed for the release commit, and that the release commit's own pull request (the one whose merge commit staging serves, or the later candidate's) is in this release's milestone; if it isn't, stop and ask the owner whether to release under that pull request's milestone name or to move the pull request and redeploy staging so its label matches, and never move it yourself, since staging already built that milestone into its label; (2) smoke-test staging (the scoreboard and a game page load, the API answers), which at that moment runs exactly the release's code; (3) open the next release's milestone and close this one first, so nothing new is assigned to it, then check which of this milestone's pull requests are merged and contained in the release commit (`git merge-base --is-ancestor <merge sha> <release sha>`), and move any that aren't (a late merge included) to the next milestone, with the issues they close or are part of (`Closes #N`, `Fixes #N`, `Part of #N`); and move into this milestone, with their issues, every merged pull request that is contained in the release commit but sits in another milestone (or none) and is not in an earlier published or prepared release (never the release commit's own pull request: step (1) already found it in this milestone, or stopped), so a pull request's milestone always names the release that ships it. For a release below v4.0.0, step (3) runs right after step (2). For a release from v4.0.0 on, it runs only once step (4)'s fan-facing notes have landed and steps (1) and (2) have run again on the commit staging then serves, the final release commit, and it starts with the move into this milestone, as a re-check, while the milestone is still open (that move already ran once before the notes were drafted, step (4)): a pull request it newly moves in is drafted in and re-approved through another notes pull request, as one that merged after the commit the draft was made from is, and once that pull request's merge deploys, steps (1) and (2) run again and step (3) starts over; only when the re-check moves nothing in does it open the next milestone, close this one and move the late merges out, once per prepare; (4) write the release's notes and rebuild `CHANGELOG.md`. Its GitHub Release notes list the pull requests it contains (no others), written after step (3), once the milestone holds exactly them. Its fan-facing notes are `releases/<version>.json` (S131; `ReleaseNotes` in `packages/domain`), from the public launch release, v4.0.0, on (owner, 2026-11-19, asked where the change log starts: "Start at v4.0.0 (Recommended)"); a release below v4.0.0 has no notes file, and its GitHub Release says it is a pre-launch release whose fan-facing notes start with v4.0.0: after step (3), step (4) writes its GitHub Release notes and runs `pnpm changelog:build` as the end of this step says, then step (5) follows. From v4.0.0 on, the fan-facing notes come between steps (2) and (3), while this release's milestone is still open: CI's `milestone` job accepts only an open milestone (`scripts/build-release.sh require`), and the notes pull request's merge commit becomes the release commit, whose own pull request step (1) requires in this milestone. v4.0.0, the initial release, is the exception (owner, 2026-11-22: "4.0.0 notes are going to be special compared to later releases because it's the initial release. We aren't going to detail every PR on that one; it'll be a more generalized update comparing to the current live version"): its `releases/v4.0.0.json` is drafted as a general overview of what's new compared with the current live version, not from each pull request's `changelog.d/` fragment, and neither the condition that the notes describe every milestone pull request, nor the drafting-in of pull requests that merge after the draft, nor the drafting-in that step (3)'s re-check starts applies to it; it is still drafted, shown to the owner, approved in session, landed through a pull request and checked by `pnpm release:check` like any other, and step (3)'s milestone moves still run, so its GitHub Release lists exactly its pull requests. From the release after v4.0.0 on, everything here applies as written. First, step (3)'s move into this milestone runs on the commit staging serves (every merged pull request it contains that sits in another milestone, or none, and is not in an earlier published or prepared release, never that commit's own pull request), so the draft describes those pull requests too. The coordinator drafts `releases/<version>.json` from the `changelog.d/` fragments of the milestone's merged pull requests contained in the commit staging serves (the entries step (4)'s `pnpm changelog:build` assembles into `CHANGELOG.md` on the release commit's tree, rule 16), bucketed as FEATURES' Update / change log UX row says: the big additions in `headline`; very impactful fixes, new settings, new features and significant design changes as their own `items`, each a feature, an enhancement, a performance change or a bug fix (`kind` `feature`, `enhancement`, `performance` or `fix`); minor fixes and polish in `fixesAndPolish`. It leaves `date` empty: the notes file is frozen in the release commit, which is fixed before the day the release ships, and the GitHub Release records that day. It shows the draft to the owner, writes the owner's in-session approval into `approval` (the date and the owner's words, quoted), never writing an approval the owner didn't give in the current session, runs `pnpm release:bundle` on the notes branch whenever the notes change (when they are first drafted, and each time a pull request is drafted in and they are re-approved, in the open notes pull request or in another notes pull request) and commits the rebuilt `functions/src/generated/release-notes.json` with the notes each time (the releases API serves that bundle, and its drift test fails `pnpm verify` when it is stale against `releases/`; S132), runs `pnpm release:check <version>` there, which must exit 0, and lands it in `stage` through a pull request assigned to this release's milestone; the release is never prepared or published without that approval (owner, 2026-11-08: "The change log and bucketing need to be manually approved by me for each release"; asked how: "Draft, you approve in session"). Before that pull request merges, each pull request that merged into `stage` after the commit the draft was made from (which the notes pull request's merge commit will contain) is drafted in and re-approved, the owner's new approval quoted in `approval`. Merges into `stage` continue while the notes are drafted and landed (owner, 2026-11-22, asked whether other code pull requests should be held from merging into `stage` meanwhile: chose "No hold"): each code pull request that lands first is drafted in and re-approved, in the notes pull request while it is open, or through another notes pull request once it has merged. `releases/` is code to the deploy (`scripts/ci-changes.sh`), so that pull request's merge deploys staging: steps (1) and (2) then run again on the commit staging serves, which becomes the release commit, the re-run of step (1) running `pnpm release:check <version>` on it again, and step (3) follows. A release is published only from a commit where `pnpm release:check <version>` exits 0 (production's deploy job runs it on the release's tag after Install and before it builds anything, and fails the deploy otherwise; it passes a version below v4.0.0 with no notes file) and whose milestone pull requests the notes all describe: one that merged into `stage` after the notes landed is left out by releasing the commit where the notes landed and moving it to the next milestone, with its issues, as step (3) moves a late merge, while staging still serves that commit for steps (1) and (2); once staging serves a later code commit, those pull requests are drafted in and re-approved instead, through another notes pull request. After step (3), for every release, the coordinator writes the GitHub Release notes, then runs `pnpm changelog:build` on the release commit's tree and opens the rebuilt `CHANGELOG.md` as a docs-only pull request into `stage` (once per release; it deploys nothing); (5) create a draft GitHub Release with the milestone's version as a `v*` tag targeting that exact sha (never the moving branch): `gh release create <tag> --draft --target <release sha> --title <tag> --generate-notes --notes-file <file>`, the file holding step (4)'s notes; GitHub generates its list from the last published release, so while an earlier draft waits, edit the generated list down to this milestone's pull requests after step (3), so a pull request already in an earlier prepared or published release is never listed twice. A draft deploys nothing (`.github/workflows/deploy.yml` runs production only on `release: published`) and creates no tag until it is published, so `gh release view`, `edit` and `delete` can't find it by tag (they fall back to GraphQL, which Claude Code sessions can't reach): reach drafts through REST only. Find one with `gh api "repos/<repo>/releases?per_page=100" --jq '.[] | select(.draft and .tag_name == "<tag>") | "\(.id) \(.target_commitish)"'`, edit its notes with `gh api -X PATCH repos/<repo>/releases/<id> -F body=@<file>`, publish it with `gh api -X PATCH repos/<repo>/releases/<id> -F draft=false`, and discard it with `gh api -X DELETE repos/<repo>/releases/<id>`. **Iterate:** `stage` keeps moving after a release is prepared; staging need not keep serving the release's code. More than one prepared draft may wait, but they publish in version order. **Publish**, when the owner says to ship a release: first check that the REST lookup above still finds a draft whose `target_commitish` is the recorded sha and that `git ls-remote --tags origin <tag>` prints nothing; then publish its draft as it is (`-F draft=false`), never retargeting it or editing its notes (the two exceptions are under Discard), so production deploys exactly the commit checked when it was prepared; check that the tag now resolves to that sha (`git ls-remote --tags origin <tag>`), and watch the production deploy and the `mirror-main` job. A release lower than one already published, or whose commit doesn't contain `main`, fails before it deploys, by design (the production job's Release order step, `scripts/release-order.sh`; owner, 2026-11-13: "The only way a rollback should happen is using a REAL rollback to a prior verison that had been released. Otherwise, an unreleased release that is a lower version than the one that is live should fail to deploy. If it still needs to be deployed, it'd need a new release."); if an older draft holds something production doesn't already run and still needs to ship, discard it and prepare a new release. **Discard** a draft with the REST delete above (safe: a draft has no tag yet), then move each of its pull requests, with its issues: one already contained in a published release's commit goes into that release's milestone and is added to that release's notes (`gh api -X PATCH repos/<repo>/releases/<id> -F body=@<file>`) with the owner's in-session approval of the new notes quoted (the first exception to never editing notes); one no published release contains goes into the lowest remaining prepared draft's milestone whose commit contains it, re-editing that draft's notes to list it with the owner's in-session approval of the new notes quoted (the second exception); and only otherwise into the next open milestone; reopen its own milestone only if that version will be prepared again and new pull requests still go to the highest open milestone, since a reopened lower milestone would otherwise attract new assignments. From v4.0.0 on, a release's fan-facing notes are frozen in its commit, so Discard changes three ways. When the discarded draft's pull requests are contained in a published release's commit, stop and ask the owner whether the discarded version's `releases/<version>.json` stays as the fans' record of them or its items are folded into that published release's notes with a new approval, instead of only editing its GitHub Release notes. A remaining prepared draft that gains pull requests is not re-edited but discarded too and prepared again (reopening its milestone, as above), with the moved pull requests drafted into its `releases/<version>.json` for the owner's re-approval; when re-preparing it would leave a higher prepared draft waiting on an older commit (the re-prepared draft's newer commit reaches `main` once it publishes, and the Release order step then refuses the higher draft), stop and ask the owner instead. And the discarded version's approved `releases/<version>.json`, which describes a release fans never got, is removed through a pull request into `stage` unless that version will be prepared again (its notes are then re-drafted and re-approved at that prepare); when another draft's old commit holds that file, the removal lands before that draft's new notes commit, and the release that ships the discarded draft's pull requests drafts them into its own notes, as step (4) says. A published release that the Release order or Release notes approved step refused never counts as released: with the owner's OK, delete it and its tag (`gh api -X DELETE repos/<repo>/releases/<id>`, then `git push origin :refs/tags/<tag>`) and handle its pull requests and issues as Discard says. A story counts as released only when its pull request is in a published release's commit. If a release breaks production, roll back on your own, without asking, and only by re-running the Deploy run of the last good release that deployed before (Actions → Deploy → that release's run → Re-run all jobs; the Release order step lets a re-run of a release that deployed before through; only if that run is past GitHub's 30-day re-run window, use `npx wrangler rollback --env production` as a last resort, which returns production to its previous deploy, itself a released version (owner, 2026-11-13, asked whether it should stay as that last resort: "1 and 2 both yes")), then tell the owner what broke and what was rolled back; `main` stays at the newer release until the next release fast-forwards it. Nothing reaches `main` without a release. The DNS cutover of `baseball.theater` stays the owner's; never change it.
