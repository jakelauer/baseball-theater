# Run backlog

The owner's shorthand (2026-10-30): _"loop the next 10 stories, in order, and if you get blocked, move on to the next story that has no unresolved dependencies."_ Bugs share that order (owner, 2026-11-18: "We need the backlog prioritization to include bugs, not just stories. [...] I want to rename "run-stories" to "run-backlog" to ensure it doesn't skip bugs."): a bug is a GitHub issue with a note, `docs/v3/backlog/bugs/<status>/B<issue>.md`, whose `priority` sits on the stories' scale. This skill strings together the flow `CLAUDE.md` already defines for one story or one bug — it adds no new rules and relaxes none. Below, an **item** is a story or a bug; where only one applies, it says so.

**This thread coordinates; each story runs in its own fresh-context subagent** (owner, 2026-11-04: "All 3", to running each story in a fresh-context subagent among the token cuts). Before this, one context carried every story: 92% of a run's input tokens, a median of 200–300k tokens re-sent on every request, because whatever one story read stayed for all the later ones. Here the coordinator keeps only what it needs to choose and check stories: the gate scripts, `docs/v3/INDEX.md`'s story list, `git`, and each worker's short report. **Don't read story notes, code, skills or ledger entries in this thread** beyond the frontmatter eligibility needs; the workers and review subagents read them.

**Argument:** `N`, the number of items to **start** (default 10), stories and bugs together. Count starts, not finishes, so a run of parked items can't stretch the loop past what the owner expected. Resuming an item that was already `doing` or `blocked` (step 1) does not count.

## 0. Before the first item

- `git status`: if a finished story or bug is uncommitted, commit it first (rule 6). If uncommitted work you can't attribute to an item is in the tree, stop and ask. (`docs/v3/.obsidian/workspace.json` is editor state — leave it out of commits, ignore it.)
- `git fetch origin`. If a previous run's `backlog/bug-notes-*` pull request is still open, finish it first (its Claude review, then merge, as step 5.2 says) before step 0 writes anything, wait for it to merge, then `git fetch origin` again, so everything below reads the merged `origin/stage`; if it can't merge, stop and ask the owner.
- Then what a previous run left stacked, from its summary's **Stacked, waiting** and **Unopened, waiting** lists (and any open pull request whose base is a `story/` or `bug/` branch): a pull request GitHub has since retargeted to `stage` gets `origin/stage` merged in, pushed, its Claude review handled and auto-merge turned on, as step 5.3 says; a branch held back unopened whose branch directly below has merged gets `origin/stage` merged in the same way, then is pushed and opened into `stage`; any whose pull request below was closed without merging is parked, with every branch above it, held or open, as step 5.3 says.
- An item already `doing` that waits on the owner (e.g. a design match): park it as in step 4. One that is mid-build: finish it first, on its own branch, as step 3 (a story through a `story-worker`, a bug through a `bug-worker`); for a bug, first check its issue (`gh issue view <N> --json state,stateReason`, read-only), and if it is closed, stop and ask the owner rather than resuming it. Its pre-PR review waits until it is merged up to the starting point (below).
- **Bug notes**, read from `origin/stage` (`git ls-tree -r --name-only origin/stage docs/v3/backlog/bugs/`):
    - Every open note (`todo`, `doing`, `blocked`) whose issue is closed is closed out: `status: done` when `stateReason` is `COMPLETED`, `superseded` when it is `NOT_PLANNED` or `DUPLICATE`. If that bug has an open parked-checkpoint pull request (`Part of #<N>`), close it (`gh pr close <n> --comment "<issue #N was closed as …>"`) and list it in the summary. Any other `stateReason` (empty, `REOPENED`, one not listed here) leaves the note as it is: the bug is held for this run (never picked, never a start) and goes in the summary as a question for the owner.
    - Every open GitHub issue labelled `bug` has a note (`gh issue list --label bug --state open --json number`); one that doesn't gets one, as `CLAUDE.md` → "A bug gets an issue" says. An open issue without the label whose text reports something broken in shipped behaviour (`gh issue list --state open --json number,title,labels,body`) is labelled (`gh issue edit <N> --add-label bug`) and gets its note the same way. A new note takes the priority the owner gave the bug, or else one just ahead of the next `todo` story; the summary names the priority each got.
    - Then `pnpm backlog:build` and one commit, `Backlog: bug notes (<what changed>)`, on a branch `backlog/bug-notes-<date>` cut from `origin/stage`. Its pre-PR review runs right away: one fresh-context `pre-pr-reviewer` covering all the checklist slices, on `git diff origin/stage...backlog/bug-notes-<date>`, any finding fixed as step 3 describes (`docs/v3/LOOP.md` §7 step 3). If that fix loop's arbiter holds the branch, stop before step 1 and ask the owner.
- **The run's starting point** is that `backlog/bug-notes-<date>` branch when step 0 made one, else `origin/stage`. The run's first item branches from it (step 3). A mid-build item finished above is brought up to it before anything branches from it: `git merge --no-commit --no-ff <starting point>` on its branch (never a rebase), then `pnpm backlog:build` (which also settles a conflict in `docs/v3/INDEX.md` or `docs/v3/BACKLOG.md`; never by hand) and `pnpm verify` on the merged tree, then `git add` and `git commit`, as step 5.3 does for a merge forward. The next item then branches from that item, not from the starting point.
- The agent types this skill names (`story-worker`, `bug-worker`, `pre-pr-reviewer`, `db-reviewer`, `fix-worker`, `fix-plan-reviewer`, `arbiter`, `backlog-reviewer`, `design-intake-reviewer`, `design-intake-merger`, `doc-parity-reviewer`) live in `.claude/agents/` and load only in a session started after that directory exists: if the Agent tool doesn't list them, restart the session before the first item.

## 1. Owner answers first

If the owner has, **in this session**, answered a parked item's question (a design match "Yes", a ratification go-ahead, a fence or scope decision, a bug's owner decision), finish that item before starting new ones: hand it to a worker (step 3: a `story-worker` for a story, a `bug-worker` for a bug) with the owner's words quoted **verbatim** in the brief, to apply (e.g. `scripts/audit.sh story <ID> --design-match -` with those words) and then finish the item. Never infer an answer — no explicit owner words in this session, no change.

## 2. Gates, before every story

A bug skips these gates: it never needs a design, backlog or design intake review (owner, 2026-11-18: bugs "should not require design reviews, backlog reviews, or intake reviews"), nor, since a bug note has no **Source:** line, a doc parity review (the agent's inference; the owner named design, backlog and intake reviews), and finishing one never counts toward review or parity debt (the debt scripts read `stories/` only). A review that is due waits for the next story, not the next bug. Before a story, check in this order:

1. **Backlog review due?** `scripts/review-debt.sh` counts `done` flips since the last review (6 triggers it) and the drift events git records; add any it can't see (`CLAUDE.md` → Agent / loop rules). Don't read `docs/v3/AUDIT.md` to count — it is ~1 MB. If due, run `.claude/skills/backlog-review/SKILL.md` in a **fresh-context subagent** (the Agent tool, `subagent_type: "backlog-reviewer"`, which loads the skill itself; this skill is the owner's explicit request for it — the agent that built the stories must not review them). Give it the script's output; **don't read the skill into this thread** (it is ~12 KB and was being pasted into the coordinator's context on every review). It makes its edits, logs them with `scripts/audit.sh review` and commits; check the commit landed. A design intake (the script says when) is two `design-intake-reviewer` subagents, started at once, each loading `.claude/skills/design-intake-review/SKILL.md` itself; then one `design-intake-merger` subagent, given both reports, merges, applies, logs and commits, so the merge also happens outside this thread.
2. **Doc parity due?** `pnpm parity:debt`. If due, run `.claude/skills/doc-parity-review/SKILL.md` the same way, in a `doc-parity-reviewer` subagent.
3. A review verdict of **`blocked` stops the whole loop**, bugs included — go to step 5. Questions from a `continue` / `amended` review don't stop it; collect them for the summary.

## 3. Pick and run the next item

**Eligible** = the lowest-`priority` item with `status: todo`, story or bug. A bug is eligible unless this run held it. A story is eligible when:

- every `depends_on` story is `done` (a dependency that is `doing`, `blocked` or `todo` is unresolved — e.g. S67 waits while S66 waits on a design match);
- every `design:` story is `done` (rule 18);
- it is not an item this run held (`docs/v3/LOOP.md` §7 step 3, "Exit"): its note on the current branch still reads `todo`, but its work sits on its own unpushed branch, so it is never picked again.

Read both lists from the note's frontmatter in `docs/v3/backlog/stories/<status>/S<N>.md` (the folder is its status; `docs/v3/INDEX.md` links to it). The generated **Next** line in `BACKLOG.md` checks designs only, not `depends_on`, so don't rely on it alone. `superseded` stories are skipped.

Find it from the **Stories and bugs** section of `docs/v3/INDEX.md` (open stories and bugs in one table, with each story's `depends_on` and design lists, then the `done` ones) or the notes' frontmatter; nothing else is needed to choose. When a story and a bug share a priority, the bug goes first.

**Give it its own branch first** (S121; owner, 2026-11-07: "I want a release to be a set of PRs basically"): `git switch -c story/S<N>` from the run's starting point (step 0: its `backlog/bug-notes-<date>` branch when there is one, else `origin/stage`) for the run's first item (or from the item step 0 finished and merged up, when there is one), and from the previous item's branch for each later one (skipping any item held or found closed: one its fix loop's arbiter held, `docs/v3/LOOP.md` §7 step 3, "Exit", or a bug whose issue was closed; then from the nearest earlier item that is neither, or the run's starting point), so a run's items stack and each branch holds its item and the ones before it. A bug's branch is `bug/B<N>`, cut and stacked the same way, but only after `gh issue view <N> --json state,stateReason` shows the issue still open: a closed one gets no branch, is held for this run (never picked again, never a start) and listed in the summary, and the next run's step 0 closes its note out. The worker commits there; nothing is committed on `stage` itself.

**A bug goes to a `bug-worker`** (`subagent_type: "bug-worker"`, `run_in_background: false`; `.claude/agents/bug-worker.md` carries its standing rules), not a story worker, with this brief:

> If issue #<N> is closed, change nothing and reply `closed`. Otherwise fix bug B<N> (GitHub issue #<N>) as one step of `/run-backlog` (`.claude/skills/run-backlog/SKILL.md`, steps 3–4) and `.claude/agents/bug-worker.md`: `status: doing` + `pnpm backlog:build`, the reuse check, a regression test shown red on HEAD before the fix, the smallest fix, `pnpm verify` 0, `status: done` + `pnpm backlog:build`, a `CHANGELOG.md` entry as rule 16 says (default to including one; frame a dev-only fix by who benefits), one commit naming #<N>. Start from `docs/v3/INDEX.md` and `gh issue view <N> --comments`. Don't build anything beyond the bug: report it as a suggestion. Do not push, open a pull request or issue, start another item, or run a review. If it is blocked, park it as step 4 says and stop. [Owner's answers for this bug, quoted verbatim, if any.]
>
> Reply with only: **outcome** (`done`, `parked`, or `closed` if the issue is already closed: then nothing else, no commit), **commit**, **one-line impact**, the regression test with its red and green output, the `pnpm verify` exit code, **suggestions** (title, what you saw, why) or "none", and, if parked, each question for the owner (bold direct question first, then self-contained context).

If the bug worker still reports the issue closed (outcome `closed`; it commits nothing; the issue was closed after the check above), commit nothing either: switch back to the previous item's branch (or the run's starting point), delete the bug's (`git branch -D bug/B<N>`), and treat the bug as held and listed, as above. Otherwise, check it as for a story (below), and run its **pre-PR review** the same way: a bug's fix gets the same code review as a story's (owner, 2026-11-18: "Bugs need code reviews."), and nothing else. **Every suggestion becomes an enhancement issue** (owner, same day: "should the bug reveal a larger issue or a suggestion from the implementer or reviewer, those suggestions must be recorded as an "enhancement" issue with a link back to the bug and should include an explanation for the suggestion"): each suggestion the bug worker reports, each pre-PR or `db-reviewer` finding about a bug that is real but beyond the fix (a larger problem, a forward-looking point, a better design), and each such comment from Claude's review in step 5. The coordinator files each one as soon as it has it: `gh issue create --label enhancement --title "<suggestion>" --body "<body>"`, where the body opens `From bug #<N> (B<N>), suggested by <the bug worker | the pre-PR review | the database review | Claude's review of #<pull request>>.`, then says what was seen and why it is worth doing, in plain words. An enhancement issue is not a bug and gets no bug note; it enters the backlog only when the owner asks for it, as a story with its own `**Source:**`. Answer a review comment filed this way with a reply naming the new issue, then resolve it.

**Hand a story to a worker:** one fresh-context `story-worker` subagent per story (the Agent tool, `subagent_type: "story-worker"`, `run_in_background: false`: the next item waits on this one's commit; `.claude/agents/story-worker.md` carries the worker's standing rules, and the brief below still goes in full). Workers run one at a time, never in parallel: they share the working tree. The brief is self-contained, since the worker starts with none of this thread's context:

> Run `/goal S<N> done` exactly as `CLAUDE.md` → "`/goal <ID> done` shorthand" defines it, as one step of `/run-backlog` (`.claude/skills/run-backlog/SKILL.md`, steps 3–4): quote the `/goal` line and ACs word for word, `status: doing` + `pnpm backlog:build`, the reuse check, grader written and shown red on HEAD before product code, build inside the fence, grader green, `pnpm verify` 0, `status: done`, `CHANGELOG.md`, the baseline table (rule 17), `scripts/audit.sh story S<N>`, one commit. Start from `docs/v3/INDEX.md`. Do not push, start another story, or run a review. If the story is blocked (step 4's list), park it as step 4 says and stop. [Owner's answers for this story, quoted verbatim, if any.]
>
> Reply with only: **outcome** (`done` or `parked`); the **commit** sha; a **one-line impact**; your `Goal for S<N>:` quote and your `S<N> verified:` section exactly as you wrote them; and, if parked, **each question for the owner**, written as step 5 asks (bold direct question first, then self-contained context), plus any drift event (turn cap, fence).

When it returns, check rather than trust: `git status` is clean, `git log -1` is the commit it named, and the note's `status` is `done` or `blocked` (for a bug, also that the regression test exists and passes). If not, finish or park the story yourself from what is committed, and say so. **Then, before the next item branches from this one, run its pre-PR review** (`docs/v3/LOOP.md` §7 step 2): parallel fresh-context `pre-pr-reviewer` subagents, one per checklist slice, each given §7, its slice and this item's own diff (`git diff <base>...story/S<N>`, or `bug/B<N>`, where `<base>` is the branch it was cut from, or, for the first and for an item merged up to it in step 0, the run's starting point (step 0), after `git fetch origin`). When that diff touches the database paths §7 step 2 lists (the schema, migrations, the classification manifest, repositories or any SQL), start one `db-reviewer` beside them (owner, 2026-11-13: "we need an agent that is a database specialist reviewer whose job it is to examine the DB schemas and queries we establish"), limited to those changes (owner, same day: "the DB reviewer's reviews should be limited to JUST changes that impact the database queries and schemas, but it will need the context about why those changes are made"): give it that slice of the diff, the story's note path (its ACs say why) and the owner's quoted decisions for it. Its must-fix findings join the merged report; its forward-looking ones go in the run summary for the owner and never hold the story. Merge their reports and drop duplicates. The goal is that Claude's review finds nothing (owner, 2026-11-07, of Copilot's review, which Claude's replaced on 2026-11-11: "Our goal should be zero Copilot discoveries for each pull request"). If they find anything, fix it as §7 step 3 says: one fresh-context `fix-worker` (this thread doesn't read code) gets every merged finding and plans the fixes, a fresh-context `fix-plan-reviewer` checks the plan, the worker builds it uncommitted on `story/S<N>` (or `bug/B<N>`), and a fresh-context `pre-pr-reviewer` (on the same model tiers as the pre-PR review) checks those changes (new files included) plus every caller they affect, with a `db-reviewer` beside it when the fix touches those database paths, repeating until they find none. This thread runs each round and passes the plan and verdicts between subagents, and after six rounds or a repeated finding hands the open findings to a fresh-context `arbiter`, which clears them, holds the story (its uncommitted fix work thrown away, its branch left unpushed), or escalates a call it judges too impactful to make to the owner (§7 step 3, "Exit"). Only then does the worker run `pnpm verify` (a change made to get it green goes back for review), re-run `scripts/audit.sh story S<N>` for a `done` story so the ledger names the commit that ships (a parked checkpoint keeps no ledger entry until it's finished: `audit.sh` writes a "completed" entry whatever the grader says), and make one commit. Only then does the next item branch from it. Relay a story worker's `Goal for S<N>:` quote and `S<N> verified:` section to the owner as they are (the `/goal` rule asks for both), and a bug worker's regression test with its red and green output; keep any questions for the summary. Don't push per item: the run pushes once, at the end (step 5), as one pull request per item.

Give the owner a one-line progress note when each item starts and ends.

## 4. Blocked → park and move on

An item is **blocked** when it needs something only the owner can give, or the rules forbid going further:

- a design match (rule 22) or ratification (rule 18) waiting on the owner;
- an AC that can't be met inside the fence (rule 10) — never widen it;
- a missing input the story says to stop and ask for;
- the turn cap reached;
- an owner decision the story can't make (a pillar citation, an `Open:` source, a new ADR);
- for a bug: a fix that needs an owner decision, a new or changed UI design, or a new feature, or a bug that can't be reproduced and whose issue doesn't say what to test.

The worker parks it (and the coordinator, if a worker stops without doing so):

1. Commit everything done so far, on the item's `story/S<N>` or `bug/B<N>` branch, as a **checkpoint** (grader or regression test, code, captures), worded like earlier checkpoints: `S<N> checkpoint (parked for …): …` (or `B<N> checkpoint …`). `pnpm verify` must exit 0 at the checkpoint. If it doesn't and can't be made to inside the fence, revert the story's product changes, keep the grader, and say so. A parked bug's checkpoint commits its regression test under the test runner's expected-failure marker (`it.fails` in Vitest, `test.fail()` in Playwright), its name naming the issue (`… (#<N>)`), so `pnpm verify` exits 0 while the test still records the bug; since that marker passes on any failure, the pull request's text (step 5) quotes the test's red output on HEAD, showing it fails for the issue's reason and not, say, an import error. Its pull request says `Part of #<N>`, and the fix that finishes the bug turns the marker back into a plain test.
2. Set `status: blocked` in its note, `pnpm backlog:build`, include it in that commit. A committed checkpoint satisfies rule 6, so other stories may run.
3. Record the question for the summary (what it needs, with the evidence). For a design match, run `pnpm design:review <ID>` and name `.designreview/<ID>/`; run `pnpm design:review <ID> --done` once the owner gives the verdict.
4. A turn-cap hit or a fence problem on a story is a **drift event**: the next step 2 makes a backlog review due. A parked bug is never one.

Then go back to step 2.

## 5. Stop

Stop when `N` items have been started, nothing is eligible, a review returns `blocked`, `pnpm verify` breaks in a way no story owns, or the owner interrupts. An item its fix loop's arbiter held (§7 step 3, "Exit") is not pushed or opened as a pull request; the items started after it were cut past it (step 3), so they push as usual. If the arbiter holds a story during step 5.3, while Claude's review comments are being fixed, its pull request keeps auto-merge off with a comment naming the open finding; the branches stacked on it that aren't pushed yet stay unpushed until it is fixed, and any that already have a pull request (into its branch, so without auto-merge) get a comment naming that open finding and wait until the fix is merged forward into them and Claude's review of their new head is handled (step 5.3). The summary lists each held story and every branch waiting on it. Then push once, for the whole run (owner, 2026-11-02: "if we're using run-stories, we don't have to push until they are all done"), as one pull request per item into its base (step 3: `stage`, or the branch below it) (S121; owner, 2026-11-07: "I think releases to main probably should use GitHub releases, if that's actually possible. I want a release to be a set of PRs basically", and on who merges them: "1. You automatically"):

1. Check GitHub Actions on `stage` first (`gh run list --branch stage --limit 1`), as `CLAUDE.md` → Agent / loop rules says.
2. If step 0 made a `backlog/bug-notes-<date>` branch, its pull request opens first, whatever happens to the items (it is never held for one): `git push -u origin backlog/bug-notes-<date>`, then `gh pr create --base stage --head backlog/bug-notes-<date> --title "Backlog: bug notes (<what changed>)" --body-file <file>`, the file written by a quoted heredoc and holding no `Fixes` or `Part of` line, since it closes nothing (its issues are already closed or newly noted). Assign the pull request, and no issue, to the next release's milestone, and handle Claude's review and auto-merge as step 5.3 says for an item.
3. In run order, for each `story/S<N>` or `bug/B<N>` branch (done or parked checkpoint; a bug branch always carries a real fix or a parked checkpoint), a bug's handled exactly like a story's with these differences: it is pushed with `git push -u origin bug/B<N>` and opened with `gh pr create --base <its base> --head bug/B<N> --title "B<N>: <one-line impact>" --body-file <file>`, the file written first by a quoted heredoc (`cat > <file> <<'EOF'` … `EOF`), so the quotes and `%` in pasted test output reach the description unchanged (`--fill` doesn't add `Fixes`). The file's first line is `Fixes #<N>`; a parked checkpoint's is `Part of #<N>` instead, followed by its regression test's red output (step 4). The pull request goes into the next release's milestone like any other (`gh api -X PATCH repos/<repo>/issues/<n> -F milestone=<number>`); a done bug's pull request moves issue #<N> into that milestone too, since `CLAUDE.md` → "A bug gets an issue" puts the issue in the milestone of the release that will carry the fix, while a parked checkpoint's leaves the issue's milestone alone, since it doesn't carry the fix; auto-merge is `gh pr merge --auto --merge bug/B<N>`, and every other command below that names `story/S<N>` names `bug/B<N>` instead; and any real but out-of-scope comment from Claude's review becomes an enhancement issue (step 3). For each: its pre-PR review already ran in step 3 (below "When it returns"), before the next item branched from it, so its pre-PR fixes are already in every later branch. Then `git push -u origin story/S<N>`, `gh pr create --base <its base> --head story/S<N> --title "S<N>: <one-line impact>" --body-file <file>`, the file written by a quoted heredoc as for a bug. **Its base is the branch it was cut from** (owner, 2026-11-19, after stacked pull requests into `stage` listed every earlier story's commits and files: "You also need to fix the stacked commits issue because it makes PRs appear way too big. This needs to be fixed as a general rule"): `stage` for the first item cut from `origin/stage`, else the branch below it (the bug-notes branch, or the previous item's), so each pull request shows only its own change. One exception: Claude's review runs on `pull_request_target`, which uses its base branch's workflow, scripts, hooks and rules, so a branch stacked on one that changes any path `is_reviewer_path` in `scripts/claude-review/plan-review.py` lists (all of `scripts/` and `.github/` among them), `.claude/`, `CLAUDE.md` or `docs/v3/LOOP.md` is not opened until the one below has merged, and then opens into `stage` after `origin/stage` is merged in, so its reviewer is always `stage`'s; it is pushed then too, not before. The hold is transitive: a branch above a held one is held too, since its base isn't on `origin` and its reviewer would be the held change's, and each opens, with `origin/stage` merged in, only once the branch directly below it has merged. The description is written, never `--fill` (which lists every commit on the branch, the earlier items' included): it says what the change does and, first (after a bug's `Fixes` or `Part of` line, which always comes first), what it waits on: a parked item's opens with **Waiting on you:**, each owner question in plain words with a link to the design or file to look at, and a stacked one says **Stacked on #<n>**, the pull request below it. Wait for Claude's review (`.github/workflows/claude-review.yml`) and handle every comment before turning on auto-merge (`gh pr merge --auto --merge story/S<N>`), as `CLAUDE.md` → "Claude's review is handled before a pull request merges" says (owner, 2026-11-07, of Copilot's review, whose rule Claude's kept on 2026-11-11: "If Copilot continues giving the same feedback you can merge when you feel the real stuff is all handled"); a fix goes on that story's branch through `docs/v3/LOOP.md` §7 step 3's fix flow (3.1–3.5, as step 3 here describes), and a comment that isn't real gets a reply. A pull request stacked on `story/S<N>` (its base is `story/S<N>`) never has auto-merge on, so a real finding of Claude's review or a failed check on `story/S<N>` holds nothing back but the fix: the pull requests stacked on it simply wait for it to be merged forward. A fix committed on `story/S<N>` after a later story branched from it (for Claude's review here, or for a failed check in step 5.4) is merged forward, in run order, into each later stacked branch, each branch from the one it was cut from (`git switch story/S<M> && git merge --no-commit --no-ff story/S<previous>`, where `story/S<previous>` is the branch `story/S<M>` was cut from, so a conflict is resolved once and carried down the stack); never a rebase or force-push, so pushed shas and ledger commits stay valid. A conflict in `docs/v3/AUDIT.md` keeps both sides' entries whole, the earlier story's first; any other conflict (`CHANGELOG.md`, the Current baseline frame note) keeps both stories' changes, the earlier story's first, and the baseline's **As of** line is the later story's; `docs/v3/audit.jsonl`, `docs/v3/INDEX.md` and `docs/v3/BACKLOG.md` are regenerated with `pnpm backlog:build`, never hand-merged. `--no-commit` stops even a clean merge before it commits, so `pnpm backlog:build` and `pnpm verify` run on the merged tree first; then `git add` the resolved and regenerated files, and only then `git commit`. A merged branch with no pull request yet is not pushed then: it is pushed only when its own turn in this step comes, so a story held later still leaves it unpushed. A merged branch that already has a pull request (into its branch below, so auto-merge is off) is pushed, and waits for Claude's review of its new head, handled as above, before auto-merge goes back on. A review run that fails is re-run; a pull request never merges without a finished review of its newest commit, and if the review still can't run, the run stops and asks the owner. Auto-merge merges each pull request once its required checks (`ci-passed`) pass, and goes on only for a pull request whose base is `stage`: on one into another branch it would merge into that branch. When the pull request below merges, GitHub deletes its branch and retargets the one stacked on it to `stage` (if it doesn't, `gh api -X PATCH repos/<repo>/pulls/<n> -f base=stage`). Never delete a branch an open pull request is based on, by hand: GitHub closes that pull request instead of retargeting it. If the pull request below is closed without merging, the stacked branch still carries its commits, so it is never retargeted as it is: it is parked, with every branch above it, held or open, and the owner asked how to go on. Then `origin/stage` is merged into the stacked branch the way a fix is merged forward above (`git merge --no-commit --no-ff origin/stage`, both sides kept, generated files rebuilt, `pnpm verify`, then commit), pushed, and its Claude review of the new head and its checks handled before auto-merge goes on.
4. Watch the pull requests' checks (`gh pr checks <number> --watch`, in the background) and report each one's result in the summary; a failure is the next thing to fix, committed on that story's branch, and merged forward into every branch stacked on it as step 5.3 says.
5. Once they merge, bring the local `stage` up to date (`git fetch origin && git switch stage && git merge --ff-only origin/stage`).

Each pull request is assigned to the next release's milestone when it's opened, and an item counts as complete only once that release is published; the summary says which release each item waits for. A run never pushes directly to `stage` or `main`, never merges into `main`, and never prepares or publishes a release on its own: the coordinator prepares one (a checked draft) and later publishes it, each only when the owner says so, publishing drafts in version order; production refuses a release lower than one already published, and rolls back only by re-running an earlier released version's Deploy run (`CLAUDE.md` → "The coordinator manages releases"; owner, 2026-11-07: "I want you to manage the releases"; then "Release when I say so. PRs must be assigned a release to be considered complete, and PRs cannot be merged to main with no release. Roll back on your own. v3.0.0. I keep DNS cutover."). Never deploy by hand.

End with one summary:

- **Done:** each story and bug with its commit and a one-line impact.
- **Parked:** each `blocked` story or bug, what it waits on.
- **Stacked, waiting:** each pull request whose base is another item's branch, and the pull request it waits on; when that one merges, step 0 of the next run (or the coordinator, if it is still running) merges `origin/stage` in and turns its auto-merge on, as step 5.3 says.
- **Unopened, waiting:** each branch held back unpushed because a branch below it changes the reviewer (step 5.3), with the branch directly below it that it waits on; the next run's step 0 opens it once that one merges.
- **Bugs set aside:** each bug held because its issue was found closed mid-run (its note closes out next run) or because step 0 met a `stateReason` it doesn't map (with the question in the list below).
- **Enhancement issues filed:** each with its number, the bug it came from and who suggested it.
- **Questions for the owner**, every one from stories and reviews, numbered, each a **bold direct question first**, then self-contained context (no "see above"). The context never stops at an ID or an AC number (owner, 2026-10-30: "you need to tell me more than just the label for the AC or the Story"): say what the story builds, what the AC or change says in plain words, what went wrong or changed, and what each answer would lead to.

- **Not eligible:** stories skipped, and the unresolved dependency or design for each.
