## 1 — Baseline

```bash
git status          # clean
git tag -l loop-baseline
```

Rollback if a loop trashes the tree:

```bash
git switch -C recovery loop-baseline
```

## 2 — Verify

```bash
pnpm verify
```

Non-zero ⇒ not done. Details: `.claude/skills/verify/SKILL.md`.

**Capture it.** `pnpm verify` prints and forgets. Every finished story and every backlog review gets an entry in the ledger, written by `scripts/audit.sh` — never by hand — as its own new file, `docs/v3/audit/<YYYY-MM-DD>/<stamp>-<ID>-<kind>.md`, so two branches' entries never conflict (S156; `docs/v3/AUDIT.md` holds the entries before it, frozen; `scripts/backlog-vault/ledger.ts` reads both):

```bash
scripts/audit.sh story S14            # grader + pnpm verify, captured verbatim
scripts/audit.sh review --verdict …   # a review pass, event-triggered or manual
scripts/audit.sh story S14 --reverify # today's grader at S14's shipping commit
scripts/audit.sh design S79 --design-match -  # an owner's design verdict on its own
```

A design match pairs each capture with the same-named ratified frame, unless the story's `docs/v3/design-checks/<ID>/frames.json` names the ratified frame(s) it is judged against (`{ "about-mobile.png": ["docs/v3/visual/…/changelog-mobile.png"] }`; owner, 2026-11-24, asked how S154 should record a design match for captures with no ratified frame of their own: "Change the tool (Recommended)").

**Two tiers (S84).** A story's grader is a **commit-time proof**: it proves that story at its own commit and is never expected to hold for the whole system later. What must hold on every commit is a **law**, listed in `docs/v3/LAWS.md` and enforced by `pnpm verify`.

The ledger is the only durable record of *what was actually checked*: which of the story's checks ran, whether they passed, and the commit the story shipped in. It is also what the review cadence counts off — "6 stories since the last review" reads from it, through `ledger.ts`.

## 3 — Conventions

Read and correct `CLAUDE.md` once. Anything you disagree with must be written there; chat-only preferences die at compaction.

## 4 — Backlog

Work only from the backlog (the story and bug issues, found through `docs/v3/INDEX.md` and `pnpm backlog:search`). If a criterion is ambiguous mid-run, **tighten the backlog** (`scripts/audit.sh edit`), then re-run — don’t just patch code.

**Status is part of done:** set the story to `doing` when you start and to `done` when all acceptance criteria pass. Commit that status flip with the implementation, and run `pnpm backlog:build` (the story list is generated from it). A green `pnpm verify` with Status still `todo` is incomplete.

**Commit before the next goal:** if the prior story is marked done (or claimed complete) but its changes are still uncommitted, **do not start the next story**. Refuse to move on until that work is committed (or the user explicitly overrides). Check with `git status`.

**Review the plan, not just the code:** `pnpm verify` proves the code is healthy and says nothing about whether the backlog is still right. Every **6** `done` stories — or immediately on a drift event (fence widened, turn cap hit, ACs rewritten mid-run, new ADR, new package, out-of-review re-prioritization, `pnpm verify` changed) — run `.claude/skills/backlog-review/SKILL.md` with **fresh context** (a `backlog-reviewer` subagent) and log the verdict in the ledger (`scripts/audit.sh review`). The review runs beside the items in flight and edits only the text of items not in flight (`node scripts/backlog-vault/claims.ts review-edits --root <main checkout>` reports a violation; owner, 2026-11-20: *"Run them in parallel (Recommended)"*); `blocked` stops new dispatches, and in-flight items finish. This is the plan-side counterpart to §7's reviewer pass.

## 7 — Reviewer pass

Loop output reaches `stage` only through pull requests, one per story or bug (S121; owner, 2026-11-07: "I think releases to main probably should use GitHub releases, if that's actually possible. I want a release to be a set of PRs basically"; on who merges them: "1. You automatically"). Each story is committed on its own `story/S<N>` branch (a bug on `bug/B<N>`); the coordinator pushes it, opens its pull request into `stage` and turns on auto-merge (`gh pr merge --auto --merge`) once its base is `stage`, provided the `stage` ruleset lists `claude-review/posted` as required (otherwise only once the review is handled), (when it opens, or when GitHub retargets a stacked one), except under `/run-backlog`, whose merge train (its step 5) turns it on one pull request at a time to keep priority order; GitHub merges it once the required checks (`ci-passed` and `claude-review/posted`, the status Claude's review sets on the head it reviewed) pass and its review threads are resolved (step 5 below), and the merge deploys `stage.baseball.theater` (unless it changes only docs, which deploys nothing). Agents never push directly to `stage` or `main` and never merge into `main`. Each pull request is assigned to the next release's milestone, and a story or bug is complete once that release is published. The coordinator prepares a release (checks a `stage` commit and saves it as a draft GitHub Release) and later publishes that draft, each only when the owner says so, drafts in version order (production refuses a release lower than one already published, and a rollback is only a re-run of an earlier released version's Deploy run); publishing deploys production and then fast-forwards `main` to the released commit, so `main` mirrors production ("2. ### Review-class checklist

What the pull request review (GitHub Copilot's until 2026-11-11, Claude's since) and the 2026-11-07 ultrareview of `stage` caught after our own reviews passed. Claude's review (`.github/workflows/claude-review.yml`) uses this list as its method too. Each item is a question to ask of every change; answer it with the input that breaks the change, or with why none can.

1. **Interrupted work.** A stop, crash or error between two writes or two steps (a snapshot written but not its projection): what is left behind, and does the next run detect and repair it, without redoing finished work?
2. **State that must survive a restart.** Every counter, streak, cursor or "given up" flag a resumed or retried run depends on is persisted, not rebuilt from what the run skips, and stays right for the next run over **any** range, not only a resume of the same one: a later run over a newer range, or one that doesn't touch the last, starts its own count instead of being ignored or continuing an unrelated one. Caught by Claude's review of PR #20. A merge or join rule that keeps an old terminal state (a give-up) must not swallow newer data that should reach its own terminal state: newer days count on their own instead of being folded into the old state and never moving it. Caught by Claude's review of PR #46.
3. **Partly present data.** A range or collection that is empty, partly stored, or stored but stale: each case says what happens (fill only what's missing, refresh what's stale), and a "nothing yet" answer is told apart from "zero".
4. **The real source of truth.** A value is read from the store that actually holds it for every case (a day's schedule summaries hold games a `games` row doesn't exist for yet). Where a piece of work belongs is read from what already holds it, not from the bucket it came from: a discarded release draft's pull requests that a later published release's commit already contains go to that release, not to the next one. Caught by Claude's review of PR #51. The same holds for a writer: where two sources hold the same thing and the reader prefers one (a raw recording over its mapped fixture), a writer that refreshes only the fallback while the preferred one exists changes nothing the reader serves, so it writes the source the reader reads, or removes the one that would win, and a test reads back through the reader after the write (a recorder that rewrote only the mapped standings file while the client still read the old raw one; caught by Claude's review of PR #321).
5. **Unsettled states.** Live, scheduled, postponed or suspended items are never treated as finished (today is never "done" while its games are live).
6. **ADR conformance.** Routes under `/api/v1/` (ADR-015), with `:name` path parameters as in `packages/domain/src/api-routes.ts`; freshness from `cacheLifetimeMs` by last change, not by "past vs current" (ADR-021); version-guarded writes (ADR-022); one named implementation per calculation (ADR-025); personal data in the inventory (ADR-028).
7. **Upstream request budget.** A read path or loop that fans out to MLB (per-day requests, `fetchGame`'s three extra calls) has a bounded request count and fits a Worker's subrequest limit; a range request beats one per item.
8. **Import side effects.** Reusing a helper never imports a module whose top level runs a script (seeding, migrating, guards); move the helper to an import-safe module.
9. **Generated files inside the fence.** Every committed file the work regenerates (`openapi/`, `web/src/api/generated/`, the types fidelity test) is inside the story's scope files, Goal condition and `/goal`. Since S156 `docs/v3/INDEX.md` and `docs/v3/audit.jsonl` are built and git-ignored, and the generated `docs/v3/BACKLOG.md` is retired.
10. **Structured lines read by parsers.** Text a script parses (a **Depends on** line makes every story ID on it a hard dependency) says only what it should; preferences go on **Prefer after**. A parser's end marker is structural (the next bullet or heading), not a sibling's name that can be renamed (a grader's awk that ended only at `- **Copilot`; caught by Claude's review of PR #26). Prose on a parsed line can change generated output: a `;` plus a negating word ("not") in a **Depends on** aside cut off the next story ID, and the regenerated `depends_on` silently lost S134 (caught by Claude's review of PR #50); diff the frontmatter after `pnpm backlog:build`.
11. **Contradictions inside a story or a procedure.** No AC requires what another AC or note forbids (existing tests "pass unchanged" while the behavior they test is removed), and no claim a procedure makes ("nothing stacked needs rebasing", "runs once") is undone by a later step of the same procedure (a review fix landing on a branch others were cut from). Caught by Claude's review of PR #11. One value can't be two things in two ACs: S135 AC 1 made `buildInfo`'s `release` null for `dev` while AC 4 printed `dev (…)` from that same value; a derived value gets its own name (caught by Claude's review of PR #50). One edit can't be owned by two stories: a note that gives a story a line to rewrite first checks no other story's AC already rewrites it (S147's note and S141 AC 3 both claimed VISUAL-DESIGN's quiet-meta line, with different targets; caught by Claude's review of PR #69). A rule about a branch's neighbour in a stack (the branch below it, the one above) also says what it does to the branches further along, which inherit the same reason (a hold on the branch above one that changes the reviewer holds every branch above that, too).
12. **Boundaries.** Inclusive ranges and their edge days, time zones (`mlbToday`), the earliest and latest allowed values, and each tested; and where two rules both reach the same edge value (a "dimmed, pickable" style and a "disabled" style on a day before the earliest date), the text says which wins. Caught by Claude's review of PR #23.
13. **Untrusted stored values.** Browser storage can throw (blocked site data, private modes) and can hold stale or out-of-range values (a clock corrected backwards): keep an in-memory fallback, and bound what is read back.
14. **Matching too broadly.** A glob, prefix or pattern matches only what it should (a `settings-*` override must not swallow frames another amendment draws), and a guard's pattern covers every name it is meant to guard (a bundled-fixture test whose pattern skipped the new `raw/standings-*` recordings; caught by Claude's review of PR #15). A new file, step or path can fall inside an old pattern: an unshipped grader's `\bbuild\b` counted the new `scripts/build-release.sh` lookup step as a build step (caught by Claude's review of PR #50); grep the graders and tests for patterns your new names match.
15. **Shared state between unrelated features.** One flag or key serving two features (one snooze hiding both the update notice and the retired-version notice) is split, or the coupling is intended and said.
16. **What a tool actually sees.** A tool that changes the working tree before it runs (claude-code-action puts the base branch's `CLAUDE.md` and `.claude/` back on disk) or reads from a checkout other than the one meant (a pull request's merge ref, not its head): every step that reads those files reads the version it means to, and says how (`git show <sha>:<path>`). Caught by Claude's review of PR #29.
17. **A structured value says what its label says.** A ledger row, table cell or field filled from an argument holds what its label names, checked against the source it summarizes (a "Stories `done` since last review" row given the review's scope listed `todo` stories as done). Caught by Claude's review of PR #31. A status read as one step's outcome comes from that step alone, not from a whole job that runs more after it (a deployment's `success`, read as "the Worker went live", was failed by a Logto step after the deploy). Caught by Claude's review of PR #51. When code moves, every comment and doc that names where it ran moves with it (two Logto comments still said "the `production` job" after the step moved to `production-logto`; caught by Claude's review of PR #51).

Caught by Claude's review of PR #14.
21. **Values compared across stores mean the same in each.** A counter stamped per database (`version`) is compared only inside the database that stamped it; a comparison between two databases (a copy, a sync) uses what both measure the same way (`lastChangedAt`, a patch count), and the receiving side's counter still only moves forward. Caught by Claude's review of PR #21.
22. **A reload re-applies what the element's attributes say.** Changing a media element's `src` (or a form's, a frame's) reloads it, and its attributes act again on the new load: `autoplay` restarts a clip the reader had paused. Code that restores state after a reload (time, paused) checks every attribute that acts on load, and a test asserts the element's attributes after the switch, since jsdom never autoplays or loads media. Caught by Claude's review of PR #58.

Caught by Claude's review of PR #58.
24. **A list that claims a class covers every member of it.** A path list or pattern said to cover "what steers CI" (or any class) is built from where that class actually lives: every file of that name at any depth (`functions/package.json`, not only the root one), every script the workflows run, found by searching them rather than from memory. Otherwise the comment narrows to what the list holds. Caught by Claude's review of PR #59.

Caught by Claude's review of PR #59.

Caught by Claude's review of PR #65.
27. **A rewritten frame or baseline line stays whole.** Every sentence of a rewritten review bullet, frame note or `**Baseline:**` line still ends, and a line keeps its trailing navigation pointer. Caught by Claude's review of PR #94. Since S156 the **As of** line is not hand-edited: each `done` story's note carries a one-paragraph `**Baseline:**` line (what it changed in the Current baseline), `pnpm backlog:build` builds the **As of** line from the newest completion's into `docs/v3/INDEX.md`, `06 Baseline history.md` is frozen, and a story still edits the Current baseline area rows its change reaches (rule 17).

Caught by Claude's review of PR #94.
29. **A rule changed in CLAUDE.md changes its procedure too.** When a change set rewrites a `CLAUDE.md` rule that names a procedure (a skill under `.claude/skills/`, a script), the procedure's own wording is updated in the same change set, so an agent following either file does the same thing. Caught by Claude's review of PR #106.
30. **An AC that removes a thing is checked against every AC that requires it.** When an acceptance criterion is rewritten to forbid or drop a file, field or step (no notes before v4.0.0), every other criterion of the story, and its deploy or CI step, is read for a check that still requires it on some input (a deploy that fails when the notes file is missing). Caught by Claude's review of PR #106.
31. **An exemption validates its input first.** A pass-through for a range of values ("a version below v4.0.0 passes") says that malformed input is rejected before the range is tested, with a test for each malformed form, so a bad value can't fall into the exempt range. Caught by Claude's review of PR #106.
32. **A permission names the rules that still limit it.** A rule that lifts a requirement ("push without asking") lists every other rule that still limits the same act (batching pushes per review round, stacking order, a run's single push), so an agent following the new rule alone breaks none of them. Caught by Claude's review of PR #106.
33. **An expected value names the recording behind it, and an AC records that recording.** An acceptance criterion that compares an answer against recorded data ("equals the table of the last regular-season day") names which recorded file backs it, and some AC of the same story records or bundles that file; otherwise the grader and the route test can each pick a different fixture (or none, and an empty answer), and one passes while the other fails. Caught by Claude's review of PR #328.
