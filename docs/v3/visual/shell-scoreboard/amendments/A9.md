In words, not drawn:

- **The ways in.** The link at the foot of the rail and the drawer (choosing it in the drawer closes the drawer), the update notice's link and the pointer's link are the only ways to the page. It is not in the nav list, and the version line is not a link.
- **The version line.** The drawer shows the same line as the rail. Since #47 (2026-11-13) every build already prints its release, the milestone of the pull request whose merge commit it builds, with the commit (`v3.2.0 (40767e9)`); a build with none prints `unreleased (<commit>)` or `dev (<commit>)` and counts as a null release for S135 AC 3, so it records nothing and shows no pointer; the update-available notice doesn't depend on the release and is unaffected.
- **Releases on the page.** A release with no date shows its version alone; one with only fixes and polish shows its version, its date if it has one, and that line. A release with several headline additions gives each its own Major Feature header, one after another. Every release is listed on one page, with no pagination (the list starts at v3.1.0). Long titles and sentences wrap; nothing on the page is cut. Release notes carry no scores, so Hide Scores changes nothing on the page, the notice or the pointer.
- **The update notice** appears as soon as the app knows of an update, on every page, and makes no request for release notes: it shows no addition.
- **Never both.** Whenever A6's box is up, in either order (already up when the pointer is due, a waiting update or S28's retired-version notice included, or arriving while the pointer shows), A6's box shows as A6 and the frames above draw it, and the pointer doesn't show; a pointer that was showing goes at once and doesn't come back on that load. Nothing here draws the two together.
- **The offline marker.** S74's marker stays in the slot under the header (`web/src/layout/NoticeSlot.tsx`) and A6's box stays floating at the bottom right, so neither moves the other. The pointer shows while the marker is up (the `updated-pointer-with-marker-*` frames).
- **When the pointer shows** (S135 AC 3). Every load of a build whose release is known records that release in this browser, under its own storage key (never A6's `bt.updateSnoozedUntil`), so a reload doesn't show it again. It shows only on a load whose release is newer (`compareReleaseVersions`) than the recorded one. Nothing shows on a first visit (nothing recorded), on the same release (a new commit of it included), on an older one (a rollback), when the build's release is unknown, or when storage throws; a recorded value that isn't a release version counts as nothing recorded and is overwritten.
- **How the pointer goes.** After 10 seconds, when it is clicked or tapped anywhere (its link still opens the change log as it goes), or when the fan opens the drawer. It has no `✕`, and its countdown never pauses, under the mouse or otherwise (Q13). The rail's link is highlighted for as long as the pointer shows; the drawer's link, when the fan opens the drawer while the pointer shows, stays highlighted until the drawer closes.
- **Reduced motion.** When the fan's device asks for reduced motion, the pointer appears and goes without fading or sliding, and its countdown line is not drawn (the 10 seconds still run).
- **The retired case.** A6's box looks the same whichever reason raised it, link included (Q14; the `update-notice-link-*` frames draw it, the retired case included). The pointer appears only on a fresh load of a newer build, which is not retired.

## Decisions

Recorded as the owner stated them.

- The page and the notices (owner, 2026-11-08): "I need a user-facing changelist page which lists the changes in each release simplified to just those things which impact users. Minor bugs and fixes should fall into a single bucket. Others that are either very impactful bug fixes, new settings, new features, new significant design changes, etc should get their own items. The update dialog should link to it and a notification that auto dismisses after updating should show a link to it. Really big new additions should show on the update notification itself (via API data comparing versions)."
- Which notification shows the big additions (owner, 2026-11-08, asked which notification): "Both"
- Where the page starts (owner, 2026-11-08): "No, start at v3.1.0"
- After the first draft (owner, 2026-11-09, shown the after-update notification stacked above the update notice, and the after-update notification listing big additions): "Image 1 here looks good. Image 2 is weird, no need to show that"
- Two boxes (owner, 2026-11-09, asked which notices should stop listing the big additions): “There shouldn’t be two boxes ever. After it updates, we should see something similar to image 1, but it should tell the user the the update is complete instead”
- Name: Change log (owner, 2026-11-10, shown the draft that called the page "What's new"): "Change list is never right. Change log is the right name. So anything that's change list anywhere should be change log."
- Address: `/changelog` (owner, 2026-11-10): "The changelog will just be at /changelog."
- Reached from: the link at the foot of the menu, in the rail and the drawer, besides the update notice's and the pointer's links (owner, 2026-11-10, asked whether the notices' links and the version line were enough): "There should be a link to the change log from the footer, I think, or the foot of the menu. Foot of the menu makes sense."
- Kinds: feature, enhancement, performance and bug fix, labeled FEATURE, ENHANCEMENT, PERFORMANCE and BUG FIX (owner, 2026-11-10): "maybe feature, enhancement, bug fix, are the big three"; and the fourth (owner, 2026-11-16, asked whether to add one and which): "Performance"
