In words, not drawn:

- **The ways in.** The link at the foot of the rail and the drawer (choosing it in the drawer closes the drawer), the update notice's link and the pointer's link are the only ways to the page. It is not in the nav list, and the version line is not a link.
- **The version line.** The drawer shows the same line as the rail. Since #47 (2026-11-13) every build already prints its release, the milestone of the pull request whose merge commit it builds, with the commit (`v3.2.0 (40767e9)`); a build with none prints `unreleased (<commit>)` or `dev (<commit>)` and counts as a null release for S135 AC 3, so it records nothing and shows no pointer; the update-available notice doesn't depend on the release and is unaffected.
- **Releases on the page.** A release with no date shows its version alone; one with only fixes and polish shows its version, its date if it has one, and that line. A release with several headline additions gives each its own Major Feature header, one after another. Every release is listed on one page, with no pagination (the list starts at v3.1.0). Long titles and sentences wrap; nothing on the page is cut. Release notes carry no scores, so Hide Scores changes nothing on the page, the notice or the pointer.
- **The update notice** appears as soon as the app knows of an update, on every page, and makes no request for release notes: it shows no addition.
- **Never both.** Whenever A6's box is up, in either order (already up when the pointer is due, a waiting update or S28's retired-version notice included, or arriving while the pointer shows), A6's box shows as A6 and the frames above draw it, and the pointer doesn't show; a pointer that was showing goes at once and doesn't come back on that load. Nothing here draws the two together.
- **The offline marker.** S74's marker stays in the slot under the header (`web/src/layout/NoticeSlot.tsx`) and A6's box stays floating at the bottom right, so neither moves the other. The pointer shows while the marker is up (the `updated-pointer-with-marker-*` frames).
- **When the pointer shows** (S135 AC 3). Every load of a build whose release is known records that release in this browser, under its own storage key (never A6's `bt.updateSnoozedUntil`), so a reload doesn't show it again. It shows only on a load whose release is newer (`compareReleaseVersions`) than the recorded one. Nothing shows on a first visit (nothing recorded), on the same release (a new commit of it included), on an older one (a rollback), when the build's release is unknown, or when storage throws; a recorded value that isn't a release version counts as nothing recorded and is overwritten.
- **How the pointer goes.** After 10 seconds, when its link is followed, when its `✕` is chosen, or when the fan opens the drawer. Pending Q13: the countdown pauses while the mouse is over the pointer or keyboard focus is inside it (on a touch screen, only while focus is inside), and starts again from where it paused. The rail's link is highlighted for as long as the pointer shows; the drawer's link, when the fan opens the drawer while the pointer shows, stays highlighted until the drawer closes.
- **Reduced motion.** When the fan's device asks for reduced motion, the pointer appears and goes without fading or sliding, and its countdown line is not drawn (the 10 seconds still run).
- **The retired case** is not drawn with the pointer: the pointer appears only on a fresh load of a newer build, which is not retired.

## Open questions

1. **Q12.** **Should the change log have a fourth kind of entry, and if so which?** Each item that gets its own entry is labeled feature, enhancement or bug fix; you asked for pitches for a fourth. Pitches: "Performance" (speed and reliability: faster loading, fewer dropped connections; recommended, since that is the gap you named between a bug fix and an enhancement), "More baseball data" (new stats or fields shown), or "Removed" (something taken out). Yes with one: S131's kinds and A9's labels gain it before either ships. No: the three stand.
2. **Q13.** **Should the pointer after updating keep a countdown line that pauses under the mouse, and a close button?** You asked for both on the box after updating ("It should just be a something that's built into Mantine that counts down with like a visible line or something, and that should pause if you hover over it."; "There should be a close button still."), then replaced that box with the pointer. As drawn, the pointer keeps both: a thin line along its foot shrinks over its 10 seconds and pauses while the mouse is over it or focus is inside it, and a ✕ closes it at once. Keep both: built as drawn. Drop one or both: the frames lose it, and the pointer just goes after 10 seconds or when its link is followed.
3. **Q14.** **When the server has retired this version, should the update notice hide its link to the change log?** You said: "I think this is obviated by the thing I just said for number 18, but if not, then my answer is yes." Number 18 was about what shows after updating; the update notice still has its link, so the agent read it as not obviated, and the retired frames draw the notice with no link: that build gets an error from every request of its retired version, so its link would open only the page's error state. Yes: built as drawn. No: the retired notice keeps the link, which opens the page after Update Now loads the new version.
