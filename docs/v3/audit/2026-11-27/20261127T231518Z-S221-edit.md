**Gap:** A `/run-backlog` run reports progress only as prose: a line per item as it starts, parks, opens its pull request and merges, and a summary at the end. Its journal (`.run/run.json`, S158) already records every `item-start`, `park` and `merged` event, but nothing turns that into a quick read of how far the run has got, so the owner has to work it out from scrolling text. The owner, 2026-11-25, mid-run: *"During run-backlog runs, can you print out an ASCII-style progress bar (or any equivalent which works for both the CLI and the app) which makes it easy for me to see progress % based on the number of things finished so far? **Impact:** Before S221, the owner had to read through a run's updates to tell how far it had got. After S221, every run prints a progress bar with the share of its planned items finished, done in one glance while scrolling, the same in the terminal and the Claude app.

**Source:** Feature: Parallel backlog work

**Depends on:** none.

**Baseline:** A `/run-backlog` run now shows how far it has got: the coordinator logs the run's plan as a `plan` event (`claims.ts run event plan --items <ID>,…`) at the start and whenever the plan grows, and prints `runs.ts progress --journal <path>` in a fenced code block after each merge or park, when the plan grows and at the head of the run's summary: a ▶ line, a 20-cell `█`/`░` bar with merged / total and the percentage, then done, in flight, parked and set-aside lines (each only when it has items), the next items and a closing rule, plain text with no colour codes so it reads the same in the terminal and the Claude app. `runs.ts` `runProgress` is the one computation: planned is every item a `plan` event names plus any with an item event, each item's state is its newest item event (`RUN_ITEM_KINDS`, so a `review-score` or `claim` after a merge never moves it back) except a `park`, which holds until `resume`, `item-start`, `merged` or `held`, a `held` item leaves the total, and the percentage is finished over planned less set aside, rounded down.

**Acceptance criteria** (checks `scripts/verify-S221.sh` performs)

1. **One computation, from the journal.** `scripts/backlog-vault/runs.ts` gains `runProgress(journal)` (ADR-025: one implementation), returning the run's planned, finished, in-flight, parked, set-aside and next items and the percentage finished. Each item's state is read from its newest item event, except a park, which holds until `resume`, `item-start`, `merged` or `held`, an item event being one whose kind is in `RUN_ITEM_KINDS` (`claims.ts`); other events that carry an item's ID (`claim`, `claim-refused`, and the review tracker's `review-score`, which names the item whose merge it follows) never set or change an item's state, since the journal logs a `review-score` for an item right after its `merged`, and reading it as the newest event would move a finished item back to in flight:
   - **Planned** is every ID named by a `plan` event (a new run-level event in `RUN_KINDS`, `run event plan --items <ID>,<ID>…`, each ID checked by `ITEM_ID`, logged at `run start` and whenever the plan grows, e.g. a bug accepted mid-run) plus every ID with any item event, so a `merged` for an ID never planned still counts once in both totals and finished can never exceed planned.
   - **Finished**: newest event `merged`. **Parked**: a `park` with no `resume`, `item-start`, `merged` or `held` after it; any other item event after a park (`findings`, `pr-open`, `ready`, `needs-lead`, `turn-cap`, `conflict`, `duplicate`) leaves it parked, since a parked design match is reviewed and its checkpoint's pull request opened after the park (a `resume` moves the item back to in flight). **Set aside**: newest event `held` (an arbiter's hold or a bug found closed); a set-aside item leaves the planned total, so a run whose other items all merge reaches 100%. **In flight**: any other item event (`item-start`, `resume`, `needs-lead`, `pr-open`, `ready`, `turn-cap`, `conflict`, `duplicate`) with no park holding. **Next**: planned items with no item event yet, in the order the `plan` events named them.
   - The percentage is finished ÷ (planned − set aside), rounded down to a whole number, and 0% when that is 0. A parked item stays in the total.
   - Unit tests in `scripts/backlog-vault/` cover an empty run, a run part-way through, a park then resume, a held item reaching 100%, a turn-capped item, a `merged` for an unplanned ID, an item added mid-run, a parked item staying parked through a later `findings`, `pr-open`, `ready`, `needs-lead`, `conflict` or `turn-cap` (and leaving the park on `resume`, `item-start`, `merged` or `held`), a `merged` followed by a `review-score` (and a `claim`) for the same ID still counted finished, and a finished run (100%).
2. **A bar that reads the same everywhere.** `node scripts/backlog-vault/runs.ts progress --journal <path>` prints the bar as plain text meant to go inside a fenced code block: a leading marker line, a 20-cell bar of `█` and `░` with `finished / total` (total being planned minus set aside, the same total the percentage uses) and the percentage, then one line each for done, in flight, parked and set aside (each only when it has items) and next (`runProgress`'s next list), and a closing rule line. No ANSI colour codes (the Claude app shows them as text). A test pins the exact output for a fixed journal.
