**Gap:** BT knows each player only by MLB's id (MLBAM, e.g. `matchup.batter.id`, the box score's person ids). That id opens the player's page on MLB.com and on Baseball Savant, which MLB runs and keys by the same id, but FanGraphs and Baseball-Reference key their player pages by ids of their own, and BT has no way from one to the other: the recorded fixtures carry no cross-reference (`fixtures/raw/people-823823.json` has none). The owner asked (2026-11-23) that *"Patrons should have the ability to choose from the other providers"* when a player's name opens their stats, so BT needs those ids. And a player's name in BT opens nothing: the pitcher and batter cards of an opened play (`web/src/components/pitch/MatchupCards.tsx`, shared with the Live room) and the box score's tables (`web/src/components/game/BoxRoom.tsx`) are plain text. The owner said (2026-11-23): *"I should be able to click on their names to open their stats, just like in the box score. Well, I guess the box score needs that."*; and, asked how: *"We should have a user setting which is the user's preference for the default stats provider, and the default should be MLB.com because that is the most likely to definitely work. Patrons should have the ability to choose from the other providers, or the option to choose on click (so when clicking on a player they'd be presented with the options)"*. Settings live on the account and are for signed-in fans only (`AccountSettings`, `packages/domain/src/settings.ts`; FEATURES' Settings row: *"Hide settings for signed out users. Settings aren't available without signin"*), and what a patron may do comes from their pledge's tier (`entitlementsForTier`, `packages/domain/src/entitlements.ts`). On 2026-11-25 the owner dropped the design story (S208), and with it the choose-on-click option: *"I think S195 and S199 could be built without designs, using existing paradigms as a guide. I don't want to require a complete 1:1 match between designs and the site at all times. Sometimes it's easier to iterate on the site itself. S197 has more to do with behavior than designs - it's just a floating video player in the corner and should use exactly the same behaviors that YouTube's mini player uses. S208 doesn't need a design either - the only parts that could are the setting and the option to pick every time. We could ditch that pick every time part, and the setting is pretty self-evident."*; and folded S210 and S211 into this story: *"Also S209-211 should just be one story"*.

**Impact:** Before S209, a fan who wanted a player's stats had to leave BT and search for the player. S209 impact: a player's name on a play or in the box score opens that player's stats page, on MLB.com by default; a signed-in fan has a Settings choice of stats site, and a patron can pick FanGraphs, Baseball-Reference or Baseball Savant instead.

**Source:** Feature: Multi-source knowledge; Settings (favorites, hide scores, playback prefs)

**Baseline:** A player's name on an opened play's pitcher and batter cards (`MatchupCards`, shared with the Live room) and in each box score table (batting and pitching) is one link component, `PlayerLink` (`web/src/components/PlayerLink.tsx`), opening in a new tab the page `playerProfileUrl(effectiveStatsProvider(settings, entitlements), ids)` builds (`packages/domain/src/player-links.ts`, beside `StatsProvider` and `gamePersonIds`): MLB.com for a signed-out visitor and by default, and for a patron (`Entitlements.statsProviderChoice`, Backer and up, derived from the tier by `entitlementsForTier` and never stored) the site saved as `AccountSettings.statsProvider` (column `stats_provider`, default `'mlb'`), chosen on Settings' Stats Site control, whose three other sites are disabled and marked "Patron option" without the entitlement; the settings route refuses only a change away from MLB.com without it. MLB's `xrefId` cross-references (recorded in `fixtures/raw/people-xref-823823.json`) carry FanGraphs ids but no Baseball-Reference ids, so both outside ids come from the Chadwick Bureau's open register (ODC-By 1.0; `ChadwickPlayerRegister` behind the `PlayerRegister` port, streaming its sixteen files in one Worker run, about 1.2 s of CPU and 11 MB of heap as measured; read only with live MLB data). They are kept in `player_ids` behind `PlayerIdRepository`: ingest adds a game's players when it is first written or its roster changes, and the cron's `player-ids` job (its own `cron` scope) resolves at most `RESOLVE_CAP` due players a run (one register read; rechecking an unmatched player after `RECHECK_INTERVAL_MS`, two weeks) and then seeds one page of `SEED_PAGE_GAMES` stored games by keyset in one SQL statement (`seedPlayerIdsPageSql`, cursor in `player_id_seed_cursor`). `GET /api/v1/players/:personId/profiles` answers the four URLs and the ids (a day's caching once checked, minutes before, 404 for no row); the link reads it only for FanGraphs and Baseball-Reference and falls back to MLB.com on an unknown id, a 404, loading or failure.

If not, the source is the Chadwick Bureau's open player register (its licence named in the story's ledger notes): the job of AC 3 fetches it at run time and keeps only the rows of the players it needs. The register is published as several large files, so the story measures whether one Worker run can read one within the Worker's memory and time limits (reading one file per run if so); if it can't, the story stops and reports (rule 10), since an import outside the Worker would be new infrastructure. A sample is recorded once into `fixtures/` for tests. Either source sits behind one port method the job calls (`MlbStatsClient` for MLB's, a small port of its own for the register's), so the job is the same. The commit body says which source, and why.
2. **One function per link** (ADR-025). `packages/domain` exports `StatsProvider` (`"mlb" | "fangraphs" | "bbref" | "savant"`) and `playerProfileUrl(provider, ids)`, which builds the player's page URL from MLBAM for MLB.com and Savant and from the provider's own id for FanGraphs and Baseball-Reference, answering `null` when that id is unknown. Table test: a known player's four URLs, each written down from the live site once and committed as the expected value, built from ids alone (no name slugs, so a renamed player's link still works), and a player with no FanGraphs id (`null`).
3. **Stored, resolved lazily, and served.** The ids live in one table behind a port (`PlayerIdRepository` in `packages/ports`, a Postgres adapter with one migration and an in-memory double, one contract test on PGlite): `person_id` primary key, `checked_at` (nullable), `fangraphs_id` and `bbref_id` (nullable), with an index on `(checked_at NULLS FIRST)`. They are resolved lazily (ARCHITECTURE §3), never by scanning every game BT holds in one go (S122 backfills every game since 1901, and the cron runs every minute under the Worker's subrequest limit):
    - **Ingest adds players.** On a game's first write, or a write whose roster differs from the stored one (not every live snapshot), ingest inserts the game's players (`INSERT … ON CONFLICT DO NOTHING`, `checked_at` null).
    - **The resolve step.** A step the existing cron runs selects exactly `<cap>` rows (a named constant) `WHERE checked_at IS NULL OR (fangraphs_id IS NULL AND bbref_id IS NULL AND checked_at < now - <interval>)` (the interval a named constant of at least a week) `ORDER BY checked_at NULLS FIRST LIMIT <cap>`, asks the source for them (when MLB is the source: in batches through the batched `people?personIds=…` call, `fetchPlayers` in `functions/src/adapters/http/mlb.ts`, with the hydrate of AC 1, at most ⌈cap / batch size⌉ calls; when the Chadwick register is, from the register as AC 1 reads it, and if one run can't read the whole register to find them, the story stops and reports under rule 10, as AC 1 already allows for memory) and writes what it finds with `checked_at` set; the rest stay `checked_at IS NULL` for the next run. This step keeps no last-run time. It and the seeding pass run in their own cron scope, as each cron job in `functions/src/worker.ts` does (`inDatabaseScope` with a `ScopeLabel` of kind `cron` and a `job` of its own), so its database waits show in its own `db-round-trips` line (ADR-020's 2026-11-25 note, S220; 2026-11-25 backlog review).
    - **The seeding pass.** Games already stored before this story are seeded by the same cron step, after the resolve step: one SQL statement takes the next page of stored games by keyset, `WHERE (official_date, game_pk) > <cursor> ORDER BY official_date, game_pk LIMIT <seed page>` (`official_date` is indexed; the seed page a named constant counted in games, apart from the resolve cap), pulls only person ids out of each page's stored snapshot in SQL (`jsonb_path_query` over `$.plays[*].matchup.batter.id`, `$.plays[*].matchup.pitcher.id` and the box score's `$.boxscore.teams.*.batting[*].id`, plus `pitching[*].id` where S207 has stored it; S205 is superseded), inserts them `ON CONFLICT DO NOTHING`, and moves a single-row cursor `(official_date, game_pk)` to the page's last game in the same transaction, so no `games.document` reaches the Worker; an empty page means it is done, and it does nothing after.
    - **Tests:** a game's first write inserts its players once, and a later snapshot with the same roster inserts nothing; with more players waiting than the cap, after run 1 the unresolved count is the number waiting less the cap, with no more than ⌈cap / batch size⌉ calls, and run 2 resolves the rest; a run with nothing waiting makes none; a player with no cross-reference is selected again only after the interval; two seeding runs over more stored games than the seed page seed every player once, a run after completion does nothing, and the seeding query selects no `document` column into the Worker (a test on the SQL it runs).

    `GET /api/v1/players/:personId/profiles` reads that table: it answers the four URLs (`null` for a site whose id is unknown, including a checked player with no cross-reference), and 404 for a person with no row; it is in `ApiRoutes` (law L4) and the OpenAPI spec (additive, `pnpm api:breaking` exits 0, `web/src/api/generated/` regenerated). An answer from a checked row is cacheable at the edge for a day; a 404, or a row not yet checked, is sent with a short lifetime (minutes) so it updates once the job resolves it. Route tests: a known player, a player with no cross-reference, an unknown id (404). For law L3, the classification manifest (`functions/src/services/data-classification.ts`) labels the repository `none` (public facts about players) under its in-memory double's class and its Postgres adapter's class, and gives the ids table and the seeding cursor's table each their own `postgresTables` entry.
