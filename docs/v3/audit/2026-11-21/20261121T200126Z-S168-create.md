**Gap:** Building and checking the repository is one chain run from the root, so a one-line change in one area runs nearly every check in the repository, one after another. What it looks like at this story's writing (evidence of today's state only; the acceptance criteria below are written against whatever the workspace holds when the story runs):
- The root `package.json`'s `verify` is `pnpm build && pnpm dup:check && pnpm test:coverage && pnpm size`, run in sequence. `build` starts with `pnpm lint`, which is `pnpm backlog:check && eslint .`, one repo-wide step outside Turborepo, before any package builds. `test:coverage` runs Turborepo's `test:coverage` and then three root Vitest suites outside Turborepo, one after another: `test:backlog` (`scripts/backlog-vault/`), `test:tools` (`tools/`) and `test:selector` (`e2e/`). Those three areas have their own code and tests but are not workspace packages (`pnpm-workspace.yaml` lists `packages/*`, `functions` and `web`), so they have no tasks of their own and run on every change.
- In `turbo.json`, `test:coverage` depends on `^test:coverage`: a package's tests wait for every dependency's tests to pass, not just for what they build, so `web`'s and `functions`' tests can't start until `domain`'s, `ports`' and `mlb-api`'s have finished.
- `turbo.json`'s `globalDependencies` include `fixtures/**`, `openapi/**`, `tools/**` and `.github/workflows/**` beside the true toolchain files (`pnpm-lock.yaml`, `tsconfig.base.json`, `.nvmrc` and the like), so a change to a fixture, an ESLint rule or a workflow changes every task's hash, including `domain`'s, which reads none of them. No task declares its own `inputs`.
- The Turborepo cache is read only when `BT_TURBO_CACHE_READ` is set, which only CI's pull-request verify step sets, and written only under GitHub Actions (S152). A local `pnpm verify`, and so `scripts/audit.sh story`, runs every task every time.

**Impact:** Before S168, checking any change, however small, ran nearly every build and test in the repository, mostly one after another, locally and in pull requests. S168 impact: each area of the code builds and tests on its own and in parallel, and a change runs only the checks for the areas it actually touches (and the areas that use them), so small changes are checked in a fraction of the time, while every merge to `stage` still runs everything.

**Source:** Feature: Fast PR checks

2. **Every area with its own code and tests is a workspace unit with its own tasks.** Every tracked test file and test config in the repository (`git ls-files`: `*.test.*`, `*.spec.*` run by Vitest, `vitest.config.*`) lies inside exactly one workspace package, except Playwright's browser specs, which stay out of the local check (law P8). Every workspace package defines, in its own `package.json`, each of `lint`, `typecheck`, `test` (with coverage where its config sets floors) and `build` that applies to what it holds (TypeScript source → `typecheck` and `lint`; test files → `test`; an emitted artifact → `build`), and `turbo.json` runs them as that unit's tasks. No root script runs ESLint, `tsc` or Vitest itself; the only root tasks are the checks that truly read the whole repository, which the ADR names (at least the backlog check and the law tests that read the whole repository, such as law P8's and P11's), each its own named Turborepo root task (`//#<name>`), never folded into another step. Grader: walks `git ls-files` and the workspace list for the first two rules, and reads the root `package.json` and `turbo.json` for the third; a test file outside every unit, a unit missing an applicable task, or a root script calling `eslint`, `tsc` or `vitest` fails.
3. **Tasks depend only on what they truly consume.** In the task graph (`turbo run <every check task> --dry=json`), no unit's `test`, `lint` or `typecheck` task depends on another unit's `test` or `lint` task; a unit's tasks depend on its workspace dependencies' `build` (or `typecheck`, where that is what they read) only. So two units with no dependency path between them have no path between any of their tasks, and Turborepo runs them in parallel. Grader: computed from the dry run for every pair of units the workspace holds.
4. **Inputs are declared per task, and a change reaches only the tasks that read it.** Every task in `turbo.json` declares its `inputs` (or inherits Turborepo's default of the unit's own files plus what it names), and `globalDependencies` holds only the toolchain files the ADR lists as reaching every task (the lockfile, the base tsconfig, `.nvmrc`, `turbo.json` and the like); every other file outside the units that a task reads (fixtures, the API spec, ESLint rules, workflows, and whatever else exists when the story runs) is an input of exactly the tasks that read it. Grader: in a temporary copy of the tree, `turbo run … --dry=json` before and after a throwaway edit, for one source file in each unit and one file under each non-toolchain input the tasks declare: each edit changes the hash of exactly the tasks whose declared inputs include it, plus their dependents, and no other; an edit to a toolchain file the ADR lists changes every task's hash. The tree is left as it was.
5. **The local check runs only what a change affects.** `pnpm verify` (or the one entry point the ADR names in its place) runs only the tasks affected by the change against the base branch (the merge base with `origin/stage`, Turborepo's `--affected` or an equivalent filter), plus their dependents, and the repo-wide tasks whose inputs the change reaches, with the local cache read and written; it runs every task when a toolchain-wide input changed or when asked to (a flag or variable the ADR names, which `scripts/audit.sh story --reverify` and a release check use). `scripts/audit.sh story`'s ledger entry records what the gate did: which tasks ran, which replayed from the cache and which were not affected, so a narrowed run is never recorded as the whole gate. Grader: dry runs against a temporary base, as AC 4; given no change and no toolchain change, nothing runs; given a toolchain change, everything does; and the ledger fragment of a test run of `audit.sh story` in a temporary copy carries the three lists.
6. **CI uses the same task graph and cache.** CI's checks call the same entry point and the same Turborepo tasks as the local check (no second list of steps), so a pull request runs the affected tasks and replays or skips the rest; every push to `stage` or `main` still runs the full graph fresh with no cache read (S152's rule; owner, 2026-11-19: *"Stage reruns everything (Recommended)"*), so a wrong narrowing or a missing input shows on the next `stage` run instead of shipping. `ci-passed` still gates every pull request on one result, and `deploy.yml`'s gate runs the full graph. Grader: parses the workflows; the pull-request path calls the shared entry point, the push path forces a full run, and `scripts/backlog-vault/ci-law.test.ts` (or its successor) asserts both.
7. **One entry point, one exit code, and the laws still hold, per unit.** The local check stays one command with one exit code that is nonzero when any task it ran failed. Every law in `docs/v3/LAWS.md` names the task that enforces it, and that task is in the graph the full run executes; each unit keeps its coverage floor (law L6, rule 21: none lowered or dropped, and each moves with its code); `pnpm verify` still starts no browser (law P8, its test following the new graph); the law rows the ADR rewords say what now runs, in the wording the owner accepted; and each property the owner accepted as a new law is a row there, enforced by a test in a repo-wide task. Grader: every law's named task appears in the full dry run, no `vitest.config.*` floor is lower than at the story's base, and the repo-wide law task passes.
8. **A change confined to one leaf unit runs no other unit's tasks.** For every unit no other unit depends on, as the workspace holds them when the test runs, a dry run of the local check for a change to one source file in that unit lists tasks of that unit only, plus the repo-wide tasks whose declared inputs include that file. A test in the repo-wide law task (so it keeps holding as units come and go) proves it with Turborepo's dry run, and the grader runs it. The time saved is recorded, not targeted: the story's finishing commit adds a `**Measured:**` note with a local `pnpm verify` on a change to one leaf unit beside a full run on the same machine, and the pull request's own CI run times beside S152's measurements.
