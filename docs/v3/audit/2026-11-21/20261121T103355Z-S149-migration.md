**Gap:** Only a game page has a live connection: each in-window game's ingest object (`functions/src/game-ingest-object.ts`) writes Postgres, then publishes to that game's hub (`functions/src/game-hub-object.ts`), which pushes to viewers over `GET /api/v1/games/:gamePk/live` (S18; ADR-020). The scoreboard re-asks its day on the live cadence instead (`refetchInterval` in `web/src/api/schedule.ts`), so it has no live connection and can't show the Live marker. The owner wants it to have one (owner, 2026-11-16, told the polling scoreboard showed no Live marker: *"the scoreboard should have a live connection"*), opened only on a day with a game in its live window, the window game pages use, from 2 hours before first pitch to 3 hours after the game ends (`DEFAULT_CADENCE`, `packages/domain/src/window.ts`) (asked when, with that rule as the option's description: *"While a game is live"*), as one WebSocket per day from a hub per day (asked whether one socket per day or one per live game: *"One socket per day"*). ADR-020's amendment of 2026-11-16 records it.

**Impact:** Before S149, the scoreboard caught up with live scores every few seconds by asking again. S149 impact: while a game on that day is live, scores arrive on the scoreboard the moment BT has them, over one connection, and the scoreboard can say it is live.

**Acceptance criteria** (checks `scripts/verify-S149.sh` performs)

1. **The day hub.** A Durable Object class (`DayHubObject`, named `day-hub:<YYYY-MM-DD>`) holds the scoreboard's viewers for one date over hibernated, one-way WebSockets, as `GameHubObject` does for a game (ADR-020), reusing its code (generalized from `GameSnapshot` and `game-hub:` names where needed; `LiveHubState`, `functions/src/services/live-hub.ts`). `wrangler.jsonc` binds it (`DAY_HUB`) at the top level and in every environment block, and adds it in a new `migrations` entry after the existing ones (`{ "tag": "v3", "new_sqlite_classes": ["DayHubObject"] }`), leaving those as they are (grep). Unit tests with the fake Durable Object storage (`functions/src/services/fake-durable-storage.ts`): a connect gets the day's latest state; a publish reaches every open socket; the last viewer leaving ends its leases.
2. **Which games feed it.** A day hub registers a lease (`functions/src/services/hub-leases.ts`, generalized as needed) with the ingest object of every game on its date that is in its live window when its first viewer connects. On each lease renewal it re-reads the day, so a game that enters its window later (a night game, a doubleheader's second game) is registered then and a game whose window has ended is let go; it unregisters from all of them when its last viewer leaves. A day's schedule changes reach its hub too: when the cron's refresh changes a stored day, or S150's switch changes a game's state (including a mend that leaves the game's snapshot unchanged, which ingest doesn't publish), the writer calls the hub of each date that changed, once per refresh after the day's write rather than once per game, and for a game's state every date whose stored day lists the game (a suspended game's two days); the hub pushes the day if it has viewers and otherwise ignores the call (on the local Node server, which has no hubs, the call is skipped), so a postponement or a new probable pitcher arrives while the socket is open and the scoreboard isn't polling. Each game's ingest object, after it writes a game, publishes that game (the `GameSnapshot` it already publishes) to every registered hub, game or day, as it does today for game hubs; a day hub does what AC 3 says with it. Unit tests: a game in its window at connect reaches the day hub; a game that enters its window after the hub registered reaches it after the next renewal; a game of another date never does; a doubleheader's two games both do; a schedule refresh that changes the day (a postponement) reaches the hub with no game update. A late game on the evening's MLB date is refreshed after midnight UTC only once issue #73 is fixed, which S149 depends on.
3. **The day hub only reads.** When a game's update reaches it (after the game's ingest has written the game and its shared state, S150), the day hub reads its day with S150's read-only `readScheduleDay` (the stored day joined to its games' states, never refreshed from MLB) and pushes that whole day, the shape `GET /api/v1/schedule?date=` serves, the `ScheduleDayResponse` shape, so every push is the whole day and a missed one is healed by the next. It writes nothing to Postgres and fetches nothing from MLB; which source feeds a game's score is S150's switch alone. On a viewer's first connect it sends the same read. Unit tests: a game's new score is in the next push; two games of the date updated together are both in the pushes that follow; a read that fails pushes nothing.
4. **Versioned (ADR-022).** A push's version is the served day's version (S150 AC 6: the stored day's served version, which only rises), and the client applies a push through `applyIfNewer` (`packages/domain/src/versioning.ts`), like a game's, so a duplicate or an older push changes nothing. A day push is the whole day, so the day stream applies any newer version at once, however far ahead (a game's stream keeps its rule of refetching on a gap, since a game push is too). Unit test: a push five versions ahead is applied with no refetch. A reconnect passes its last version (`?since=<version>`) and gets the full day if it is behind. Unit tests: a duplicate, an older and a newer push, client and hub sides.
5. **The route.** `GET /api/v1/schedule/live?date=<YYYY-MM-DD>` (a query parameter, like its sibling `GET /api/v1/schedule?date=`) upgrades to the day hub's WebSocket only while the day has a game in its live window, worked out at request time from the day's games and the clock with `scheduleWindowMode` (`packages/domain/src/window.ts`, which applies `isGameInActiveWindow` to each game; ADR-025: one implementation of "the day has a game in its window"), not from the stored `windowMode`. The day is read through the existing day read (as `GET /api/v1/schedule?date=` reads it, fetching a day BT doesn't hold yet; the socket's own pushes then use the read-only `readScheduleDay`, AC 3), and a day with no games answers as an out-of-window day, not as an error; otherwise it answers as `GET /api/v1/games/:gamePk/live` does for a game out of its window. Like the game route it sits outside `ApiRoutes` and the OpenAPI spec (`functions/src/handlers/live.ts`): it is added to the `STREAMING_ROUTE_EXCEPTIONS` tuple and to `API_ROUTER` (`functions/src/handlers/api.ts`), so the route-table test still passes and `pnpm api:spec` leaves the spec unchanged (grep). A `*.workerd.test.ts` runs the real Worker in workerd: a socket to an in-window day receives the day after a game's ingest writes; a request for a day out of its window doesn't upgrade.
6. **The scoreboard connects, and says whether it is connected.** While the shown day has a game in its live window (`scheduleWindowMode` on the cached day's games at the current time, the function AC 5 uses, re-judged at least once a minute, so a day loaded before its first game's window opens connects when it does), the scoreboard opens one socket to its day through a `useLiveDay` hook in `web/src/api/` that reuses `LiveGameStream`'s reconnect, backoff, `?since=` and polling fallback (`web/src/api/live-stream.ts`, generalized rather than copied). It writes each applied push into the day's cache through `writeScheduleDay` and stops the day query's own re-asking while the day streams (in its window), as `web/src/api/game.ts` does for a streaming game (its `streaming` is the in-window flag, not the socket's open state, so a reconnect wait doesn't start query polling on top of the stream's own fallback, which does the polling). `useLiveDay` reports whether its socket is open (open; or closed, reconnecting, fallen back to polling, stopped). It opens no socket for a day out of its window, closes it and settles to the cached day's polling policy when a pushed day leaves its window, and closes it when the shown day changes or the page unmounts. Unit tests with the stream's fake socket and fake timers: an in-window day connects and a push updates the scoreboard; open reports open; a close, each reconnect wait and the polling fallback report not open; an out-of-window day doesn't connect; a day whose only game's window opens 5 minutes later connects once the clock passes it; a day leaving its window closes the socket; switching days closes the old socket; during a reconnect wait the day query starts no refetch interval.
7. **The marker.** If S148's `LiveMarker` component exists in `web/src/layout/` (grep), the scoreboard shows it exactly while `useLiveDay` reports open, where S147's ratified amendment places it (RTL: open shows it; closed, reconnecting, polling and an out-of-window day don't). If it doesn't exist yet, S148 AC 3 wires the scoreboard when it ships, and this AC passes on that grep.

**Notes:**

- **Why a day hub, not one socket per live game.** The owner chose one socket per day (2026-11-16). A busy day has about 15 live games, which would have been 15 sockets per scoreboard viewer, each pushing a whole game when the scoreboard needs only its row.
- **Before first pitch and after the last out** the scoreboard is connected, and shows the marker, for as long as a game on its day is in its live window (2 hours before first pitch to 3 hours after the game), the rule the owner chose.
- **The day of a game** is its official date in the schedule (`officialDate`), the date the scoreboard lists it under, so a game that runs past midnight stays on its day's hub.
- **Hide Scores** is unchanged: the pushed day is the same payload the HTTP route serves, and the scoreboard masks it as it masks a fetched one.
