**Acceptance criteria** (checks `scripts/verify-S158.sh` performs)

1. **A run journal.** `node scripts/backlog-vault/claims.ts run start --n <N> --c <C>` (both required) writes `.run/run.json` (`{ "id", "n", "c", "startedAt", "events": [] }`, the ID with no `-`, so a fragment name can carry it); with a `run.json` already present it exits 1 naming that run. `run start --resume` takes no `--n` or `--c`, keeps the journal (its `n` and `c` stand) and appends a `run-resume` event. Every write to `run.json` (`run start`, `run event`, and `claim`'s append) takes the same lock as `claim`, so no event is lost to a concurrent write. `claims.ts run event <kind> [<ID>] [--pr <n>] [--path <p>] [--barrier]` appends `{ kind, id?, pr?, path?, barrier?, at }`. Item kinds need an `<ID>` that passes `in-flight.ts`'s `ITEM_ID`: `item-start` (with `--barrier` for a barrier item, step 3.1), `needs-lead`, `park`, `resume`, `held`, `pr-open` (with `--pr <n>`, required), `ready` (joined the merge order), `merged`, `conflict` (a record file conflicted in a merge; `--path` required) and `duplicate` (a duplicate implementation found built, at review or merge). Run kinds take no ID: `gate-open`, `gate-close`, `interrupted` (the owner stopped the run). Any other kind, a missing required ID or flag, or an ID that fails `ITEM_ID` exits 1. `claims.ts claim` appends `claim`, or `claim-refused` on an exit 1, itself, and only when a `run.json` exists and it is not a `--dry-run`: otherwise it writes no event and behaves exactly as today. `claims.test.ts` covers each kind, each refusal, a refused second `run start`, `--resume`, `claim` with and without a journal, `claim --dry-run`, and two appends made at once (both events kept).
2. **One summary function** (ADR-025). `scripts/backlog-vault/runs.ts` exports a pure `summarizeRun(journal, findingsByPr, earlierRuns, { abandoned })`. **Active time** leaves out every span from `interrupted` to the next `run-resume`; every duration below is active time. An item is **in flight** from `item-start` to its `merged`, `park` or `held`, and again from each `resume` (an item with no `item-start` is never in flight). It returns: items started (`item-start` events, barriers included); the peak number of non-barrier items in flight at once; per item, build time (`item-start` → `ready`), merge wait (`ready` → `merged`) and owner wait (each `park` → its `resume`, or the run's end when none, listed as still parked); gate time (each `gate-open` → `gate-close`); drain (the first `ready` → the last `merged`, or `null` when nothing merged); record conflicts (`conflict` events); duplicate implementations (`duplicate` events; `claim-refused` is the admission check working and never counts); and Claude-review findings per opened pull request (the `--pr` numbers of `pr-open` events; `null` when none opened). `runs.test.ts` checks every value against hand-built journals, including a resumed item, an interrupted-then-resumed run, a barrier, an item parked to the end, and a run with no pull request.
3. **What counts, and what is clean.** `summarizeRun` marks a run **counted** when it started at least 4 items (S156's Phase 2 exit criteria), its non-barrier peak in flight reached its `C`, at least one of its pull requests merged, and `abandoned` is false (AC 4); an uncounted run neither moves concurrency nor resets the count. A counted run is **clean** when it has no record conflicts, no duplicate implementations, a drain under 3 hours of active time (S156's Phase 2 exit criteria), and Claude-review findings per pull request no higher than the lowest of the earlier counted runs at `C` = 2 (owner, 2026-11-20, choosing *"First C=2 run sets it (Recommended)"*: "Each later run is clean on this point if its findings per pull request are no higher than the lowest earlier recorded run's. The first run passes this condition by definition."; "recorded" is read here as a counted run's entry, so a run too small to count never sets the bar). The first counted run at 2 has no earlier one and meets this condition. The bar only falls: after a counted run with 0 findings per pull request, a later run is clean on this point only with 0 too, as the owner's answer says. `runs.test.ts` covers: 3 items started, a non-barrier peak of 1 at `C` = 2, no pull request merged, and an abandoned run (each uncounted); the first counted run at 2 with findings (clean); a later run with more findings per pull request than the lowest earlier one, a record conflict, a duplicate, and a 3-hour active drain (each not clean); a run whose interrupted gap is longer than 3 hours but whose active drain is under (clean); and a `claim-refused` event (clean).
