**Gap:** FEATURES' Inning / game insight pipeline and ADR-011 plan, at the end of every inning of every game in its window, a few **insight items** (notable stats, things to note) appended to an in-game feed, and nothing produces them: ingest doesn't mark inning ends and BT stores no feed. ADR-011 left open "heuristic vs model for inning items". The owner put end-of-inning insight items in the backlog (owner, 2026-11-22: *"1, 2, 3, 4, 5, 6, 7, 8 should go into the backlog."*) as an API feature for now (*"Oh ok, fair. I would say we can just make these API features for now."*), checked as the owner described (*"I imagine I could have the recap system write a recap AND evaluate the output with a fact checker agent until it's verified"*). The research (`docs/v3/AI-RESEARCH-2026-11.md` §5 row 4) has rules find the candidates and a cheap model pick and phrase one to three, with quiet innings skipping the model.

**Impact:** Before S181, BT said nothing about a game while it was being played beyond the raw plays. S181 impact: after each inning of a live game, BT adds one to three short notes worth knowing (a pitcher tiring, a streak, a big swing in who's likely to win), each fact-checked, building a running feed of the game; an inning with nothing notable adds nothing and costs nothing.

**Acceptance criteria** (checks `scripts/verify-S181.sh` performs)

1. **Inning ends, detected once.** One domain function, `inningEnded(previous, next)`, answers the inning that ended when an ingest tick moves a game past the end of a full inning (the bottom half done, or the top half of the 9th or later when the home team leads, or a walk-off ending the game), from the stored linescore and plays (table test over the 823823 replay's states, extra innings, a walk-off, a rain-shortened game, and a tick that jumps two innings at once, which yields both). Ingest enqueues one job per ended inning, keyed `gamePk:inning:<n>` (a repeat is a no-op, ADR-011's idempotency; test), and the next tick runs it without a batch; the ingest tick itself never waits on a model (test: the tick returns before the stub answers).
2. **Rules find the candidates.** One pure domain function, `inningInsightCandidates(game, inning)`, finds candidates from BT's data with the facts each rests on, at least: a win-probability swing of 15 points or more within the inning; a pitcher's fastball velocity in the inning 1.5 mph or more below his first inning's; a pitcher passing 100 pitches; batters retired in a row (9 or more) or a no-hit bid still alive (5th inning or later); a batter's second home run or third hit of the game. Thresholds are named constants. Table tests for each, on invented games, and an inning with none.
3. **Quiet innings skip the model** (ARCHITECTURE §5's knob): an inning with no candidate writes nothing and makes no call (test counts stub calls: zero).
4. **The model picks and phrases one to three.** Otherwise S176's `writeVerified`, with the inning job's instructions and only the candidates' facts, writes 1–3 `InsightItem`s (`kind`, `title`, `body`, the `refs` of plays and players behind it), through the full loop (rules checker, fact-checker agent, up to two revisions); an inning whose notes still fail adds nothing.
5. **An append-only feed.** Items are stored per game in inning order (`insight_items`, Postgres; a migration; never edited once stored), and `GET /api/v1/games/:gamePk/insights` answers `AiOutputResponse<InsightItem[]>` in that order, to whom `canReadAiOutput` allows, `null` for a game with none yet; in `ApiRoutes` (law L4) and the OpenAPI spec (additive, `pnpm api:breaking` exits 0, `web/src/api/generated/` regenerated); a live game's answer is cached as live data is (ADR-021's live lifetime).
6. **The package gains its highlights.** S178's package gains `insightHighlights`: up to three stored items, chosen by one domain function by `salience` (a number each candidate rule assigns); a package built before any item exists has an empty list (test). Its `promptVersion` doesn't change, since no prompt does.
7. S181's **Status** is `done`: its snapshot records `done`, the status it ships with, written by `audit.sh story` (`story_snapshot_status`).
