**Gap:** ADR-011 and FEATURES' Inning / game insight pipeline make a finished **game package** ("what mattered": key moments, standout lines, accomplishments, narrative beats) the canonical input for the AI recap, the day digest and later ranking, and nothing builds one: BT notices a game going final only to stop polling it, and stores no package. The owner put the postgame package in the backlog (owner, 2026-11-22: *"1, 2, 3, 4, 5, 6, 7, 8 should go into the backlog."*), as an API feature for now (*"Oh ok, fair. I would say we can just make these API features for now."*), and the research's build order puts it first among the text features, since the recap, the digest and the ranker read it (`docs/v3/AI-RESEARCH-2026-11.md` §6 step 3).

**Impact:** Before S178, once a game ended BT kept only its raw data. S178 impact: shortly after every game ends, BT stores a short "what mattered" summary of it (the plays that swung it, the players who stood out, anything historic, and a headline with a few lines of story, fact-checked before it is kept) that any app or later feature can ask for.

**Source:** Feature: Inning / game insight pipeline; AI game companion

**Acceptance criteria** (checks `scripts/verify-S178.sh` performs)

1. **BT computes the facts.** `packages/domain` exports `GamePackage` (`gamePk`, `version`, `finalAt`, `keyMoments`, `standoutLines`, `accomplishments`, `videoOrder`, `narrative`) and one pure function, `buildGamePackageFacts(game)`, reusing S177's package fact pack: `keyMoments` from `topPlaysByWinProbabilityAdded`, ordered as they happened; `standoutLines` from one function choosing the game's standout batting and pitching lines from the box (reusing `pitcherLine` / `batterLine`); `accomplishments` from one rules function over the game (at least: a cycle, a no-hitter or perfect game, a complete-game shutout, a multi-home-run game, 10 or more strikeouts by a pitcher, a walk-off), each with the plays it rests on; `videoOrder` from `rankHighlightsByImpact`. Tests on fixtures and on invented games for each accomplishment, and a game with none.
2. **The model writes only the headline and the beats.** `narrative` (`headline` and 2–4 `beats`) comes from S176's `writeVerified` with the package job's instructions and the full loop (rules checker, then the fact-checker agent, up to two revisions); every other field is BT's own computation and is never sent back through a model. When the loop publishes nothing (failed, budget stopped, no model configured), `narrative` is `null` and the rest of the package is still stored and served.
3. **Triggered once per final, and survives a crash.** One domain function, `gameFinalTransition(previous, next)`, says when an ingest tick moves a game to final (and not for postponed, suspended or cancelled games, which are never final; table test over MLB's status codes from `fixtures/raw/gamestatus.json`). Ingest then enqueues one job keyed `gamePk:final:<source version>` in a Postgres job table (a second enqueue of the same key is a no-op; test), and a scheduled tick (the existing cron, `wrangler.jsonc`) runs queued jobs. A job's state (`queued`, `submitted` with its provider batch id, `done`, `failed`) is stored, so a tick that stops between submitting and storing the result resumes the submitted batch on the next tick instead of paying for it again (test with the stub: a crash after submit, then a tick that finishes it with no second writer call).
4. **Postgame is batched, at half price.** `AiModelClient` gains a batch submission and a result lookup; the Anthropic, OpenAI and Google adapters implement them (tests on recorded responses), and the Workers AI adapter, which has no batch, falls back to an immediate call. The package job submits its calls as a batch, and S176's meter prices them at the batch rate.
5. **Late changes rebuild it.** Media or data that arrive after the final (the post-game trail) change the game's source version; the next tick builds a new package for the new version, which replaces the served one (ADR-011: replace-on-final, versioned), and the old one stays in S176's log. A newer version is never replaced by an older one (ADR-022; test).
6. **Served.** `GET /api/v1/games/:gamePk/package` answers `AiOutputResponse<GamePackage>`: `output` is `null` for a game with no package yet (not final, or not built); `narrative` is served only to whom `canReadAiOutput` allows and is `null` for anyone else; it is in `ApiRoutes` (law L4) and the OpenAPI spec (additive, `pnpm api:breaking` exits 0, `web/src/api/generated/` regenerated), cached by `cacheLifetimeMs` like a finished game (ADR-021). Route tests: a final game with a package, one whose narrative failed, a live game (`output: null`), an unknown game (404).
7. The package's `insightHighlights` (the best inning notes) is not built here: S181 adds it once inning notes exist.
8. S178's **Status** is `done`: its snapshot records `done`, the status it ships with, written by `audit.sh story` (`story_snapshot_status`).
