Issue: #232

**Body**

<!-- bt-body:begin -->
**Gap:** MLB publishes the strike zone the ABS system judged a game against — its top and bottom as a share of the batter's height, and its width — through the live feed's `ruleSettings` hydrate; BT doesn't keep it (owner, 2026-10-30: *"Also add stories to ingest all of this extra data."*).

**Impact:** Before S100, BT drew the strike zone from each pitch's own top and bottom. S100 impact: BT keeps the zone the game's ABS challenges were actually judged against.

**Source:** Feature: More MLB game data

**Baseline:** BT ingests the rules each game was played under (the live feed asked with `hydrate=ruleSettings&fields=gameData,ruleSettings`, recorded as `fixtures/raw/rulesettings-823823.json`, bundled for local dev, scanned by `pnpm mlb:scan-drift`), typed in `packages/mlb-api/src/rule-settings.ts` and parsed with zod (`parseGameRuleSettingsResponse`), fetched through `MlbStatsClient.fetchGameRuleSettings` (HTTP, fixture and overlay clients) and projected by `functions/src/mappers/rule-settings.ts` onto `GameSnapshot.ruleSettings`, each setting by name with its label, description, value and unit (on 823823 the ABS zone's top is 53.5% and its bottom 27% of the batter's height, its width 17 inches); the spec and generated web types carry it additively. It is a request of its own rather than a hydrate on `fetchGame`'s live feed (the reuse check: nothing in `packages/mlb-api/src/live.ts` or `functions/src/mappers/live.ts` read the settings, and riding the feed would add them to every live poll for a value fixed before first pitch), asked off the fetch path through S101's helpers extended rather than copied: `askGameRuleSettings` through `askWithinLimit`, `askedExtraDue` (S101's `uniformsDue` generalized to name the extra), `withAskedExtras` / `askDueExtras` asking both extras at once (so a read or write waits one `PLAY_METRICS_LIMIT_MS` at most), `keepStoredExtras`' `KEPT_WHOLE` list, the ingest object's final-trail guard (`EXTRAS_ASKED_KEY`) and a fifth backfill extra source in `EXTRA_SOURCES`, given up after 14 days of games without any. A final game stored before S100 and past its re-check window, which the backfill skips as already stored, stays without the field: the gap S99 and S101 accepted (#619), accepted here too. No view draws the zone yet.

The HTTP adapter (`functions/src/adapters/http/mlb.ts`) knows one `baseUrl` (statsapi); a feed on another host needs its own base URL, kept testable.

**Fence widened to `web/src/api/generated/` (2026-11-02 backlog review, after S94's rule 10 stop at `3e3a4a2`).** A field added to the game payload regenerates `openapi/bt-api.v1.json`, and ADR-016's drift gate (`web/src/api/codegen.test.ts`, in `pnpm verify`) then fails until `web/src/api/generated/bt-api.v1.ts` is re-rendered from it (`pnpm api:types`). S93's identical change edited that file (`7e2e080`). Only the generated directory joins the fence: the field is optional, so no web code or test literal has to change; anything else under `web/src/` is still a rule 10 stop.

- **A new extra must not slow a game fetch or add a request to every poll (2026-11-25 backlog review, after S216).** Since S216, `HttpMlbStatsClient.fetchGame` (`functions/src/adapters/http/mlb.ts`) fetches the live feed, then its extras at once, and answers a cold read without the play metrics once they pass `PLAY_METRICS_LIMIT_MS` (750 ms, S216 AC 5; `functions/src/services/ingest.play-metrics.test.ts`). Joined to that `Promise.all` unbounded, a slow or hanging rule-settings request would hold every game read until it answered, and each live poll would call it again for a value that doesn't change during a game. So the call either runs off that path or under the same limit, and AC 5's test adds: a rule-settings request that never resolves leaves `fetchGame` answering within `PLAY_METRICS_LIMIT_MS` with the field absent (review-class checklist items 3 and 7, partly present data and upstream request budget). The reuse check's `packages/mlb-api/src/live.ts` is the place to ask whether `hydrate=ruleSettings` can ride on the live feed request `fetchGameFeed` already makes, with no request of its own; if it can, AC 3's method may read it from there, and the recording in AC 1 still holds the hydrated response.

- **Asked off the fetch path, kept across refreshes (2026-11-25 backlog review, after S99).** S99 asks its extra (the player of the game) only outside `fetchGame`, at each ingest path that writes a game (`ingestScheduleDay`, `readGames` and `tickIngest` in `functions/src/services/ingest.ts`, `recheckDueGame`, the game's ingest object in `functions/src/services/game-ingest.ts`, and the backfill), and keeps a stored value a fetch lacks at both game writes (`keepPlayerOfTheGame`). The sequence that breaks AC 5 without that: the rule settings are asked once, the next live poll's `fetchGame` answers without them, `storeGames` writes the fetched game whole, so the stored field disappears and each later poll that doesn't ask makes a new version for its absence (review-class checklist items 2 and 3). S101 has since landed and generalized S99's helper, so this story reuses it (next note). A game stored as final before this story never gets the field unless a path asks it again, the gap S99 accepted (#619): the ledger notes say whether this story accepts the same gap. Turn cap raised from 12 to 14 for this wiring.

- **Reuse what S101 built (2026-11-25 focused backlog review, after S101 merged).** S101 generalized S99's ask and keep, so AC 5's shared helper now exists and is extended, not written again: the keep is `keepStoredExtras` in `packages/domain/src/player-of-the-game.ts` (`ruleSettings` joins `StoredExtras` and the `KEPT_WHOLE` list, whose comment already says a new extra joins it rather than getting its own keep); the bounded ask is `askWithinLimit` in `functions/src/services/player-of-the-game.ts` (an `askGameRuleSettings` beside `askGameUniforms`); the decision when to ask generalizes `uniformsDue` (none stored, and the game is new, its status changed, or it is final) to name the extra rather than copying it as a second function with the same body. If the settings are asked off the fetch path as the uniforms are, they ride the same wiring rather than a parallel one: `ingestGame`'s optional `mlb` (its `Pick` gains `fetchGameRuleSettings`), the cold read's one `Promise.all` in `readGames` (so a read still waits one bounded limit at most, not one per extra), and the ingest object's `UNIFORMS_ASKED_KEY` final-trail guard in `functions/src/services/game-ingest.ts` (renamed if it now covers both extras, so a final trail asks neither on every poll). Every adapter S101 taught `fetchGameUniforms` learns the new method too: the HTTP and fixture clients, `functions/src/adapters/overlay-mlb.ts`, `functions/src/test/recorded-mlb.ts`, the recorder (`functions/src/services/recorder.ts`) and `scan-drift.ts`. **The backfill**, when the settings are asked off the fetch path (riding the live feed request instead, they come with the backfill's own feed fetch), matters: `functions/src/services/backfill.ts` writes its games through `ingestGame` with `mlb` removed and asks each extra itself as one of `EXTRA_SOURCES`, so an ask wired only into `ingestGame` never reaches it. The sequence that breaks AC 5 then: a backfill over last week stores each game as final without `ruleSettings`, its 7-day re-check window passes, and no later write asks again. So either `ruleSettings` joins `EXTRA_SOURCES` (asked while due, bounded, its give-up counted like the uniforms'; test in `backfill.test.ts`), or the ledger notes accept the gap with the #619 one (review-class checklist items 2, 3 and 7).
