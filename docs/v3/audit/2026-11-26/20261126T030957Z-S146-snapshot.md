**Gap:** Whether staging deploys is decided by a path list: `scripts/ci-changes.sh` calls any `*.md`, `docs/` or `.claude/` change docs and everything else code (owner, 2026-11-07: *"Things like this shouldn't trigger CI."*; staging stopped deploying docs-only pushes on 2026-11-11). A list says nothing about what the build actually reads. A change to a script, a test or a fixture the app never bundles still rebuilds, migrates and redeploys staging, and the list must be kept by hand. The owner asked for the decision to come from the build's inputs instead (2026-11-11): *"ultimately it'd be nice if this used some kind of hashing or something rather than directory allow/blocklists … What I'd like is for something to check the inputs to the build at build time or prior to it (ideal) or for the build output hash to be compared to the last deployed output hash (less ideal, only works if the build output is deterministically identical with identical inputs)"*, then *"yeah, I like your plan"* to recording what the build reads and checking those files' hashes before the next build.

**Impact:** Before S146, staging rebuilt and redeployed after almost any change, even one that changed nothing the site is built from (a test, a script, a fixture), and which changes counted was a hand-kept list. After S146, each deploy records exactly which files went into it, and the next one skips the build and the deploy when none of them changed, so staging only redeploys when what it serves could actually be different.

**Source:** Pillar: Delightful — deploys run only when what they build from changed, so changes reach staging without churn from edits that change nothing it serves; the same reason S89 cites for faster checks. Asked "Can the input-hash story cite the Delightful pillar (as S89 did), or Dependable?" Approved by owner 2026-11-11: "delightful"

**Baseline:** **S146** landed: staging and previews deploy only when what their build reads changed. `pnpm build:inputs record` (`functions/src/deploy/build-inputs.ts`) writes, after a build, every file it read with its git blob hash at the built commit: Vite's module graph (a `bt-build-inputs` plugin in `web/vite.config.ts`, joining the service worker's build too), the Worker's `wrangler deploy --dry-run --metafile` inputs, an esbuild graph of the deploy scripts and `web/vite.config.ts` (`GRAPH_ENTRIES`), and a named list (lockfile, workspace `package.json` and `tsconfig*.json`, `.nvmrc`, `wrangler.jsonc`, the configs Vite finds by lookup (`web/postcss.config.cjs`), `web/index.html`, `web/public/`, the migrations, `deploy.yml` and its two shell scripts), plus `BT_RELEASE` and the deployed commit. `deploy.yml` stores it as the `build-inputs-staging` / `build-inputs-preview-<N>` Actions artifact only after the deploy step succeeds (a skip, decided in a `staging-inputs` job that never touches the `staging` environment, re-stores it with `covers`, its own commit; only when runs race, the `staging` job repeats the served check, or decides itself after its `staging-inputs` was cancelled, and a run it then skips shows in that environment); the next run fetches it and runs `node functions/src/deploy/build-inputs.ts check` (only `node:` imports) before install, skipping install, build, migrations and deploy on `unchanged`. Staging trusts a record only of the commit it serves (`--served`), and only from this repository's own Deploy runs on `stage` (`build-inputs.ts trust`); a skipped preview still comments, naming the recorded head commit; `preview-teardown` (now `actions: write`) deletes a pull request's records; a `reopened` event always deploys; a `workflow_dispatch` run on `stage` with `force` deploys staging (never over a newer commit) and `changes` answers `code=true` for it; production always deploys. The release rule's prepare step (1) may target a later `stage` commit the check finds unchanged against staging's record of the served commit.

1. **Recording the inputs.** A `pnpm build:inputs record <out>` command (its code under `functions/src/deploy/`) writes, after a build, a JSON record of every file that build read, each with its git blob hash at the built commit:
    - every module the web build bundled, taken from Vite's own module graph (a plugin in `web/vite.config.ts` that writes the list it reports, never a hand-kept list of folders);
    - every module the Worker bundle read, taken from the bundler's own metafile (`wrangler deploy --dry-run --metafile`);
    - a short, named list of inputs outside those graphs: `pnpm-lock.yaml`, every workspace `package.json`, `.nvmrc`, `wrangler.jsonc`, the TypeScript, Vite and Wrangler configs and every repository file those configs import (`web/vite.config.ts` imports `web/src/pwa/options.ts`), `web/index.html`, every file under `web/public/` (copied, not imported), every migration the deploy applies, and `.github/workflows/deploy.yml` with the scripts its deploy steps run and every repository file those scripts import, taken from a bundler's graph of those entries (for example an esbuild metafile of `functions/src/scripts/deploy-bootstrap.ts`, `db-migrate.ts` and `db-reapply-deletions.ts`), not a hand list.
    - the build's inputs that aren't files: the release label `BT_RELEASE` (`scripts/build-release.sh`, read by `web/vite.config.ts`), so moving a merged pull request to another milestone changes the record. The commit in the version line is not an input: a skipped deploy keeps the version line's older commit, and README says so.

   Files under `node_modules/` and virtual modules (ids starting `\0` or `virtual:`) have no git blob and are left out: `pnpm-lock.yaml` stands for the dependencies. Unit tests (`functions/src/deploy/`) show, against a fixture repository: a file the build imports is recorded; a Markdown file and a test file are not; a file under `web/public/`, a migration, `web/index.html` and a file a config imports are; a `node_modules` path and a virtual module are left out without failing; a file only `deploy-bootstrap.ts` imports (such as `functions/src/deploy/bootstrap.ts`) is recorded, so an edit to it alone makes `check` fail; and `check` given a different `BT_RELEASE` than the record's fails.
2. **Checking the inputs.** The check runs with plain `node` and no installed dependencies (Node 24 runs TypeScript with only `node:` imports), so it can run before `pnpm install`: `node functions/src/deploy/build-inputs.ts check <record>` (also `pnpm build:inputs check <record>`, each given the build's `BT_RELEASE`) exits 0 and prints `unchanged` only when the record parses, its `BT_RELEASE` is the one given, and every file it lists has the same blob hash at HEAD. It exits nonzero, naming the first difference, for: no record, a record it can't parse, a listed file whose hash changed, a listed file that was deleted, and a record made by a different version of the command. Unit tests cover each case. A new source file can only enter a build through an import added to a recorded file, so that edit changes a recorded hash; a test shows adding an import to a recorded file makes `check` fail.
3. **Deploying from it.** In `.github/workflows/deploy.yml`, the `staging` job (through the `staging-inputs` job it needs) and the `preview` job each fetch the record of their environment's last successful deploy before installing or building (if the record is an Actions artifact, `staging-inputs`, `staging` and `preview` gain `actions: read` and `preview-teardown` gains `actions: write`, which deleting one needs; a job that gains a `permissions:` block keeps every scope its steps use today, since a job block replaces the workflow's: staging's `contents: read`, `pull-requests: read` and `issues: read` for `scripts/build-release.sh merged`, and the preview's `pull-requests: write` for its comment and `issues: read` for `build-release.sh pr`), and skip install, build, migrations and deploy when `check` prints `unchanged`. This is an extra skip inside the jobs: the docs-only gate and its law P11 test (`scripts/backlog-vault/ci-law.test.ts`, outside this story's fence) stay as they are, so verify still runs only for code. A record is stored only after its deploy step succeeds, so a failed or cancelled deploy never leaves one, and it names the commit it deployed: staging deploys when the commit it serves (`bt-commit.txt`) isn't that record's commit, so a `wrangler rollback` or an older run landing last is never left in place. Only a record stored by this repository's own Deploy runs is trusted: for staging, a push or manual run on `stage` whose commit is on `stage`; for a preview, that pull request's own runs; and a record listing no files is never `unchanged`. The one other store is a skip's: a run skipped for unchanged inputs stores that same record again, unchanged but for `covers`, naming its own commit (`build-inputs.ts cover`), so the record says which commit staging stands for (`build-inputs.ts stands`). The skip is decided in a `staging-inputs` job that the `staging` job needs, under the same `deploy-staging` concurrency group and with no environment, so a skip decided there never touches GitHub's `staging` environment (owner, 2026-11-26: "Only real deploys (Recommended)"). Two exceptions, both when runs race in that group: the `staging` job repeats the served-commit check before deploying, since another run may have deployed or skipped between the two jobs, and it decides itself (the input check and cover) when its `staging-inputs` job was cancelled by another job queuing in the group; either way it may deploy, so it holds the environment, and a run it then skips still shows there. Staging's served-commit check still runs, comparing this commit with the one staging stands for, so an older run never deploys over a newer one, even a newer one that skipped. A skipped preview still posts its comment, saying the preview from the recorded commit still serves this one; a preview's record names the pull request's head sha for that comment, not `GITHUB_SHA`, GitHub's test merge commit no one can look up. A record is only trusted while its Worker exists: `preview-teardown` deletes the pull request's record along with its Worker, and a failed deletion fails the teardown job rather than being swallowed; a `reopened` event always deploys, so a reopened pull request never gets a "still serves" comment for a deleted preview. A manual run of Deploy for `stage` with a `force` input deploys staging whatever the record says, but only the commit staging stands for or a newer one (for a rotated secret or variable, which changes no file), and README names it: the workflow gains a `workflow_dispatch` trigger with that input, the `changes` job answers `code=true` for it (as it does for a release, so `verify` runs), and the staging job's `if:` admits that event as well as a push; without both, a forced run on a `stage` whose head already passed would be stopped by `code=false` before the record is read. The `production` job always deploys. A test in `functions/src/deploy/` reads `deploy.yml` and pins all of this, the jobs' permissions included.
