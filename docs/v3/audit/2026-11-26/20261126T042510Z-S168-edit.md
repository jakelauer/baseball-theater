**Gap:** Building and checking the repository is one chain run from the root, so a one-line change in one area runs nearly every check in the repository, one after another. What it looks like at this story's writing (evidence of today's state only; the acceptance criteria below are written against whatever the workspace holds when the story runs):
- The root `package.json`'s `verify` is `pnpm build && pnpm dup:check && pnpm test:coverage && pnpm size`, run in sequence. `build` starts with `pnpm lint`, which is `pnpm backlog:check && eslint .`, one repo-wide step outside Turborepo, before any package builds. `test:coverage` runs Turborepo's `test:coverage` beside three root Vitest suites outside Turborepo (through `concurrently`, one at a time under GitHub Actions): `test:backlog` (`scripts/backlog-vault/`), `test:tools` (`tools/`) and `test:selector` (`e2e/`). Those three areas have their own code and tests but are not workspace packages (`pnpm-workspace.yaml` lists `packages/*`, `functions` and `web`), so they have no tasks of their own and run on every change.
- In `turbo.json`, `test:coverage` depends on `^test:coverage`: a package's tests wait for every dependency's tests to pass, not just for what they build, so `web`'s and `functions`' tests can't start until `domain`'s, `ports`' and `mlb-api`'s have finished.
- `turbo.json`'s `globalDependencies` include `fixtures/**`, `openapi/**`, `tools/**` and `.github/workflows/**` beside the true toolchain files (`pnpm-lock.yaml`, `tsconfig.base.json`, `.nvmrc` and the like), so a change to a fixture, an ESLint rule or a workflow changes every task's hash, including `domain`'s, which reads none of them. No task declares its own `inputs`.
- The Turborepo cache is read only when `BT_TURBO_CACHE_READ` is set, which only CI's pull-request verify step sets, and written only under GitHub Actions (S152). A local `pnpm verify`, and so `scripts/audit.sh story`, runs every task every time.

**Impact:** Before S168, checking any change, however small, ran nearly every build and test in the repository, mostly one after another, locally and in pull requests. S168 impact: each area of the code builds and tests on its own and in parallel, and a change runs only the checks for the areas it actually touches (and the areas that use them), so small changes are checked in a fraction of the time, while every merge to `stage` still runs everything.
