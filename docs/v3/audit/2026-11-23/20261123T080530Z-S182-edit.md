**Impact:** Before S182, a fan who didn't follow why a play went the way it did had to look it up. S182 impact: for a game's key plays and its eventful half-innings, BT has a short, fact-checked explanation in plain words of what happened and the rule behind it, written as the game goes.

**Acceptance criteria** (checks `scripts/verify-S182.sh` performs)

1. **Rules decide which plays and what happened.** One domain function, `explainablePlays(game, inning)`, picks an inning's key plays: those whose win-probability swing is among the game's top 10 so far, plus every play whose event the glossary marks as rules-heavy (at least: an error leading to an unearned run, a fielder's choice, a sacrifice fly, an infield fly, a balk, catcher's interference, obstruction, an automatic runner in extra innings, an ABS challenge and its result). A fixed glossary, `RULES_GLOSSARY` in `packages/domain`, keyed by a BT play kind: MLB's event type where one exists, otherwise a kind one function, `playKind(play)`, derives from the play's data (a steal of home from a stolen base by the runner on third; an inside-the-park home run from a home run whose hit data shows the ball stayed in the park; a position player pitching from the pitcher's primary position; an immaculate inning from its nine pitches), table-tested, holds each rule's plain-words explanation and goes into the prompt as facts. Table tests on fixtures and invented plays.
2. **Rare plays use templates, no model.** Events the glossary marks rare (at least: a triple play, a steal of home, an inside-the-park home run, a position player pitching) get a fixed template filled from the play's data, never a model call (test: zero stub calls).
3. **Eventful half-innings get an inning explainer.** One function, `eventfulHalfInning(game, inning, half)`, is true for a half-inning with a run, an error or a glossary event; each such half-inning gets a short explanation of how it unfolded; a quiet one gets none and costs nothing (test: a quiet inning makes zero explainer calls to the stub).
4. **Through the full loop, live.** Each explainer comes from S176's `writeVerified` with the explainer job's instructions and only that play's (or half-inning's) facts and glossary entries (full loop, up to two revisions; a failed one is not published), run by S181's inning job when the inning ends, without a batch.
5. **Served.** `GET /api/v1/games/:gamePk/explainers` answers `AiOutputResponse<GameExplainers>` (`plays`: each with its at-bat index and text; `halfInnings`: each with its inning, half and text), to whom `canReadAiOutput` allows, `null` for a game with none yet; in `ApiRoutes` (law L4) and the OpenAPI spec (additive, `pnpm api:breaking` exits 0, `web/src/api/generated/` regenerated); cached as live or finished data by `cacheLifetimeMs` (ADR-021). Route tests: a live game mid-way, a final game, a game with none.
