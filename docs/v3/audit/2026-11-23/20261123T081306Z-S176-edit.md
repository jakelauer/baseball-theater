**Gap:** FEATURES' AI game companion and Inning / game insight pipeline promise text BT writes about games (recaps, a postgame package, a day digest, inning notes, explainers, chat), and ADR-007 left open the providers, grounding rules, caching, cost caps and free versus patron outputs. **Impact:** Before S176, BT had no way to have an AI write anything. **Acceptance criteria** (checks `scripts/verify-S176.sh` performs)

1. **The AI port.** `packages/ports` gains `AiModelClient`: `generate(request)` takes a model id, fixed instructions (marked cacheable, so a provider's prompt caching can bill re-reads at its cache price), the input, a JSON schema the output must match, a maximum output length and a low reasoning effort, and answers the parsed output plus its usage (input, cached input, cache-write and output tokens), model and provider. Nothing in `packages/domain` or `packages/ports` imports a provider SDK or names a provider's URL (grep).
2. **Four provider adapters and a stub.** `functions/src/adapters/ai/` holds an adapter each for Anthropic, OpenAI, Google (Gemini) and Cloudflare Workers AI, each over plain `fetch` with its key from the Worker's secrets (no new dependency; the root `package.json` still gains the export script of AC 8), each tested against a response recorded once into `fixtures/ai/` (`BT_USE_LIVE_AI=1`, keys never committed; a test greps `fixtures/ai/` for key-shaped strings): success, a refusal or error status, output that fails the schema (one retry, then an error), and usage mapped to the port's fields. A stub adapter answers scripted responses for tests and local development. Local development and CI use the stub; a Worker with no writer model configured makes no call and every AI feature shows nothing.
3. **Which model does what is configuration.** Each job (recap, package, digest, inning notes, explainers, chat) names a writer model and a checker model through one config read (`wrangler.jsonc` vars or secrets), never in code. When the writer and checker of a job come from the same provider, the Worker still runs and logs a warning naming the job, since the owner asked for a different provider where possible. S177's result sets the values.
4. **What a call costs.** `packages/domain` exports a dated price table (`AI_PRICES`, per model: input, cached input, cache write, output, batch input and output; seeded from the research's addendum A, prices of 2026-11-22) and one function, `aiCallCost(usage, price)`, in US dollars. Table tests: a cached read billed at the cache price, a batch call at the batch price, a model missing from the table refused (the call is not made), thinking tokens billed as output.
5. **The $100 cap, an 80% alert and a hard stop.** `AI_MONTHLY_CAP_USD` is 100 and `AI_ALERT_SHARE` is 0.8, named constants quoting the owner (*"$100/month"*, the option reading *"More room for chat use; alert at 80%."*). `packages/ports` gains `AiSpendRepository` (Postgres adapter with one migration, memory adapter; one contract test runs both on PGlite): before each call the meter reserves the call's most it can cost (its input priced, plus its maximum output priced), and after it settles the actual cost; a reservation is refused when spent plus reserved plus it would pass the cap, so concurrent calls can't jointly cross it (contract test: two reservations racing for the last dollars, one refused). A refused reservation refuses that one call; it is not a state of the month. An immediate call's reservation left unsettled for 15 minutes (a crash between call and settle) counts at its full amount; a batch call's reservation (S178) stays reserved until its results are fetched and settled, or the batch is cancelled or expires, and the 15-minute rule doesn't apply to it (test). The month is the UTC calendar month (`2026-11-30T23:59:59Z` and `2026-12-01T00:00:00Z` fall in different months; test). One domain function, `aiBudgetState(spent, reserved, cap)`, answers from those numbers alone: `stopped` when spent plus reserved is at or past the cap, `alert` when at or past 80% of it, otherwise `open` (table test at each boundary). Crossing 80% sends the owner one email that month through the existing `Mailer` port to the address in the secret `AI_ALERT_EMAIL`, and reaching `stopped` sends one more; a stored flag keeps a second crossing in the same month from sending again (test). Once the cap is reached, AI features stop and show nothing (owner: *"$100/month"*, AI features showing nothing at the cap): the meter refuses every reservation, so no call goes out. S176 has no AI route, so this is tested through `writeVerified` (a stopped month makes no stub call and publishes nothing) and AC 9's helper; S178's first route tests it end to end.
6. **The verification loop** (owner, 2026-11-22: *"I imagine I could have the recap system write a recap AND evaluate the output with a fact checker agent until it's verified"*). One service function, `writeVerified(job, facts, options)` in `functions/src/services/`, is the only way any AI text feature gets text:
    1. The writer model drafts, given only the job's facts (a JSON fact pack BT computed) and its fixed instructions.
    2. The **rules checker** runs first: one pure function in `packages/domain`, `checkFactsByRule(output, facts)`, pulls every number (digits and spelled-out numbers up to twenty), player name, team, inning (`7th`, `seventh`, `top of the 7th`) and count (`3-2`) from the draft and answers each one the fact pack doesn't hold, as a specific error (`"Says 4 RBI; the facts give 3 for Judge"`). Table tests over invented drafts: a wrong score, a player not in the facts, the wrong team, a misnumbered inning, a count that never happened, and a clean draft with no errors.
    3. The **fact-checker agent** then checks the claims the rules can't (`the go-ahead hit`, `his best start of the year`) against the same fact pack, through the port with the job's checker model, and answers each unsupported claim as a specific error, in a JSON schema.
    4. If either found errors, those errors go back to the writer, which revises.
    5. At most `AI_MAX_REVISIONS` (2, a named constant) revisions follow the first draft. A draft both checks pass is **verified**; if the last revision still fails, the item is **failed** and nothing is published for it (see **Waiting on the owner**, question 2, for whether a plain data-built fallback should show instead).
    6. Every round is logged (AC 8).

    `options` let a job skip the agent check, lower the revision cap, supply a first draft it got some other way (`firstDraft`: S178's batched draft, which the loop then checks as round one), and send its rounds to its own log instead of AC 8's (`logSink`: chat's, S184): chat uses the **lighter version** (rules checker only, at most one revision, and a failed answer is replaced by "I don't have that", S184); every other text feature uses the full loop. Each model call in the loop goes through the meter (AC 5); a refusal mid-loop ends the item as **budget stopped**, publishing nothing. Tests with the stub: a draft verified on the first try (one writer call, one checker call); one fixed on the first revision (the errors passed to the writer are the checks' own words); one failing after two revisions (three drafts, nothing published); the agent skipped for chat's options.
7. **Cached once per version.** An item's key is the job, its subject (a `gamePk`, a game and inning, or a date), the source data's version, the prompt version and the two models. For a postgame or daily job the source version is ADR-022's version of what the facts were built from; for a live job (inning notes, explainers) it is the fact pack's hash, since the game's live version moves on every pitch. A key whose item is `verified`, or `failed` after the revision cap, is never sent to a model again (test counts stub calls: zero on the second request); new source data is a new key. An item that ended `budget_stopped`, or `retryable` after a transport error (a provider's 5xx or 529, a timeout, an outage), is tried again on a later tick, a `retryable` one at most `AI_MAX_ATTEMPTS` (3, a named constant) times before it is `failed`. A budget refusal never counts toward `AI_MAX_ATTEMPTS`: a `budget_stopped` item is tried again only on a tick where its reservation would now fit (spent plus reserved plus its most cost at or under the cap), which in practice is after the UTC month changes or reserved dollars are released; until then the tick skips it without a call (tests for each, including a $1 reservation refused at $99.40 spent, which stays `budget_stopped`, not `failed`, across many ticks). Reads go through one repository; the store is Postgres (ADR-018). **Chat is exempt from this key:** each question is answered once for the fan who asked and never served to another, so S184 owns chat's storage and keys nothing here.
8. **Everything is logged, and the owner's corrections too.** Each item keeps its key, its fact pack (and its hash), its final verdict (`verified`, `failed`, `budget_stopped`, `retryable`), its published text if any, and its total cost; each round keeps its draft, the rules checker's errors, the agent's errors and that round's tokens and cost. `PUT /api/v1/admin/ai-outputs/:outputId/correction` (a signed-in session with role `admin` only: 403 for anyone else, 404 for an unknown id) stores the owner's corrected text and a note beside the output, and `GET /api/v1/admin/ai-outputs` lists items by job and date range for review; both are in `ApiRoutes` (law L4) and the OpenAPI spec (additive, `pnpm api:breaking` exits 0, `web/src/api/generated/` regenerated). `pnpm ai:export-training --from <day> --to <day>` writes JSON lines (facts, prompt version, models, every round, verdict, published text, correction) for a future fine-tune or evaluation. The classification manifest labels these repositories `none`, with why (game data and the owner's own corrections, no fan's data; no user id stored), so law L3 passes. Chat's questions and answers never enter this log: a fan's free text tied to an account is personal data, so S184 keeps chat's rounds in its own `personal` store (ADR-028: exported, deleted with the account, law L3), through `writeVerified`'s `logSink`.
9. **One answer shape.** `packages/domain` exports `AiOutputResponse<T>` (`{ output: T | null }`) and one helper, `toAiOutputResponse(item)`, which every AI route (S178 onward) uses: `output` is `null` when nothing is published for the item (not written yet, failed, budget stopped, retryable, or no model configured), so a client never sees why; a unit test for each case.
