**Acceptance criteria** (checks `scripts/verify-S178.sh` performs)

1. **BT computes the facts.** `packages/domain` exports `GamePackage` (`gamePk`, `version`, `finalAt`, `keyMoments`, `standoutLines`, `accomplishments`, `videoOrder`, `narrative`) and one pure function, `buildGamePackageFacts(game)`, reusing S177's package fact pack: `keyMoments` from `topPlaysByWinProbabilityAdded`, ordered as they happened; `standoutLines` from one function choosing the game's standout batting and pitching lines from the box (reusing `pitcherLine` / `batterLine`); `accomplishments` from one rules function over the game (at least: a cycle, a no-hitter or perfect game, a complete-game shutout, a multi-home-run game, 10 or more strikeouts by a pitcher, a walk-off), each with the plays it rests on; `videoOrder` from `rankHighlightsByImpact`. Tests on fixtures and on invented games for each accomplishment, and a game with none.
2. **The model writes only the headline and the beats.** `narrative` (`headline` and 2–4 `beats`) comes from S176's `writeVerified` with the package job's instructions and the full loop (rules checker, then the fact-checker agent, up to three revisions, then one escalation pass and, if that fails too, the report email to the owner; S176); every other field is BT's own computation and is never sent back through a model. When the loop publishes nothing (failed, budget stopped, no model configured), `narrative` is `null` and the rest of the package is still stored and served.
3. **Triggered once per final, and survives a crash.** One domain function, `gameFinalTransition(previous, next)`, says when an ingest tick moves a game to final (and not for postponed, suspended or cancelled games, which are never final; table test over MLB's status codes from `fixtures/raw/gamestatus.json`). Ingest then enqueues one job keyed `gamePk:final:<source version>` in a Postgres job table (a second enqueue of the same key is a no-op; test), and a scheduled tick (the existing cron, `wrangler.jsonc`) runs queued jobs. A job's state (`queued`, `submitted` with its provider batch id, `done`, `failed`) is stored, so a tick that stops between submitting and storing the result resumes the submitted batch on the next tick instead of paying for it again (test with the stub: a crash after submit, then a tick that finishes it with no second writer call).
4. **Postgame's first draft is batched, at half price.** `AiModelClient` gains a batch submission and a result lookup; the Anthropic, OpenAI and Google adapters implement them (tests on recorded responses), and the Workers AI adapter, which has no batch, falls back to an immediate call. Only the first draft of each package is batched: the job state holds the batch id, and the tick that collects the result stores the draft in the job state and then runs `writeVerified` with it as `firstDraft` (S176), so the fact check and any revisions run as immediate calls and the loop never suspends between batch rounds. A crash after collecting re-runs the checks and revisions from the stored draft with no second batched writer call (test). S176's meter prices the batched call at the batch rate.
5. **Late changes rebuild it.** Media or data that arrive after the final (the post-game trail) change the game's source version, and any tick that stores a newer version of a final game enqueues `gamePk:final:<new version>` (test: a late media update to a final game enqueues exactly one job with the new version; an unchanged poll enqueues none); the next tick builds a new package for the new version, which replaces the served one (ADR-011: replace-on-final, versioned), and the old one stays in S176's log. A newer version is never replaced by an older one (ADR-022; test).
6. **Served.** `GET /api/v1/games/:gamePk/package` answers `AiOutputResponse<GamePackage>`: `output` is `null` for a game with no package yet (not final, or not built); `narrative` is served only to whom `canReadAiOutput` allows and is `null` for anyone else; it is in `ApiRoutes` (law L4) and the OpenAPI spec (additive, `pnpm api:breaking` exits 0, `web/src/api/generated/` regenerated), never in the shared edge cache: because `canReadAiOutput` makes the answer depend on the session, it is sent `Cache-Control: private, no-store` (ADR-021's shared freshness doesn't apply to a gated answer; test: a free and a patron session fetch the same URL in turn through the Worker's cache and each gets its own answer, the free one `output: null` and the patron one the text). Route tests: a final game with a package, one whose narrative failed, a live game (`output: null`), an unknown game (404).
