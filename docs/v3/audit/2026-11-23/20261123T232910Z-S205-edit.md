**Gap:** BT's box score (`GameBoxscore`, `packages/domain/src/types.ts`) holds each team's batters and the game's info lines only; the projection (`mapBoxscore`, `functions/src/mappers/live.ts`) drops what MLB's live feed already sends and the upstream types already parse (`LiveBoxscoreTeam` in `packages/mlb-api/src/live.ts`): each team's pitchers and their lines (`pitchers`, `players[…].stats.pitching`), each team's detail groups (`info`: `BATTING` with 2B, HR, RBI and the like, `BASERUNNING` with SB, `FIELDING`; recorded in `fixtures/raw/live-823823.json`), each team's notes (`note`), and the game's `pitchingNotes`. The owner said (2026-11-23): *"Right now we're missing the entire pitching part of the box score and then we're also missing all of the details. Like, you should just look at one of the baseball, a few of the baseball theater box scores from live site, because you see there's like all of the extra base hits and all of the RBIs and stolen bases."*; *"There's fielding stuff, intentional walks. There's all this stuff. And we're missing that stuff."* FEATURES' Box score row already names *"the batting / pitching tables, and the game's details"*.

**Impact:** Before S205, BT didn't keep a game's pitching lines or its box score details (extra-base hits, RBIs, stolen bases, fielding), so no screen could show them. S205 impact: BT stores and serves them for games it ingests or refreshes from then on (an older game gains them the next time it is read), so the Box room can show the whole box score.

1. **The domain shape.** `GameBoxscore` gains, per team, an optional `pitching?: BoxscorePitcher[]` in the order MLB lists them (`pitchers`), each with the person's id and name, and this game's IP, H, R, ER, BB, K, HR, pitches and strikes, and season ERA after the game, as MLB formats them; `details?: BoxscoreDetailGroup[]` (each a `title` such as `BATTING` and its `label: value` lines, in MLB's order); and `notes?: BoxscoreInfoLine[]`; and the game gains `pitchingNotes?: string[]`. 2. **The projection.** `mapBoxscore` fills them from `LiveBoxscore`; a line or group with no label or value is left out, as the info lines are today. Tests in `functions/src/services/projection.test.ts` (or a colocated mapper test) on `fixtures/raw/live-823823.json`: the away team's first pitcher's name and line equal the recording's, the `BATTING`, `BASERUNNING` and `FIELDING` groups with their first line each, and a fixture with `pitchingNotes` (`live-209865.json`) carries them.
3. **A new stored shape is not a new game state.** Refresh-on-read (`needsRefresh`, `functions/src/services/ingest.ts`) re-fetches a finished game on read once its cache lifetime (capped at 48 hours) has passed, so every older game read after this ships is projected again with the new fields; `stampVersion` (`packages/domain/src/versioning.ts`) would see that as a change, bump its `version`, set `lastChangedAt` to now and restart ADR-021's ladder (about seven extra MLB fetches per game read, and its edge lifetime dropping to minutes). So a re-projection whose only difference from the stored game is fields BT's own projection newly adds (these, and no upstream value) keeps the stored `lastChangedAt`; its `version` still moves on so clients take the new shape. Unit test: a stored game without the new fields, refreshed to an otherwise identical snapshot, keeps its `lastChangedAt` and its next `needsRefresh` answer; an upstream change still resets it.
4. **The bundled fixtures carry them.** `fixtures/game-823823.json` and `fixtures/game-823823-live.json` (the local and CI data the web reads) are rebuilt with their box score passed through the new `mapBoxscore` from `fixtures/raw/`, and a test asserts the bundled fixture's `boxscore.teams.away.pitching[0]` equals the one mapped from the raw recording, so S207 can build against them.
