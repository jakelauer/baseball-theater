Issue: #282

**Body**

<!-- bt-body:begin -->
**Gap:** A game's score is stored in three places: inside its date's scoreboard day (`schedule_days`, written by the cron's schedule refresh, `refreshTodaysWindow`, and by the day read's refresh, `ingestScheduleDay`, both in `functions/src/services/ingest.ts`), inside its game snapshot (`games`) and inside its projection (`game_projections`), the last two written by the game's ingest (`storeGame`). The day's copy comes from MLB's schedule, which MLB caches apart from the live game feed, so a schedule fetched after a game update can hold an older score, and nothing decides which copy is right. The owner wants one stored copy (owner, 2026-11-17: *"seems like we should store game linescores in one table that is referenced wherever it is needed, and it contains whatever data is shared between those two sources. Then we can check the newness of the data when we get it from either source and update that table if the data is newer than the stored data."*). MLB's schedule carries no time of its own per game, so the two sources can't be compared by age; told so, and offered a switch that hands the row to the live feed while the game is in its live window and to the schedule otherwise, the owner chose that (2026-11-17: *"Ok, I like your idea of a sort of "railroad switch" based on game state."*), as one point that switches sources (*"a single point which switches sources, as opposed to two separate places independently checking"*). S149's live scoreboard builds on it.

**Impact:** Before S150, the scoreboard could briefly show a score a run behind the game page, or step a score back, because it kept its own copy from a slower MLB source. S150 impact: every page reads a game's score from one stored place, and while a game is live only the live feed changes it.

**Source:** Feature: Live marker

**Baseline:** Each game's status, linescore and on-field moment are stored once, in `game_states` (`functions/src/adapters/postgres/migrations/0001_game_states.sql`, filled from the stored days, the copy changed last for a game on two days, and from the stored snapshot for a game no day lists), as a `GameState` (`packages/domain/src/game-state.ts`, built by `gameStateFromSummary` from a scoreboard row and `gameStateFromGame` from a game) beside the source that wrote it, the newest feed time it accepted, its official date and first pitch, behind `GameStateRepository` (Postgres and in-memory adapters, contract case (k)). `switchGameState` (`functions/src/services/game-state.ts`) is its only writer: `storeSchedule` hands it every game of every schedule fetch and `storeGame` every feed poll, unchanged ones included, and it asks `gameStateSource` once, so the feed owns a game's row while it is in its live window and the schedule before and after it; a feed state older than the row's accepted feed time is skipped, and so is another day's postponed or suspended listing of the game (`isOtherDaysListing`). The port's game fetch returns a `FetchedGame` (`{ game, feedTime? }`, the feed's `metaData.timeStamp` as ISO), never stored on the game or pushed by the hub. `schedule_days` stores a day without its games' states (`StoredScheduleDay`, a postponed or suspended listing keeping its own `listingStatus`, served on that day once its game has moved to another, so a postponed game's original day shows Postponed and only its makeup day its score) plus `served_base`; `readScheduleDay` and the day read join the rows into the served day (`joinScheduleDay`: `windowMode` from the joined games, a version that only rises), and `getOrRefreshGame`, the game hub's first send and the ingest's publish serve `servedGame`. The backfill, `ingestScheduleDay`, `refreshTodaysWindow` and the dev overlay read the joined day; the baseball-data copy has a `game_states` rule and raises `served_base` for a day it replaces. `GET /api/v1/schedule` and the game route answer in the same shapes (OpenAPI unchanged).

**Depends on:** nothing. Issues #71 (the live window measured from midnight UTC instead of first pitch) and #72 (postponed games kept in the window forever) are fixed first, by their own pull request; AC 1, AC 3 and AC 4 assume the fixed window and the game's `startTime`.

Two named functions in `packages/domain` build it, one from a scoreboard row (`ScheduleGameSummary`, what the schedule fetch returns) and one from a game (`GameSnapshot`, what the feed fetch returns: runners and batter and pitcher from its `live`, their names from its current at-bat, the count from its linescore), so it works the same from MLB, recorded fixtures and the dev seed, which hand over already-mapped games. Unit tests: the recorded feed of a game and its schedule row at the same moment give the same status, linescore and runners, using an in-progress moment for the runners (`scheduleMomentsAt().live`, `functions/src/services/live-fixture.ts`, a schedule row built from the feed recording at `LIVE_FIXTURE_TIMECODE`, since no MLB schedule was recorded mid-game; it checks the row builder, not MLB's schedule) and the final pair (`mapScheduleGame` on `fixtures/raw/schedule-2026-09-05.json` against the final feed) for the real schedule mapper; where batter or pitcher differ (the schedule reads them from the linescore, the feed from the current play, which part ways between batters), the test says so.
2. **The feed's own time, never stored on the game.** The live feed's time (MLB's `metaData.timeStamp`, `YYYYMMDD_HHMMSS` in UTC, e.g. `20260905_233435`, parsed today and dropped by `mapLiveFeed`) is converted to an ISO instant and returned beside the game, not on it: the port's game fetch (`fetchGame`, `fetchGameFeed`, `packages/ports/src/mlb.ts`) returns a `FetchedGame` (a type in `packages/domain`: `{ game, feedTime? }`, the unversioned game beside its optional feed time, not merged into it), which no API response type names, so the recorder and the dev seed, which write fetched games to files, write the game alone. `storeGame` hands the feed time to `switchGameState` and stamps and stores the game without it, so `GameSnapshot`, `GameSnapshotResponse`, the OpenAPI spec and the hub's pushes are unchanged (`pnpm api:spec` leaves `openapi/bt-api.v1.json` unchanged, grep). A game with no feed time (fixtures, the dev seed, older recordings) is never skipped for its time and never moves the row's accepted time. Unit tests: the HTTP adapter's fetched game carries the feed's time as ISO; the stored game document and the hub's push carry no `feedTime`.
3. **One table.** A `game_states` table (`functions/src/adapters/postgres/schema.ts`, with a generated migration under `functions/src/adapters/postgres/migrations/`) holds one row per game, keyed by `game_pk`: `version`, the source that wrote it (`feed` or `schedule`), the newest feed time it has accepted (null until the feed writes one), the game's official date and first pitch (`startTime`: the schedule row's, or the game's, which issue #71 adds to `GameSnapshot` from the feed's `gameData.datetime.dateTime`; a write without a start never clears a stored one, since snapshots stored before #71 have none), which the switch needs, and the `GameState` document. A game listed on two days (a suspended game, resumed later) has one row, which both days read. A `GameStateRepository` port (`packages/ports/src/repositories.ts`) has Postgres and in-memory adapters, both run by the repository contract tests (`functions/src/adapters/repository-contract.ts`); its write takes a row only when its `version` is newer, or its version is the same and its feed time newer (moving the time, and marking the row `feed`). The data classification manifest (`functions/src/services/data-classification.ts`) lists the table. The baseball-data copy (`COPY_RULES`, `functions/src/services/baseball-copy.ts`) has a rule for it: newer by `lastChangedAt`, except that a target row written by the feed whose game is in its live window is the target's own (as `changedLater`'s `ingesting` case treats a live game today), and the target's accepted feed time is never copied over, nor is a stored first pitch cleared by a row without one. The copy never copies `schedule_days.served_base` (AC 6) either, which is a counter of the target's own; when it adopts a day it raises the target's `served_base` so that day's served version doesn't fall. A copy test covers all three, including a production day with a lower `served_base` and one game fewer. The migration fills the table from the stored days (`schedule_days`) and, for a game no stored day lists, from its stored snapshot (`games`), taking for a game listed on several days the copy changed last (`SELECT DISTINCT ON (game_pk) … ORDER BY game_pk, lastChangedAt DESC`), so no stored game loses its score (a migration test on a PGlite database holding one game on two days and one game in `games` only). `README.md`'s table lists and its Neon `pg_dump` line, and the backfill report's `GAME_TABLES` (`functions/src/services/backfill-report.ts`), name `game_states`.
4. **The switch: one point picks the source.** One pure function in `packages/domain`, `gameStateSource(row, incoming, now)`, returns which source may write a game's row at that moment. It asks the live window (`isGameInActiveWindow`, measured from first pitch once issue #71 is fixed, and treating a postponed game as out of it once issue #72 is) with the row's stored status, first pitch and official date, or the incoming state's when there is no row yet, and the clock: `feed` while the game is in its window, including a game in progress or delayed past its expected end and a final game's trail; `schedule` before it and after it, and for a postponed game whatever the clock. Reading the stored status is safe: inside the window only the feed writes it, and outside it a schedule write that finds the game started (`I`) rightly hands the row to the feed. A game with no row takes the first state from either source. One function in `functions/src/services/game-state.ts`, `switchGameState`, is the only code that writes `game_states` (grep: the repository's write is called nowhere else, the baseball-data copy of AC 3 being the one named exception): the schedule refresh and the game's ingest each hand it the state they fetched with their source and check nothing themselves; it asks `gameStateSource` once and writes the state only if it came from that source, so the decision lives in one place. A feed state older than the row's accepted feed time is skipped. A schedule state is skipped as another day's listing of the game when all three hold: its own status is postponed or suspended; its official date isn't the row's; and either the row's status isn't postponed or suspended, or its official date is earlier than the row's. So a postponed or suspended game's original day never changes the row once its makeup or resumption day holds it, a makeup or resumption day's listing still takes over a row its original day wrote, a game postponed again on its makeup day stays there, and a game MLB moves to an earlier or later day with no postponement takes its new day's listing (AC 5, AC 6). The one case this doesn't settle, MLB keeping the original official date on both listings, is #439. Every write is stamped with `stampVersion`, so an unchanged state isn't a new version, and the repository's write (AC 3) still moves the accepted feed time on an unchanged state. Unit tests: `gameStateSource` before, in and after the window, with no row, and for a game postponed at 9am before a 7pm start; in the window, a schedule a run behind arriving after a feed write leaves the feed's score; a final game in its trail keeps the feed's final when a schedule a run behind arrives; an older feed time is skipped; an unchanged poll moves the accepted time, so a stale copy between the two polls is then skipped; after the window, a schedule state is written and a feed state isn't; another day's listing: a game moved to an earlier day takes that day's listing and its feed then writes it, a game moved to a later day with no postponement takes that day's listing, a game postponed again on its makeup day keeps the row against its first day's postponed listing, and a suspended game with its own resumption date keeps the row against its original day's listing, none of them flipping on repeated refreshes.
5. **Writers hand over every poll.** `storeSchedule` hands each game's state to `switchGameState` before it writes the day, and before any early return for an unchanged day, then stores the rest of the day: which games, start times, probable pitchers, decisions, records. The stored day's type (`StoredScheduleDay`) has no status, linescore or live moment, with one exception: a listing whose own status is postponed or suspended may keep that status in a separately named field (not `status`), so AC 6 can serve it once the game's current official date is another day. The fetched and served day (`ScheduleDay`) keeps its shape, so the MLB port, the fixtures and `fixtures/schedule-823823-moments.json` are unchanged. `storeGame` hands the feed's state to `switchGameState` on every call, before its early return for an unchanged snapshot, so every feed path (`ingestGame`, `tickIngest`, `getOrRefreshGame`, `ingestScheduleDay`'s loop) reaches the switch, and a stop between two writes, or a row backfilled from the schedule while the game is live, is mended by the next poll. Unit tests: an unchanged snapshot still reaches the switch, through `tickIngest`; an unchanged stored day still hands over a postponement; a stop after the snapshot write is mended by the next poll.
6. **Readers use it.** One named function in `packages/domain` (ADR-025), `joinScheduleDay`, joins a stored day with its games' rows, by the gamePks the day lists, into the served `ScheduleDay`; a listing whose date isn't its row's official date and which kept its own postponed or suspended status (AC 5) is served with that status instead of the row's; a game with no row yet is served with the status and linescore it was stored with on the snapshot, or as scheduled with no score if BT has neither, except a listing that kept its own postponed or suspended status, which is served with that status. A read-only function `readScheduleDay(date)` in `functions/src/services/` returns that join without refreshing from MLB, and the day read (`getOrRefreshSchedule`) refreshes, as today, then returns the same join, so `GET /api/v1/schedule?date=` answers in the same shape as before (`ScheduleDayResponse`; `pnpm api:spec` leaves `openapi/bt-api.v1.json` unchanged, grep). The served day's `windowMode` is computed at read time from the joined games with `scheduleWindowMode`, not taken from the stored day (whose games no longer carry their status), and `needsRefresh` judges that joined `windowMode` with the stored day's own `lastChangedAt`, its schedule data; a game's score is kept current by its writers, not by the day's refresh. Unit test: a day stored `active` whose joined games are all final past their trails is served `cache` and goes stale on the cache ladder. The code that read a game's status from the stored day reads the joined day: the backfill (`isScheduleDaySettled`, `isFinalSummary`, `functions/src/services/backfill.ts`), `ingestScheduleDay`'s loop and the local dev overlay (`storeOverlay`, `functions/src/adapters/overlay-mlb.ts`). **A day's version that only rises:** the served day's `version` is the stored day's version plus a `served_base` column of `schedule_days` (outside its document, so not hashed) plus the state versions of the games it lists; when a refresh drops a game from a day, `storeSchedule` adds that game's state version to `served_base` in the same statement that writes the day, so the sum never falls, even if the Worker stops mid-refresh (a test stops it between the day's read and write). Its `lastChangedAt` is the latest of the day's and its games'. **The served game:** one named function in `functions/src/services/` builds it from the snapshot and the row (status and linescore from the row, or from the snapshot when there is none), keeping the snapshot's `version` and taking the later `lastChangedAt` of the two, so its cache headers (ADR-021, which follow `lastChangedAt`) follow a state change, and the game hub's pushes and the HTTP read compare as before. `getOrRefreshGame`, the game hub's first send (`functions/src/game-hub-object.ts`) and the ingest object's publish (`functions/src/services/game-ingest.ts`) all serve it. Unit tests: a day read shows a feed score newer than the day's schedule fetch; a state change raises the day's version; a game dropped from a day doesn't lower it; a game with no row is served from its snapshot; the day read and the game read show the same score; a game on two days shows the same state on both, unless one listing kept its own postponed or suspended status; a game listed postponed (`D`) on day A and scheduled, then final, on its makeup day B, with A and B refreshed in both orders: B serves the row's state, A serves Postponed, and once the row's official date is B a schedule write of day A leaves the row unchanged (same version and document); the HTTP game read's version equals the game hub's first send, and the game's next change is pushed one version higher, so the client's stream (`web/src/api/live-stream.ts`, unchanged) applies it.

**Notes:**

- **Why the window, not the newer copy.** MLB's schedule has no time per game, so a schedule copy's age is unknown. Ordering copies by game progress (inning, outs, count) would mostly work but would lose official scoring changes, which correct a game without moving it on. In the window, the live feed is polled every few seconds and is the fresher source; out of it, both have settled.
- **One switch, not two checks** (owner, 2026-11-17: *"The way that should work is a single point which switches sources, as opposed to two separate places independently checking to see if they should update the DB"*). Neither writer knows the rule; changing it means changing `gameStateSource` alone.
- **ARCHITECTURE's "Response aliases" example** (`ScheduleDayResponse = ScheduleDay` as a passthrough) stays true: the served day keeps its shape, and the stored type is the new one.
- **A row with no ingest running.** If a game's ingest object stops inside its window, the cron restarts it within a minute (ADR-020); its row waits for the feed in the meantime rather than taking the schedule's copy.
- **A postponed game's two days** (owner, 2026-11-23, asked "When a postponed game is made up on a later day, what should the original day show?": chose "Original day: Postponed (Recommended)", the option reading "each day's listing keeps its own postponed or suspended status, and only the makeup day shows the live score and final. Needs a small AC change to S150: the stored day may keep a status for a game whose listing date isn't the game's current date."). AC 4 keeps the original day's listing off the row, AC 5 lets the stored day keep that listing's status, and AC 6 serves it. If MLB's data for a resumed suspended game keeps the original day's `officialDate`, so the row's official date can't tell the original day from the resumption, stop and ask rather than choose a rule (pre-PR check of this edit: no recorded fixture holds a resumed game).
- **The games and projections tables** keep the feed's copy because ingest stamps the whole snapshot's version and diffs it (`stampVersion`); only the live feed writes them, so they can't disagree with themselves. Readers take the shared fields from `game_states`.
