**Impact:** Before S224, a story that only touched its own package's build settings, or added one command to the repository's list, held up every other story in a run until it merged, and a run could only count as clean by passing a fixed numeric bar that thorough reviews made harder to pass, so backlog runs stayed at two items at a time. After S224, such stories run beside the others, and only changes to shared machinery still run alone; and a fresh agent looks at what actually happened in the run and judges whether running that many side by side caused trouble, while a broken staging build, a reverted change or a defect that got through still marks the run not clean, so runs can safely go back to three at a time.

Unit tests cover both.
3. **One added root script is a hot file, checked at commit time.** A claim naming the root `package.json` is admitted as a hot file, not a barrier. At commit time `claims.ts touched` compares the root `package.json` in the worktree it runs in (its working directory, committed and uncommitted changes alike, since a worker runs the check before its one commit; never the `--root` checkout, which only holds `.run/`) with the same file at `--base <ref>`, the base the step gives `story_own_changed_files` (`origin/stage` when omitted, so the agents' commands keep working; the branch below for a stacked item, so a script the branch below added isn't counted as this item's second): when the change is exactly one new entry under `"scripts"` and nothing else, it passes; any other change to the root `package.json` (an existing script changed or removed, a second script added, a dependency, `engines`, `packageManager`, `pnpm` settings or any other key, or a reformat) is reported as a barrier path touched under a claim that isn't a barrier, as `touched` reports one today, so the worker stops with `needs-lead`. Run-backlog's step 3 check passes `--base <base>` with the base it already names. _A judged clean run (T6, S227's ACs 1–7)_

8. **A judge with one question.** A new agent definition, `.claude/agents/run-judge.md`, meets law L18 (frontmatter with `name: run-judge` and a `description`), is read-only (no edit, write or shell tools in its `tools:` line) and runs on a light model, as `review-tracker` does. It is asked one question, in its definition's words: did running this many items side by side cause problems in this run, and would running one more have? It answers `clean` or `not-clean` with a reason of at most a few sentences that cites the numbers it relied on. It is never the coordinator and is started fresh for each run. Grader: reads the file's frontmatter and body.
9. **The numbers are its evidence, not the verdict.** The judge's input is the run's own record, built by one function in `runs.ts` (ADR-025) from the journal: `C` and the peak in flight, items started and merged, merge conflicts, refused claims (`claim-refused`), duplicates, turn-cap hits, parks and set-asides, the drain time, pre-PR findings per pull request (with any unknown counts named as unknown), and any tripwire (AC 10). Unit tests pin the input for a fixed journal.
10. **Tripwires override the judge.** Three events make a run not clean whatever the judge says: `stage` went red during the run (a CI run on `stage` failed), a pull request the run merged was reverted, or a defect in something the run merged was found on staging or in production (an escape). The coordinator logs each as `run event tripwire --kind red-stage|revert|escape --ref <run, pull request or issue>` (a new run-level kind in `RUN_KINDS`), and `summarizeRun` reads them. A revert or escape is often found after its run's entry is written, when it can no longer change that run's summary: the coordinator then logs it in the current run's journal with `--run <the earlier run's ID>`, the current run's entry records it, and the run records built in `runs.ts` for `concurrencyFromRuns` (`runRecordOf`) mark the earlier run not clean, so a later run never rises to 3 on it (`concurrencyFromRuns` itself unchanged, AC 12). Unit tests cover each tripwire turning a judged-clean run not clean, and an escape logged during a later run turning the earlier run's record not clean.
11. **Clean is the judge's verdict, recorded.** The coordinator logs the verdict as `run event clean-verdict --verdict clean|not-clean --reason "<text>"` before `audit.sh run`. `summarizeRun`'s clean becomes: counted (unchanged: at least `MIN_ITEMS` started, the peak reached `C`, one merge, not abandoned) and no tripwire and a `clean` verdict; a run with no verdict is not clean. The fixed findings bar (`underBar` and the `bars` it reads) is removed, and conflicts, duplicates and the drain become evidence for the judge, not conditions. The run entry records the verdict, its reason and the evidence beside the existing figures. Unit tests cover: a judged-clean counted run is clean; judged not-clean is not; no verdict is not; an uncounted run is never clean whatever the verdict; and a run with high pre-PR findings but a clean verdict and no tripwire is clean.
12. **Concurrency still moves one step at a time.** `concurrencyFromRuns` is unchanged: 3 when the newest counted run was clean at 3 or the newest two were clean at 2, else 2, never above 3, and the owner can still set `C` in the session. Its existing tests pass unchanged.
13. **The rule says so.** `run-backlog`'s SKILL.md (the **Concurrency** paragraph in step 3 and the summary in step 6) says the judge decides clean, which tripwires override it, how the coordinator logs both, and that the judge's input is the evidence record (AC 9). Checked by the grader reading the SKILL.md.
