**Gap:** A finished item's local gate runs the full graph (`pnpm verify --all`, ADR-030 rule 8; owner, 2026-11-26: "Full suite, cached"), every unit's lint, typecheck and whole test suite, even when the change reaches a few test files. The speed review of 2026-11-27 (its second, measured pass) timed one-line changes through the lock: a `functions` test file change took 319 s where the tests its import graph reaches took 5 s; a `functions` service, 434 s against 24 of 111 files in 49 s; a `web` component, 260 s against 32 of 100 files in 78 s. The commit hook (`scripts/pre-commit-tests.ts`) already computes that import-graph selection, and 26 of the last 32 bugs touched one unit. A narrower gate would trade the local full run for CI's (a pull request runs what it reaches, `stage` runs everything fresh), but nothing measures yet whether the precise selection would ever pass a change the full gate fails. Changing the gate itself changes ADR-030 rule 8, which is the owner's decision; this story only gathers the evidence for it. The owner, 2026-11-28, asked "Should I create the speed review's tooling stories T1–T7 in the backlog?": *"Yes, all seven"*; this is T5.

**Impact:** Before S226, nobody could say whether checking only what a change reaches would let a broken change through, so every finished item waited for the whole suite. After S226, every finished item also tries the precise check on the side and records whether it agreed, so after twenty pull requests the owner can decide on evidence whether to make finishing much faster.

**Acceptance criteria** (checks `scripts/verify-S226.sh` performs)

1. **One selection, shared.** The import-graph selection `scripts/pre-commit-tests.ts` makes (the changed packages and their dependents through `vitest related`, with its whole-suite fallbacks for `fixtures/`, a package's own config and the root toolchain files) becomes one exported function (ADR-025) that both the commit hook and the gate call; the hook's behaviour is unchanged. Its existing behaviour is pinned by unit tests in the `@bt/scripts` unit before it moves.
2. **The precise gate is defined and runnable.** For a change against the merge base with `origin/stage` (committed, uncommitted and untracked alike, as `pnpm verify` finds it), the precise gate is: the lint and typecheck tasks a narrowed `pnpm verify` runs for that change, the root tasks it reaches, and only the test files AC 1's selection picks, with no coverage floors. Running it alone prints what it selected and exits nonzero when any part fails. Unit tests cover the selection for a test-file-only change, a service change, a `web` component change, a `fixtures/` change (whole `functions` suite) and a root toolchain change (everything).
3. **Shadow mode at the finishing gate.** When the finishing gate runs (`pnpm verify --all`, from `scripts/audit.sh story` or a bug's own run), it also runs the precise gate and times both, and the full graph's exit alone decides the gate, as ADR-030 rule 8 says. A shadow result records: the precise gate's selection (units, root tasks, test file count), its exit and time, the full gate's exit and time, and a **miss** flag when the full gate failed and the precise one passed (with the failing tasks or test files the precise gate didn't select), or a **disagreement** flag when the precise gate failed and the full one passed. `BT_VERIFY_SHADOW=0` turns the shadow run off (the back-out), and a shadow run never writes or changes S222's stamp. Unit tests cover the miss and disagreement flags from fixed results.
4. **Every shadow result is kept.** A story's is a `Shadow gate` row in its `audit.sh story` ledger fragment. Under `/run-backlog` every finishing gate, a bug's included, is also logged as a `shadow` event in the run journal (`claims.ts run event shadow <ID> …`), and `audit.sh run` carries the run's shadow results into its run entry, so a bug's result outlives its worktree and session. Unit tests cover the event and the run entry's rows.
5. **A report says where the trial stands.** `node scripts/verify-shadow.ts report` (or the name the reuse check settles, never a root `package.json` script) reads the ledger through `scripts/backlog-vault/ledger.ts` and prints: the pull requests observed (one result per item, its last gate, since each item lands as one pull request; story fragments and run entries alike), each miss and disagreement with its item and the tasks or files involved, and the median time of each gate.
