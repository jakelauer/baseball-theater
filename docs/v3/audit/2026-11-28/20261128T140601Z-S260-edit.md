**Gap:** Four extras a finished game carries beside MLB's feed, the uniforms each team wore (S101), the rules it was played under (S100), MLB's player of the game (S99) and the per-play metrics (S93), can each be lost for good, in three ways:

- **Bug #720 (B720): the time limit starts too early.** Each bounded ask (`askWithinLimit`, `functions/src/services/player-of-the-game.ts`, 750 ms `PLAY_METRICS_LIMIT_MS` from `functions/src/adapters/http/mlb.ts`) starts its timer when the ask is created, not when its request leaves the Worker's queue of six simultaneous connections. A request that does several asks at once can run out the limit before the ask is sent, and the extra is silently dropped. B577 (PR #718) fixed this only for the cold day digest, whose late asks now run after the response with `LATE_ASK_LIMIT_MS` (15 s). The cron's ingest, the cron re-check (`functions/src/services/game-recheck.ts`) and each game's ingest Durable Object (`functions/src/services/game-ingest.ts`) still start the timer before the ask is queued.
- **#719: after-response asks that get cut off.** Since B577 the digest's late asks run after the response and are written by a late write (`storeLateAnswers`, `functions/src/services/ingest.ts`). If that work is cut off (the Worker's 30 s `waitUntil` cap, a database error before the late write, or every late ask timing out), a past, finished game stays stored without them. Such a game is served from the store and never asked again (S212). A plain rule ("a past final with no play metrics is due") can't tell a cut-off from a game MLB never had play metrics for, so it would ask MLB on every read forever (ADR-002, ADR-021). `readGames`' comment records the gap: telling the two apart "needs a stored mark". That mark changes how a game is stored, so where it lives was the owner's call: the **Owner answer** below.
- **#721 and #619: games already stored without them stay that way.** Before B577, a cold day's later games lost their bounded extras while queued (games 718501, 661126, 663004 and 662370 on staging, among others). A final game stored before S99, S100 or S101 shipped never got its pick, uniforms or rule settings either. Two places record #619 as an accepted gap: `functions/src/services/backfill.ts:30-34` and S100's and S101's baseline lines. Nothing repairs these games. The S122 backfill skips any game already stored as final (`fetchGame` in `backfill.ts`, about lines 178-183, repairing only its projection). So does the past-season backfill the owner plans to run. The re-check covers only the 7 days after a game.

The owner, 2026-11-28, asked *"Which of these enhancement groups should become stories? Pick any. Picking none leaves them as enhancements."*, chose *"Missing extras repair"* (the option: *"B720 plus #721, #719 and #619 in one pass: stop extras being lost on every path, and repair stored games that are missing them (the backfill won't). Medium. #719 needs a small stored marker, which the story would put to you."*). The owner's rule for work that computes (owner, 2026-11-28): *"For the computation ones though, I want to focus on performance of the computation. I don't want to end up spending a ton on compute"*. So the repair is a bounded, paced pass whose cost the tests count. It walks the stored games once and then stops costing anything but one read a tick.

**Impact:** Before S260, a finished game could end up without its uniforms, rules, player of the game or play metrics: on a busy request the ask ran out of time before it was even sent, or the work after the page answered was cut off. Nothing ever went back for them, and games stored before those features shipped never got them at all. After S260, the time limit runs from when each ask is really sent, a cut-off game is asked once more, and a slow background pass fills in the games already stored without them, a game at a time, then stops.

Two approaches are allowed, and the commit body says which was taken and why. One is a BT-side gate of the Worker's six connections (a named constant), whose slot starts the timer. The other moves those paths' asks after their write, as B577 did for the digest. The ask still never waits unbounded. 2. **A cut-off game is asked once more (#719): a mark on its stored row, which AC 4's pass re-asks (the Owner answer above).**
    - **Where the mark lives** (the agent's reading of *"Column on the stored row"*): a nullable column on the `games` row (for example `late_asks_owed_at`, the time the mark was set), outside its `document`, added by its own migration. Not a companion table: the mark describes that row's document, so it lives beside it, and `baseball-copy.ts`, which copies the columns both sides have, brings a copied game's mark with the document it describes. The mark is set and cleared only by its own statements, which never touch `version` or `document`. The ADR-022 versioned upsert (`… WHERE excluded.version > games.version`) doesn't write the column, so a duplicate or stale write neither sets nor clears it. `data-classification.ts` labels the column `none` (no user data, ADR-028), as `games`' other columns are. A partial index on the marked rows keeps the lookup below to those rows alone.
    - **What is owed, judged once** (ADR-025): one named function in `packages/domain/src/player-of-the-game.ts` beside `askedExtraDue` (for example `lateAsksOwed`, table-tested) says which after-response asks a digest's game owes (uniforms, rule settings, player of the game, playMetrics), from the inputs `askAfterResponse` gets today (the answered snapshot, the stored one, `playerOfTheGameDue`, and the playMetrics condition at `ingest.ts`' `askAfter` branch). Its per-extra rule is `askDueExtras`' `due` and its pick rule `withAskedPlayerOfTheGame`'s guard, made its named parts and called by both, so no second copy exists. It is judged once per game, after the batch's write lands; the mark and `askAfterResponse` both use that one result, and `askAfterResponse` asks exactly what it says. The other callers of `askDueExtras` and `withAskedPlayerOfTheGame` (the read's own asks, the cron's ingest, `recheckDueGame`, the game ingest object, the backfill) behave as today, their tests unchanged.
    - **Set before the response, one statement a batch:** after the read's batch write lands and before the response, one statement of its own marks every game this request fetched that owes any ask and is past and finished (`isPastFinishedGame` over the game as served, the judgement its late write's purge uses). Only such a game is never re-asked on read (S212); a live or upcoming game is refreshed by the next read, so it is never marked and its digest runs no mark or clear statement. A batch with no such game runs no mark statement. The mark is never set in the after-response follow-up, the work that gets cut off. A failed mark statement is logged and the read still answers (those games go unmarked, as every game is today). `GameRepository` (`packages/ports`) gains three one-statement methods, mark and clear (each a list of game keys) and the marked-game lookup below, built in `PostgresGameRepository`, `InMemoryGameRepository` and `functions/src/test/counting-repos.ts`, with cases in the shared contract suites (`functions/src/adapters/repository-contract.ts`, `storage-contract.ts`);
    - **Cleared after the late step, one statement a batch:** in the follow-up, once every game's late step has settled, and before its purge and before it throws for any failed game, one statement clears every game whose late step ended cleanly: no ask ran out its `LATE_ASK_LIMIT_MS`, and the late write landed or there was nothing to store (even when the answers add nothing). A failure of that statement joins the follow-up's failures and the marks stay. Whether an ask ran out its limit is told by `askWithinLimit`'s `onLimit` alone: `AskLimit` gains an optional `onLimit`, `askWithin` calls it when the limit ends an ask, and `askAfterResponse` builds its own `AskLimit` on each call (`LATE_ASK` with an `onLimit` that sets that call's flag; the shared constant carries none) and passes it to `askPlayMetrics`, `askDueExtras` and `withAskedPlayerOfTheGame`, returning the answered game or null, with the flag. `storeLateAnswers` returns whether it stored, had nothing to store, or was refused twice; its S216 `late` caller ignores that and is never marked. The mark stays when any ask ran out its limit (even if another answered), when the late write throws, and when it is refused twice by newer stored versions, since a timed-out ask and a write that doesn't land are the cut-offs (#719) the mark exists for. A failed ask counts as answered and clears it: every `fetch*` method in `adapters/http/mlb.ts` returns null for a failure and for "MLB has none" alike, and `askWithinLimit` maps a throw to null, so the late step can't tell them apart (Notes, **What it leaves**). The one re-ask clears it whatever happens, so a game MLB has nothing for is asked at most once more and never again;
    - only AC 4's `extras-repair` pass re-asks a marked game. Each tick it looks up marked games first (one statement on the partial index, oldest mark first) and asks one, within the same `EXTRAS_REPAIR_ASKS_PER_TICK`, before any game of its walk. It keeps doing so after the walk has ended. Two racing ticks ask a marked game once, and a stop between the ask and the clear asks it at most once more;
    - a past, finished game is never asked on read, marked or not (S212 holds), so a fan's read never calls MLB for it;
    - the re-ask uses the same bounded asks and keeps what is stored (`keepStoredExtras`);
    - a re-ask that changes the game writes its next version and purges its game, day and digest URLs through the existing purge (`purgeGameAndDayEdge`, owed on failure);

That function walks the stored games newest first, from a fixed cutoff date set when the story ships (games stored after it go through AC 1's and AC 2's paths), using a durable cursor kept in one row (a new table with its own migration, labelled in `data-classification.ts` and handled in `baseball-copy.ts` as its neighbours are, unless the reuse check finds an existing store that fits). A game is asked at most once in the pass, whether MLB answers or fails (a failure is logged). The cursor moves past it either way, and two racing ticks never ask the same game. The walk ends when the cursor passes the oldest stored game, or every source is given up and the cursor is before the player of the game's first season. After that a tick reads the cursor row and looks up AC 2's marked games, and does nothing more unless one is marked.
