**Gap:** BT's supporters are Patreon backers, and the owner probably wants to retire Patreon's tiers (nothing has changed yet): *"I probably will want to just retire all Patreon tiers, but include the patreon connector to figure out what backer level the person was and give them a great deal or an automatic backer status on the new tiers. I think the new tiers will include entirely different perks for legal reasons, and I'll want to do a thorough check on what those features could be"* (owner, 2026-11-28), after *"Actually... if it makes no difference that Patreon acts like a donation then I probably want to phase out Patreon in favor of Link, Stripe, or similar"* the same day, and then *"I'm not sure I even want tiers"*. Asked earlier that day whether to add the full Patreon connector (OAuth, pledge webhooks setting tiers, Unlink), he answered *"Not yet"*; this story is only the narrow lookup his later answer asks for. BT has no Patreon code beyond a place to keep the link: `users.patreon_user_id` (`functions/src/adapters/postgres/schema.ts`), classified personal and deleted with the account (`functions/src/services/data-classification.ts`, `userProfileFields.patreonUserId`); the stored `entitlements` row is "the real tier, which only a Patreon link writes", and nothing writes it yet. Patreon's API v2 gives a user's own OAuth token their identity and, with the `identity.memberships` scope, their memberships, while a creator's token reads its campaign's members (`/api/oauth2/v2/campaigns/{id}/members`) with fields such as patron status and lifetime support; which of these shows a former backer's tier and support to which token is checked on Patreon's own documentation by S258 (its `**Patreon API check:**` line), before its frames are drawn. What a former backer is given follows how supporters fund BT (S256), its screens are S258's, and its payment side S256's too (the provider, from S257, which S256 absorbed on 2026-11-28).

**Impact:** Before S259, a fan who backed BT on Patreon would lose any recognition of it if Patreon's tiers are retired, as the owner probably wants. After S259, a signed-in fan can link Patreon once, BT sees what Patreon shows of their backing and gives them the thanks or benefit the owner chose, and BT keeps no Patreon access afterwards.

**Acceptance criteria** (checks `scripts/verify-S259.sh` performs)

1. **What Patreon shows, from S258's check.** The lookup follows S258's `**Patreon API check:**` line; before writing code the story re-reads the pages it cites, and if they no longer say what the line records, it stops and reports (rule 10). It uses the user's own token if that shows the backer level. Otherwise it takes the member id of the user's membership of BT's campaign from the user's own token (`identity.memberships`) and reads that one member with the creator's token (`/api/oauth2/v2/members/{id}`), never paging the campaign's members. If S258's check found that `identity.memberships` doesn't list a former backer's membership, there is no member id to read, so the story stops (rule 10) and asks the owner, rather than paging the campaign.
2. **Link once, read once, keep no access.** A signed-in user starts the link from Settings (S258's frames); BT sends them to Patreon's OAuth with only the scopes AC 1 needs and a `state` that BT signs, that is bound to the user's session and that expires after a named `PATREON_STATE_TTL_MS`. Single use comes from Patreon's authorization code, which Patreon accepts once, so BT keeps no table of used states. Sessions are bearer tokens, so Patreon returns the user to a web route, following the sign-in callback's pattern (`web/src/session/SignInCallback.tsx`), that POSTs `code` and `state` to BT's API with the session's bearer. Tests refuse a missing `state`, another session's, an expired one and a tampered one, and a replayed return (the same `code` and `state` again: Patreon's double refuses the used code, and BT reports a failure without changing what it stored). BT then exchanges the code, reads the user's identity and backer level once, and discards the tokens: no user access or refresh token is stored. The grader greps the story's own added lines in the Postgres schema and migrations for `access_token` and `refresh_token` and finds none. For secrets it reads only the names this story adds, in its own added lines of the Worker's env interface (`WorkerEnv`, `functions/src/worker-app.ts`) and of `wrangler.jsonc` (the names already there, such as `BT_SESSION_KEY`, `LOGTO_S2S_SECRET` and the purge token, are not its to check), and allows only the OAuth client's id, client secret and redirect URI, the creator's token if AC 1 needs it, and the claim key if AC 4 needs it. A test asserts that no user token reaches a repository. Patreon is called through a port (`packages/ports`) with an HTTP adapter and a fixture double; tests use recorded or hand-written answers named as such, never the network.
3. **What BT keeps, and only that.** BT stores the Patreon user id (the existing `patreon_user_id`) and what it found (the level, whether current or former, lifetime support if S258's check found it, and when it looked) behind a repository port, Postgres with one migration and an in-memory double, one contract test against both. The classification manifest labels the new fields or table personal (law L3), the data download includes them (S80) and account deletion removes them (S77), each proven by a test; ADR-028's inventory in `docs/v3/ARCHITECTURE.md` names them, and the rows this design makes untrue are updated in the same change: `BT database: Patreon link (later)` (an encrypted refresh token; S259 stores no token) and `Patreon` ("BT deletes its copy and revokes access"; BT holds no access to revoke once the lookup ends). One Patreon user id may be claimed by one BT account only: the migration adds a unique constraint on `users.patreon_user_id`, which has none today (`functions/src/adapters/postgres/schema.ts`), and a second claim is refused (tested).
4. **The benefit, as the owner chose, never apart from its claim.** The benefit S258 records from the owner on its `**Owner answer:**` lines, the source of every word and rule this story takes from the owner, is granted by one domain function from the level found (a table test over every level Patreon's tiers had, `Backer` to `Premium Sponsor`, and over none and former), once per Patreon user id while its claim is stored: granting again changes nothing (ADR-022). A claim and its benefit can't come apart: where the benefit needs nothing stored of its own (a credit, a badge), it is derived at read time from the stored claim row by that function, so there is no second write; where it must be stored (for example a membership S256's proposed amendment calls for, if the owner has accepted it), the claim and the grant are written in one transaction, and a contract test makes the grant fail after the claim is written and finds neither stored. Whether a claim outlives the account follows S258's answer to its question (b): if a claim must survive deletion, BT keeps a keyed hash of the Patreon user id (an HMAC with a Worker secret, never a plain hash of a sequential id) after deletion, named as personal data in ADR-028's inventory with no deletion path (kept to stop a second claim), and ADR-028's decision gains a dated line quoting S258's answer as the owner's exception to "deletion reaches all of it"; a delete-and-relink can't claim again (tested); if not, BT keeps nothing and a relinked account may claim again (tested).
