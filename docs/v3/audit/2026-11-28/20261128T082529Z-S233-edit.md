**Gap:** BT has no league rankings, and the owner has chosen that BT compute its own rather than copy Savant's. First, on S104's catalogue (owner, 2026-11-28): *"percentile rankings for qualified players is worth getting, but if we can compute it from the other stats we already get that's another story. I don't know if we really know that though; the percentile stuff usually is not a normal stat and I'm not sure they even show which value is the one used"*, then *"I like your recommendations."* (S104's: fetch them, not compute them). Then the owner was asked the same day, *"The legal report says to compute percentile rankings ourselves (a sort over facts BT stores), but you chose S233 as 'fetched, not computed' from Savant. Which should stand?"*, and answered *"Compute our own (Recommended)"*, the option reading *"Rewrite S233 so BT ranks qualified players itself from stored facts and labels the values as BT's. Numbers can differ slightly from Savant's."* That answer supersedes the fetch. On cost the owner added: *"For the computation ones though, I want to focus on performance of the computation. I don't want to end up spending a ton on compute"* (2026-11-28). Ranking needs each player's season figures, and BT keeps them only inside each stored game's document (`games.document`, a `GameSnapshot` of about 300 pitches): per pitch MLB's speed, spin, extension, zone, call and contact (`packages/domain/src/plays.ts`), and S103's Savant figures where they were pulled, bat speed among them (`packages/domain/src/savant.ts`). Reading every game of a season each day to add them up would parse about 2,430 documents a day. This story extracts each game's per-player facts once, into a small table, so S237 can rank from it and S230 can add its results by pitch type in the same pass; it also builds the pieces those stories and S234 share, first in the chain; how Savant ranks (its pools and formula) is in `docs/v3/SAVANT-CATALOGUE.md` § Percentile rankings.

**Impact:** Before S233, BT's numbers about a player's season existed only scattered through each game it stored. S233 impact: BT keeps, for every game once it is final, each player's counts and measurements from that game (plate appearances, strikeouts, exit velocities, swings and misses, pitch speeds and spins), updated only when a game changes, so S237 can rank players and S230 can keep results by pitch type cheaply. No screen changes.

4. **Stored once per game, at one extractor version.** These tables sit behind one repository port, with Postgres (one migration), an in-memory double and one contract test against both (PGlite):
    - `player_game_facts` (season, game, player, role, team, AC 2's facts);
    - a state record per game, `player_facts_games` (game, season, official date, game type, home and away team ids, final status code, `extracted_version`, `extractor_version`, `extracted_at`, `claimed_at`, `tried_at`). No retention is needed: these tables grow by about 80,000 rows a year;
    - the sweep cursor's one row (AC 5).

    `PLAYER_FACTS_EXTRACTOR_VERSION` is a named constant, raised whenever extraction gains a fact or a table (S230 raises it). A game's facts are replaced and its state record written in one statement, only when the game's stored version is newer than `extracted_version` or its `extractor_version` is below the constant (ADR-022). The statement takes any further per-game rows in the same write, so S230's sibling table joins it without a second statement. The in-memory double applies all the writes or none, and the contract test runs the same cases on both, a failure part-way through leaving the old facts, `extracted_version` and `extractor_version`. Finishing or failing a game clears its `claimed_at` (test).
5. **Which games, and when.** A cron step in its own scope (`inDatabaseScope`, kind `cron`, job `player-facts`) runs each cron run. Every rule below is applied in the database, and the step reads a game's document only to extract it.
    - **Seasons:** only games whose official date falls in `mlbToday`'s year or the year before (`mlbToday`, `America/New_York`), so a new season's first final game is extracted the day it ends.
    - **Final first:** a game is a candidate only once its shared state says it is over: `game_states.document->'status'->>'codedGameState'` (a small document, `GameState.status`) is one of `FINAL_STATUS_CODES`, a list `packages/domain/src/window.ts` exports from its `STATUS_KINDS` table (whose `isFinalStatus` reads the same table) and passes to the statement, so the rule is written once. The game's code is kept in its state record. A live game re-stored every few seconds is never due and its document is never read. A `games` row with no `game_states` row is not a candidate, and nothing is logged, until its state row is written (test).
    - **Recent games:** due when final, and either its stored version is newer than `extracted_version` (or it has no state record) or its `extractor_version` is below `PLAYER_FACTS_EXTRACTOR_VERSION`, and it isn't resting. Candidates are found through the `games_official_date` index over the last `PLAYER_FACTS_LOOKBACK_DAYS` dates (2, which covers a game's ingest window and S103's last Savant pull after the final, `savantPullDue`) and joined to their state rows by key, so the lookup's cost doesn't grow with the season.
    - **Older games, the sweep:** a cursor row, `player_facts_sweep`, holds `sweep_date` (the date reached), `pass_extractor_version` (the extractor version the pass runs at), `passes_finished` (passes completed at that version), `pass_started_at` and `rest_until`.
        - When no recent game is due, a run claims up to `PLAYER_FACTS_GAMES_PER_RUN` due games of `sweep_date`. When it claims fewer than that, the same statement moves `sweep_date` one date back by compare-and-set on its old value, so two overlapping runs can't both move it and skip a date. A 12-game date therefore takes three runs (5, 5, then 2 and the move).
        - A resting or claimed game is not claimable, so it never pins the cursor; the next pass picks it up.
        - The cursor runs from the lookback edge back to January 1 of the year before. Reaching it finishes a pass (`passes_finished` + 1) and rests the cursor for `PLAYER_FACTS_SWEEP_INTERVAL_MS` (a week) before the next pass.
        - When `PLAYER_FACTS_EXTRACTOR_VERSION` is above `pass_extractor_version`, a new pass starts at once at the new version with `passes_finished` reset to 0, so the batches wait for the refill (AC 7).
        - The first fill of a new database is about 695 dates and about 1,400 runs: about 24 hours at one run a minute.
    - **Game type:** read once, from the game's stored schedule day (`schedule_days`, `ScheduleGameSummary.gameType`, S167) with `storedGameType` (and `dayRegularSeason` for the day), and kept in the state record with both team ids (from the snapshot). A game that isn't regular season is recorded without facts and is not due again until its version changes. A game whose type is unknown (`storedGameType` and `dayRegularSeason` both null, as on schedule days stored before S167) is recorded as unknown, without facts, and logged when recorded. It is due again, whatever its versions, once it hasn't been tried for `PLAYER_FACTS_UNKNOWN_TYPE_RETRY_MS` (a day); that retry reads only its schedule day, not its document, until the type is known.
    - **Claimed:** at most `PLAYER_FACTS_GAMES_PER_RUN` (5) due games, in the same statement, each with a lease of `PLAYER_FACTS_CLAIM_LEASE_MS` (as `GAME_RECHECK_CLAIM_LEASE_MS`), skipping one claimed inside its lease or tried within `PLAYER_FACTS_RETRY_MS` (an hour), so two runs never take the same game.
    - **Failed:** a game whose document can't be read or extracted keeps its old facts, gets `tried_at`, has its claim cleared, and is logged with its game and the reason.
    - **Idle:** when no game is due, the run is that one statement and reads no game document.
    - Tests on a fake clock:
        - idle: one statement, no documents;
        - a new final game: one document read and its facts stored;
        - the first final game of a new season (2027-04-01 with only 2026 facts stored): extracted;
        - a live game re-stored every minute for three hours: never read until final, then once;
        - the same game re-stored with S103's figures after its final: extracted again;
        - a game extracted at extractor version 1, then the constant raised to 2: extracted again by the new pass, and `passes_finished` is 0 until that pass ends;
        - a spring-training game: recorded and never extracted;
        - a game of unknown type: recorded, logged, not extracted; its schedule day (stored before S167) then refreshed with `R`: extracted on the next retry after a day;
        - two racing runs: each game read once, and the cursor moved once;
        - a failed game: rested, then retried;
        - a resting game on the sweep's date: the cursor still moves on;
        - a 12-game date: three runs;
        - an old game re-stored: extracted on the sweep's next pass.

7. **The batch gate, shared.** One function in `functions/src/`, `factsBatchDue`, answers whether a daily batch over these facts (S230's daily pass, S237's ranking) should run for a season. It takes the batch's own state (the facts watermark it last ran at, and when) and runs one statement:
