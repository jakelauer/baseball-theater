**Gap:** BT knows each pitch's type from MLB's live feed, but not how that pitch does for the pitcher over a season, or how a batter does against that type: MLB's API has pitch-type split codes (`pff`, `psl`) that return no rows from `statSplits`, and Baseball-Reference has none (`docs/v3/SAVANT-CATALOGUE.md` § Pitch-arsenal-stats). S104 catalogued Savant's player data and the owner set the tests (owner, 2026-11-28: *"I am only interested in data I can get 1) for every player, 2) which isn't available from other free sources, 3) which is a) reasonably useful to show users as is, or b) is reasonably useful to show in combination with another stat we can already easily get from mlb, or c) is usable to mathematically calculate something that is reasonably useful to show people."*); results by pitch type passed them, and the owner chose them: *"I LOVE the idea of pitch 1, especially the putaway pitch thing, the BAA for a given pitch, etc as long as it's not repetitive for every single batter. But as far as getting the data, yes."* Savant publishes them as a leaderboard file, but the owner was then asked (2026-11-28) *"S230 (results by pitch type: batting average, slugging, whiff rate per pitch type) downloads Savant's whole pitch-arsenal leaderboard file every day, which the legal report counts as the bulk-leaderboard risk. BT already stores every pitch with its type, so it could compute these itself in the same daily batch as the percentiles. Which should S230 do?"* and answered *"If we can compute it without exorbitant cost, do that"*, under the owner's cost rule (*"For the computation ones though, I want to focus on performance of the computation. I don't want to end up spending a ton on compute"*, 2026-11-28). BT already stores every pitch of every game it keeps, backfilled games included (S122 stores the full feed): its type (MLB's own `details.type` code, the same code a live pitch carries), the count after it, the call and the batted ball (`packages/domain/src/plays.ts`), and the at-bat's result. S233 extracts each final game's per-player facts once, in one statement a game, behind a gate for daily batches. This story adds the same facts per pitch type to that pass. Then the owner was asked (2026-11-28) *"Callouts showing a pitch's season record: should the numbers count only games before the one you're watching? Today S230 serves current season totals, so a finished game's callout includes that game, and looking back at an old game includes games played after it. Counting only earlier games means S230's route takes a date, and that's cheapest to settle before S230 is built."* and answered *"How much processing will it require to compute with the date? Or maybe it would be best to store the daily values?"*; asked *"On season numbers 'as of the game': the cheapest way is to store each player's running season totals per pitch type as of each game they play. That gets computed once, when S233 extracts a game, as a running sum (about 380k rows a season, the same size as S233's facts table), and a callout reads the latest row before the game's date with one indexed lookup. Storing a snapshot for every player every day would be about 1M rows a season for the same answer, and computing it on each request reads a few hundred rows per player, though edge caching would soften that. Which?"*, he answered *"Can we store the running totals with the game, not the player? Each game could just have a running totals blob for the players in the game, which just requires one row per game"*. So a callout's numbers for a game of the current season count only the games before it, stored with the game, one row per game. Of earlier seasons he said *"Don't provide the season numbers for earlier seasons. Put that recomputation into the ideas milestone"*, then, superseding it, *"Actually scratch that, use the season total for earlier seasons with a callout at the top saying certain stats may be iffy"* (both 2026-11-28): a game of an earlier season gets that season's full totals, which include the game shown and those after it, and S231 draws a notice at the top saying so; exact as-of-the-game numbers for earlier seasons are an idea in the Ideas milestone (#726).

**Impact:** Before S230, BT could say what a pitch was but not how well that pitch works for the pitcher, or how the batter does against it. 4. **Earlier seasons, the cron step and its statements.** For the season other than the current one that has pitch-type facts (S233 keeps `mlbToday`'s year and the year before, so the year before), the daily pass sums that season's `player_game_pitch_type_facts` per player, role and pitch type into `player_pitch_type_results` (counts only), when its facts changed since its own state row, so about once after the season ends (the owner's second instruction above). Seasons older than S233's window have no facts and so no numbers (the agent's reading of S233's window). The state is one table, `player_pitch_type_aggregations`, keyed by season and kind (`current`, `earlier`): the facts watermark, when the pass last ran, and, for `current`, the today step's watermark and date.

    - **Statement 1, the check:** reads both candidate seasons' state rows by key, which seasons hold pitch-type facts (for `servedSeason`), S233's sweep cursor (`passes_finished`), and the today step's conditions through `PITCH_TYPE_TOTALS_GAMES` for today's date and S233's `player_facts_games (season, extracted_at)` index, and returns the current season's newest `extracted_at`, the watermark the writes then use.

    - **Statement 3, only when due:** the daily pass or the today step, each one statement of data-modifying CTEs. Its first CTE is a compare-and-set `UPDATE` of its state row whose `WHERE` matches the values statement 1 read and also holds back while a game of the season is claimed inside its lease (S233's partial index on `claimed_at`, as the gate reads it), and every other CTE joins its `RETURNING`: a run that lost a race, or that a claim made after the check holds back, changes nothing, its state row included, so the next run writes. For a season's first run (no state row yet), that first CTE is instead `INSERT … ON CONFLICT DO NOTHING RETURNING`, under the same claim guard, so of two first runs the loser gets zero rows and writes nothing. Its upsert overwrites a row only from a watermark at least as new (`ON CONFLICT (game_pk) DO UPDATE … WHERE excluded.watermark >= game_pitch_type_totals.watermark`, ADR-022). The daily pass also sets the `current` state row's today watermark and date (so a today step doesn't rewrite the same rows right after it), writes the earlier season's totals when due, as an upsert of the new set's keys plus a delete of the keys absent from it (disjoint key sets, never a delete and a re-insert of the same keys in sibling CTEs), deletes the per-game rows of every season but the current one in the same statement (so on the turn last season's games answer from their rows until its totals exist), and deletes pitch-type facts, totals and state rows of seasons before the year before. The today step runs only once the sweep has finished a pass at the current extractor version.
