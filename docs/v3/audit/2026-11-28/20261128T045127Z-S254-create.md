**Gap:** BT's server reads MLB's Stats API, mlb.com, MLB's search and GraphQL hosts and Baseball Savant through one adapter, `HttpMlbStatsClient` (`functions/src/adapters/http/mlb.ts`; the backfill paces it with `PoliteFetch`, `functions/src/services/polite-fetch.ts`), and the fixture recorder fetches the same hosts itself (`functions/src/services/recorder.ts`). None of them says who is asking: no request sets a `User-Agent` (`grep -rn "User-Agent" functions/src` finds nothing), so MLB sees whatever the runtime sends by default, which names the runtime, not BT. A legal research note the owner read on 2026-11-28 (research, not legal advice) found that, for pages and APIs open to anyone with no login or key, as `statsapi.mlb.com` and `baseballsavant.mlb.com` are (both answer `access-control-allow-origin: *`), reading them is not access "without authorization" under the computer-misuse law, a position that weakens if MLB blocks BT and BT gets around the block; and that MLB's realistic steps are a cease-and-desist letter or blocking BT's addresses. Its advice for this lowest-risk use: keep the cadence design (ADR-002: one reader per game, not one per fan), identify BT honestly in the User-Agent, and never evade a block. The owner: *"I want to do all your suggestions except redrawing the fields (which I'll do but not yet)."* (2026-11-28). The backfill already paces itself so as not to be a bad citizen (owner, 2026-11-07: *"I don't want to be a bad citizen, don't hit the API too hard"*); `PoliteFetch` retries a 429 and a 5xx, and answers a 403 as it is.

**Impact:** Before S254, MLB's servers couldn't tell BT's requests from anyone else's. After S254, every request BT makes to MLB or Baseball Savant names Baseball Theater and where to find it, BT never changes how it identifies itself to get past a refusal, and a refusal is logged so the owner sees it.

**Acceptance criteria** (checks `scripts/verify-S254.sh` performs)

1. **One identity, set in one place.** One exported constant, `BT_USER_AGENT`, in `functions/src/adapters/http/` holds BT's User-Agent: the product name and a URL where MLB can read what BT is, `BaseballTheater (+https://baseball.theater/about)`, with a comment saying why (the owner's words above). One exported wrapper beside it, `withBtUserAgent(fetchImpl)`, takes any fetch function, the runtime's `fetch` or an injected one (the backfill hands `PoliteFetch`'s fetch to `HttpMlbStatsClient`, and the recorder takes a `fetchImpl`), and answers a fetch that sends `User-Agent: BT_USER_AGENT` and passes everything else through, keeping the caller's own headers whether given as an object or a `Headers`. It is the only place a User-Agent is set under `functions/src/`: the grader strips comments from the non-test files and greps the code left for the header name as a string literal (`"User-Agent"` or `"user-agent"`, either quote), finding only the wrapper's. Nothing chooses between identities (no list, rotation or per-request choice).
2. **Every MLB and Savant request carries it.** `HttpMlbStatsClient` builds its fetch through `withBtUserAgent` once, in its constructor, whether it was given a fetch or not (so a `PoliteFetch` or a test's fake fetch sees the header too), never per method; the recorder's two fetches (`recorder.ts`, each a `doFetch` built from `options.fetchImpl` or `fetch`) are built through it too. The client's test is driven by a table with one row per method: the arguments that make it send at least one request (for example `fetchPlayers` with a non-empty list of ids). A guard lists the class's prototype and fails when a method is in neither the table nor an exclusion list, each excluded method (private helpers such as `getJson`, `standingsAt` and `fetchContent`) with why, so a method added later must be placed. For each row the test asserts that at least one request was recorded and that every recorded request's `User-Agent` equals `BT_USER_AGENT`; it checks the recorded requests, not the method's result, and tolerates a rejection (a parser refusing the fake body). The table runs twice, with the default fetch stubbed and with a custom `fetchImpl` passed in. Further cases: a caller's own headers (`accept`, Search's headers, a `Headers` object) arrive unchanged beside it; the recorder's two fetches send it (test). Requests to hosts that are not MLB's (the Chadwick register on GitHub, Cloudflare's purge API, the identity provider) are not changed by this story.
3. **A refusal is never routed around.** A 401, 403 or 451 from an MLB or Savant host is answered as it is: `PoliteFetch` does not retry it (test: one request, no second, for each status), the client does not retry it with other headers, another host or another path (test with a fake fetch counting requests), and the wrapper logs one structured line for it, `event: "upstream-refused"`, with the host, the status and the path without its query. The line is logged in `withBtUserAgent` itself, because some callers (`fetchVenueField`, `fetchContent`) swallow a non-OK answer; it is logged at most once per host for each wrapper instance, and the story records in SAVANT-DATA (AC 4) where instances are made (test: two refusals from one host through one wrapper log one line; one from each of two hosts log two). There is no back-off: BT keeps its normal cadence after a refusal and simply doesn't retry or reroute (the agent's reading; whether BT should pause a refused host is the owner's to decide). No code under `functions/src/` sends MLB requests through a proxy or alternate address (the grader greps for `proxy` in the HTTP adapter and the services and finds none added by this story).
4. **The rule is written down.** `docs/v3/SAVANT-DATA.md` § Terms of use gains a paragraph, dated, saying BT identifies itself as `BT_USER_AGENT` says on every MLB and Savant request, keeps ADR-002's one-reader-per-game cadence, and on a block or a letter from MLB changes nothing to get around it (not its identity, address or route), and the agent who sees the `upstream-refused` line or the letter asks the owner what to do, quoting the owner's 2026-11-28 answer. It also says where `withBtUserAgent` instances are made (each `HttpMlbStatsClient` and each recorder run, as the story finds them), so a reader knows what "once per host per wrapper instance" means in practice. The grader checks the paragraph names the constant's value and the word `withBtUserAgent`.
5. **MLB answers the new identity.** Before shipping, the story sends one request with `BT_USER_AGENT` to each host BT reads (the Stats API, mlb.com's content, MLB's search and GraphQL hosts, and Baseball Savant), through `withBtUserAgent` (the recorder with `BT_USE_LIVE_MLB=1` where it reads that host, otherwise a one-off script under `functions/src/scripts/`; this is the story's one live check, and tests stay offline), and records each host, the status it answered and the date on a `**User-Agent check:**` line in its own text (`scripts/audit.sh edit S254`).
