**Gap:** A `/run-backlog` run's concurrency `C` rises from 2 to 3 only after counted runs that were "clean", and `summarizeRun` (`scripts/backlog-vault/runs.ts`) decides clean by a fixed formula: no merge conflicts, no duplicate implementations, a drain under 3 hours, and pre-PR findings per pull request no higher than the lowest earlier counted run's at `C` = 2 (owner, 2026-11-20: "First C=2 run sets it (Recommended)"; 2026-11-26: "Count pre-PR findings (Recommended)"), with a run whose findings went unrecorded never clean. The speed review of 2026-11-27 found the bar cannot be met as written (the run it read was unmeasured, its journal rebuilt) and that counting what the pre-PR review finds marks a run unclean for thorough review rather than for problems that running items side by side caused. The owner, 2026-11-27, on that proposal: *"Can the judgment of what is clean actually be a judgment rather than be deterministic and based on outcomes? … maybe it should just be something where an agent is asked the question"*. Then, 2026-11-28, asked "Should I create the speed review's tooling stories T1–T7 in the backlog?": *"Yes, all seven"*; this is T6.

**Impact:** Before S227, a run could only count as clean by passing a fixed numeric bar that thorough reviews made harder to pass, so backlog runs stayed at two items at a time. After S227, a fresh agent looks at what actually happened in the run and judges whether running that many side by side caused trouble, while a broken staging build, a reverted change or a defect that got through still marks the run not clean, so runs can safely go back to three at a time.

**Acceptance criteria** (checks `scripts/verify-S227.sh` performs)

1. **A judge with one question.** A new agent definition, `.claude/agents/run-judge.md`, meets law L18 (frontmatter with `name: run-judge` and a `description`), is read-only (no edit, write or shell tools in its `tools:` line) and runs on a light model, as `review-tracker` does. It is asked one question, in its definition's words: did running this many items side by side cause problems in this run, and would running one more have? It answers `clean` or `not-clean` with a reason of at most a few sentences that cites the numbers it relied on. It is never the coordinator and is started fresh for each run. Grader: reads the file's frontmatter and body.
2. **The numbers are its evidence, not the verdict.** The judge's input is the run's own record, built by one function in `runs.ts` (ADR-025) from the journal: `C` and the peak in flight, items started and merged, merge conflicts, refused claims (`claim-refused`), duplicates, turn-cap hits, parks and set-asides, the drain time, pre-PR findings per pull request (with any unknown counts named as unknown), and any tripwire (AC 3). Unit tests pin the input for a fixed journal.
3. **Tripwires override the judge.** Three events make a run not clean whatever the judge says: `stage` went red during the run (a CI run on `stage` failed), a pull request the run merged was reverted, or a defect in something the run merged was found on staging or in production (an escape). The coordinator logs each as `run event tripwire --kind red-stage|revert|escape --ref <run, pull request or issue>` (a new run-level kind in `RUN_KINDS`), and `summarizeRun` reads them. A revert or escape is often found after its run's entry is written, when it can no longer change that run's summary: the coordinator then logs it in the current run's journal with `--run <the earlier run's ID>`, the current run's entry records it, and the run records built in `runs.ts` for `concurrencyFromRuns` (`runRecordOf`) mark the earlier run not clean, so a later run never rises to 3 on it (`concurrencyFromRuns` itself unchanged, AC 5). Unit tests cover each tripwire turning a judged-clean run not clean, and an escape logged during a later run turning the earlier run's record not clean.
4. **Clean is the judge's verdict, recorded.** The coordinator logs the verdict as `run event clean-verdict --verdict clean|not-clean --reason "<text>"` before `audit.sh run`. `summarizeRun`'s clean becomes: counted (unchanged: at least `MIN_ITEMS` started, the peak reached `C`, one merge, not abandoned) and no tripwire and a `clean` verdict; a run with no verdict is not clean. The fixed findings bar (`underBar` and the `bars` it reads) is removed, and conflicts, duplicates and the drain become evidence for the judge, not conditions. The run entry records the verdict, its reason and the evidence beside the existing figures. Unit tests cover: a judged-clean counted run is clean; judged not-clean is not; no verdict is not; an uncounted run is never clean whatever the verdict; and a run with high pre-PR findings but a clean verdict and no tripwire is clean.
5. **Concurrency still moves one step at a time.** `concurrencyFromRuns` is unchanged: 3 when the newest counted run was clean at 3 or the newest two were clean at 2, else 2, never above 3, and the owner can still set `C` in the session. Its existing tests pass unchanged.
