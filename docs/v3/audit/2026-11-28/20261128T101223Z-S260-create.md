**Gap:** Four extras a finished game carries beside MLB's feed, the uniforms each team wore (S101), the rules it was played under (S100), MLB's player of the game (S99) and the per-play metrics (S93), can each be lost for good, in three ways:

- **Bug #720 (B720): the time limit starts too early.** Each bounded ask (`askWithinLimit`, `functions/src/services/player-of-the-game.ts`, 750 ms `PLAY_METRICS_LIMIT_MS` from `functions/src/adapters/http/mlb.ts`) starts its timer when the ask is created, not when its request leaves the Worker's queue of six simultaneous connections. A request that does several asks at once can run out the limit before the ask is sent, and the extra is silently dropped. B577 (PR #718) fixed this only for the cold day digest, whose late asks now run after the response with `LATE_ASK_LIMIT_MS` (15 s). The cron's ingest, the cron re-check (`functions/src/services/game-recheck.ts`) and each game's ingest Durable Object (`functions/src/services/game-ingest.ts`) still start the timer before the ask is queued.
- **#719: after-response asks that get cut off.** Since B577 the digest's late asks run after the response and are written by a late write (`storeLateAnswers`, `functions/src/services/ingest.ts`). If that work is cut off (the Worker's 30 s `waitUntil` cap, a database error before the late write, or every late ask timing out), a past, finished game stays stored without them. Such a game is served from the store and never asked again (S212). A plain rule ("a past final with no play metrics is due") can't tell a cut-off from a game MLB never had play metrics for, so it would ask MLB on every read forever (ADR-002, ADR-021). `readGames`' comment records the gap: telling the two apart "needs a stored mark". That mark changes how a game is stored, so the shape and versioning are the owner's call (Owner question below).
- **#721 and #619: games already stored without them stay that way.** Before B577, a cold day's later games lost their bounded extras while queued (games 718501, 661126, 663004 and 662370 on staging, among others). A final game stored before S99, S100 or S101 shipped never got its pick, uniforms or rule settings either. Two places record #619 as an accepted gap: `functions/src/services/backfill.ts:30-34` and S100's and S101's baseline lines. Nothing repairs these games. The S122 backfill skips any game already stored as final (`fetchGame` in `backfill.ts`, about lines 178-183, repairing only its projection). So does the past-season backfill the owner plans to run. The re-check covers only the 7 days after a game.

The owner, 2026-11-28, asked *"Which of these enhancement groups should become stories? Pick any. Picking none leaves them as enhancements."*, chose *"Missing extras repair"* (the option: *"B720 plus #721, #719 and #619 in one pass: stop extras being lost on every path, and repair stored games that are missing them (the backfill won't). Medium. #719 needs a small stored marker, which the story would put to you."*). The owner's rule for work that computes (owner, 2026-11-28): *"For the computation ones though, I want to focus on performance of the computation. I don't want to end up spending a ton on compute"*. So the repair is a bounded, paced pass whose cost the tests count. It walks the stored games once and then stops costing anything but one read a tick.

**Impact:** Before S260, a finished game could end up without its uniforms, rules, player of the game or play metrics: on a busy request the ask ran out of time before it was even sent, or the work after the page answered was cut off. Nothing ever went back for them, and games stored before those features shipped never got them at all. After S260, the time limit runs from when each ask is really sent, a cut-off game is asked once more, and a slow background pass fills in the games already stored without them, a game at a time, then stops.

**Acceptance criteria** (checks `scripts/verify-S260.sh` performs)

1. **The limit starts when the ask is sent (B720, #720).** On each of the three paths, the cron's ingest (`ingestGame` from the cron tick), the cron re-check (`recheckDueGame`) and the game ingest object's poll (`functions/src/services/game-ingest.ts`), a bounded ask's `PLAY_METRICS_LIMIT_MS` counts from when its request is sent, not from when it is created. Two approaches are allowed, and the commit body says which was taken and why. One is a BT-side gate of the Worker's six connections (a named constant), whose slot starts the timer. The other moves those paths' asks after their write, as B577 did for the digest. The ask still never waits unbounded. Tests on fake timers, one for each path, use a fake MLB client that holds six slots like the Worker's queue: six slow requests fill them for 2 s, then the uniforms, rule-settings and player-of-the-game asks queue behind. Each answers 100 ms after it is sent, and the stored game keeps all three (on HEAD they are dropped). An ask that doesn't answer within its limit of being sent is still left out at that limit, logged as today, and nothing already stored is lost (`keepStoredExtras`).
2. **A cut-off game is asked once more (#719), built as the owner answers the Owner question below.** Whichever option is chosen:
    - a game whose after-response asks were started but whose late write didn't land carries the mark;
    - the late write, or the one re-ask, clears it whether MLB answered or not, so a game MLB has nothing for is asked once more and never again;
    - a past, finished game with no mark is never asked on read (S212 holds);
    - the re-ask uses the same bounded asks and keeps what is stored (`keepStoredExtras`);
    - a re-ask that changes the game writes its next version and purges its game, day and digest URLs through the existing purge (`purgeGameAndDayEdge`, owed on failure);
    - setting or clearing the mark is versioned and served exactly as the answer says.

    Tests cover: a late write cut off before it lands (the mark is set, one re-ask fills the extras and clears it); MLB answering nothing (cleared after one re-ask, then no more asks over ten further reads or ticks, counted on the fake client); and a late write that lands (no mark left, no re-ask). If the chosen option changes the served snapshot, `openapi/bt-api.v1.json` and `web/src/api/generated/` change additively (`pnpm api:breaking` 0). Otherwise neither file changes.
3. **The comments are true.** `readGames`' comment no longer calls the cut-off gap unrepaired. `backfill.ts`' header no longer calls #619 an accepted gap: it names this story's pass as the repair for games it skips as stored finals. `game-recheck.ts`' request budget comment matches AC 1's approach. `pnpm comments:stale` only flags and always exits 0, so the grader runs it against the story's base and fails on any symbol it lists in a file the story changed, unless the grader's own `COMMENTS_STILL_TRUE` list names that symbol with why its comment still holds.
4. **Stored games missing extras are repaired by a paced pass (#721, #619).** A cron job, `extras-repair`, runs in `functions/src/worker.ts` in its own `waitUntil` and database scope, logging S220's round-trip line with `job: "extras-repair"`. It calls one function, `repairStoredExtras` in `functions/src/services/extras-repair.ts`. That function walks the stored games newest first, from a fixed cutoff date set when the story ships (games stored after it go through AC 1's and AC 2's paths), using a durable cursor kept in one row (a new table with its own migration, labelled in `data-classification.ts` and handled in `baseball-copy.ts` as its neighbours are, unless the reuse check finds an existing store that fits). For each game it asks MLB only for what that game is missing and could have:
    - uniforms and rule settings while `askedExtraDue` says so;
    - the player of the game while `playerOfTheGameExpected` holds and a side is missing;
    - play metrics while none are stored.

    Each source is given up after `GIVE_UP_AFTER_DAYS` days of games in a row with no answer, as the backfill does (`recordSourceDay`, reused, not copied). The pass writes through the existing paths, so a write that changes nothing stamps no version, and a changed past game's URLs are purged as in AC 2. A game is asked at most once in the pass, whether MLB answers or fails (a failure is logged). The cursor moves past it either way, and two racing ticks never ask the same game. The pass ends when the cursor passes the oldest stored game, or every source is given up and the cursor is before the player of the game's first season. After that a tick reads the cursor row and does nothing more.

    **Cost, counted** (the owner's rule above). Named constants hold the pace:
    - `EXTRAS_REPAIR_SCAN_PER_TICK` games read a tick, at most 20, through one statement that selects only each game's key, date, status and which extras it holds, never its whole document, and uses the `games_official_date` index;
    - `EXTRAS_REPAIR_ASKS_PER_TICK` games asked a tick, at most 1, so at most 4 MLB requests a tick.

    The test counts round trips (`functions/src/test/counting-repos.ts` or S220's `countRoundTrips`) and MLB requests on a counting fake client, and holds them:
    - a tick after the pass has ended: 1 statement, 0 MLB requests;
    - a tick whose games are all complete: at most 2 statements (the scan and the cursor move), 0 MLB requests;
    - a tick with a game missing everything: at most 4 MLB requests and at most `EXTRAS_REPAIR_STATEMENTS_PER_TICK` statements (a named constant the test states);
    - the scan with `ANALYZE` first, on PGlite: it uses the `games_official_date` index, and reads the same number of rows at 2,430 and at 4,860 generated games (small stand-in documents).

    Further cases: a game stored before S99 with no pick gets one (#619); a game holding every extra is never asked; a source given up after its run of empty days is not asked again; two racing ticks ask the game once; a stop between the ask and the cursor move asks it at most once more. Milliseconds are measured and recorded in the ledger, never asserted. The story's comment on `repairStoredExtras` states the pass's MLB ceiling (4 requests a tick, 5,760 a day, only while the pass runs) beside the re-check's. If a count is over its ceiling, the story stops and reports (rule 10).
5. **Coverage holds.** `functions/vitest.config.ts`' floors are raised to their new measured values where they rose (rule 21), never lowered. `scripts/verify-S54.sh`'s check 3 names the floors.

**Owner question** (asked before AC 2 is built; options in order, the first recommended):

*#719's "re-ask once" needs a stored mark on a game whose after-response asks were cut off. Where should it live, and what re-asks it?*

1. **A mark beside the game, re-asked by the paced pass (Recommended).** The mark is a column on the game's stored row (`games`), outside the snapshot it serves. Setting or clearing it doesn't change the game's version, served answer, edge copy or API. AC 4's cron pass asks marked games first, within the same per-tick ceiling, so a read never asks MLB (S212 holds). Cheapest: no new version, purge or spec change, except when a re-ask actually fills something in.
2. **A field on the snapshot, re-asked by the next read, as #719 describes.** `GameSnapshot` gains an optional `lateAsksPending` flag, written in the document and served (spec and generated client additive). Setting and clearing it are versioned changes like any other, each purging the game's edge copy. The next read of a marked past game re-asks once after its response. Visible to clients and to the data download, and it costs a version and a purge on every cut-off and every clear.
3. **No mark: leave #719 to the paced pass alone.** AC 4's pass is extended to re-walk recent games once a day for missing extras, asking each source at most once per game per walk. No stored shape changes, but a game MLB has nothing for is asked again on each walk while it stays in the recent window.
