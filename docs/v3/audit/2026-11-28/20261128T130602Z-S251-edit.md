**Gap:** S151 restored the video player's Download button: `PlayerActions` (`web/src/components/videos/PlayerActions.tsx`) draws it for any clip whose MP4 is on MLB's clip hosts (`isMlbClipMp4` and `MLB_CLIP_HOSTS`, `packages/domain/src/video-quality.ts`) while the service worker in control answers its ping (`useDownloadRoute`, `askDownloadRoute`), and the worker (`web/src/pwa/download.ts`, wired in `web/src/pwa/sw.ts`) answers `/download/clip` by streaming MLB's file to the device as an attachment, a whole condensed game included. MLB's Terms of Use (last updated March 11, 2025, read 2026-11-28), §1, allow *"downloading one copy … on any single device for your personal, non-commercial home use"*. A legal research note the owner read on 2026-11-28 (research, not legal advice) ranked clip download the highest risk BT carries: MLB registers its telecasts, so video is where statutory damages exist, and a button built to save MLB's files, long-form condensed games included, which MLB sells access to, is the story a plaintiff would tell. It offered two changes: the cheapest kept Download for short highlights only, with a "for your personal use" line; the safest replaced Download with an "Open at MLB" link. The owner first answered *"I want to do all your suggestions except redrawing the fields (which I'll do but not yet)."* (2026-11-28), and then, asked whether to keep the cheapest Download option (short highlights only, personal-use line) or the safest (drop Download, replace it with "Open at MLB"): *"Let's ditch the download option. We already have the direct link"* (2026-11-28). So Download goes, with the worker route and the domain check that only it used; the palette's Direct link, which opens MLB's own file in a new tab, stays as it is. The link to MLB's page for each clip is S252's design and S253's build.

Three small leftovers in the same player (from S261, folded in here):

- **#500: hls.js has no size budget.** B415 plays MLB's adaptive HLS stream on desktop Chrome and Firefox through hls.js (`hls.js/light` 1.7.4). It is loaded as its own chunk only when an HLS clip plays (`loadHls`, `web/src/components/videos/hls-loader.ts`). That chunk is about 117 KB gzipped; the owner was told about 60 KB when choosing it. `.size-limit.json` budgets only the entry chunk (`web/dist/assets/index-*.js`, 200 KB gzipped, ADR-026), so an hls.js upgrade could grow the chunk with nothing noticing.
- **#501: an HLS-only clip has no second try.** When hls.js fails on a clip (a fatal error, or its chunk won't load), `VideoPlayer` (`web/src/components/videos/VideoPlayer.tsx`) switches to the same cut's MP4 from the same moment. A clip MLB gives only an HLS rendition has nothing to switch to. Its comment says so: *"A clip MLB gives no MP4 for has nothing to fall back to: it stays paused."* One passing network or media error is enough to leave a dead player.
- **#600: `clipClock`'s comment is untrue.** `clipClock` (`packages/domain/src/highlights.ts`) says *"The video badge (`clipDuration`) and the player's elapsed / total time (S70) both print through it"*. B579 replaced that custom time display with the browser's own controls, so only `clipDuration` uses it now. It can't be removed, as #600 first suggested, because `clipDuration` calls it (`highlights.ts:269`) and `VideoCard` shows `clipDuration`. ADR-025 still requires the comment to be true.

The owner, 2026-11-28, asked *"Which of these smaller groups should become stories? Pick any. Picking none leaves them as enhancements."*, chose *"Video player cleanup"* (the option: *"#500 (an hls.js size budget), #501 (an HLS fallback) and #600 (a stale clipClock comment), with or after S251. Small."*).

**Impact:** Before S251, the video player had a Download button that saved MLB's video file to the fan's device, a whole condensed game included; nothing stopped the video library behind MLB's adaptive streams from quietly growing; and a clip MLB sends only as a stream stopped for good at its first playback hiccup. After S251 there is no Download button, and Direct link still opens MLB's own file, as before; the library has its own size limit that the checks enforce, and a stream-only clip gets one more try before it gives up.

    - adds a stand-in hls.js chunk to its stand-in tree;

    The grader builds to a temporary folder as `verify-S110.sh` does. If no single glob can match the default chunk name without `web/vite.config.ts` naming the chunk, the story stops and reports (rule 10): `web/vite.config.ts` is outside the fence.
7. **An HLS-only clip gets one more try (#501).** When hls.js fails on a clip with no MP4 quality, `VideoPlayer` tries once more from the same moment before giving up:
    - for a fatal media error, hls.js's own `recoverMediaError()` once;
    - for a fatal network error, or a chunk that wouldn't load, one new attempt (`loadHls` again and a new player);
    - at most one retry per clip opening.

    If the retry fails too, the player ends as it does today: paused, HLS out of the picker, no reload to resume, and no element or text added. A clip with an MP4 keeps today's behaviour: it switches to the MP4 at the first failure with no retry. RTL tests in `VideoPlayer.test.tsx`, with `loadHls` mocked as `PlayerActions.test.tsx` does, cover:
    - an HLS-only clip whose first chunk load is refused and whose second succeeds plays on from the same time;
    - a fatal media error calls `recoverMediaError` once, and a second fatal error gives up with no third attempt;
    - both attempts failing leaves the player paused with no added text;
    - a clip with an MP4 falls back to it with `loadHls` called once.
8. **The comments are true.** `clipClock`'s doc comment names `clipDuration` (the video badge) as what prints through it. It no longer names the player's elapsed / total time (S70), which B579 removed (#600). `clipClock` stays exported, because its own tests pin the edge cases `clipDuration` can't reach (fractions, `NaN`, negatives).
