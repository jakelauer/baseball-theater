**Gap:** B532 turned on Smart Placement for the staging and production Workers (`wrangler.jsonc`: `"placement": { "mode": "smart" }`), which moves only the fetch handler near Neon (us-east-2). Cloudflare's documentation says cron runs and Durable Objects don't move with it, and both talk to Postgres: the per-game ingest Durable Objects (ADR-020; `functions/src/game-ingest-object.ts`, made with `namespace.get(namespace.idFromName(…))` and no location hint) and the per-minute cron (S194's month refresh, S212's 7-day re-check). Staging measured about 70 ms a round trip from far away (B532), so live ingest (pitch to screen) and the cron's budget may still pay it on every query. Enhancement #538, filed from B532 by its worker, suggested measuring after B532 deploys and then trying a Durable Object `locationHint` near us-east-2 or a placement hint; the owner, asked in `/pending` (2026-11-25) *"Which of these four enhancements should become stories?"*, chose *"All four (Recommended)"*.

**Impact:** Before S220, nobody knew how long the live game updaters and the minute-by-minute jobs wait on the database, and they may run far from it. S220 impact: BT logs how long they wait, and staging places the live game updaters near the database, so the numbers show whether production should follow.

**Source:** Feature: Robust core

**Baseline:** Every database scope of a game's ingest Durable Object (its alarm and calls, kind `ingest`), a game hub's call (`hub`), a day hub's call or alarm (`day-hub`) and each job of the per-minute cron (`cron`, `job` `ingest-start`, `month-refresh`, `game-recheck` or `edge-purge-retry`) logs one structured line, `event: "db-round-trips"`, with its round trips and their total and largest ms, counted by one wrapper on the connection (`countRoundTrips`, applied by `withDatabase` and `setNodeDatabase` in `functions/src/adapters/postgres/connect.ts`; the label is `inDatabaseScope`'s `ScopeLabel`); a request's scope logs nothing. Both callers that reach an ingest object (the cron's `ensureGameIngest`, the hubs' `ingestLease`) get it through `gameIngestStub` (`functions/src/game-ingest-object.ts`), which passes `{ locationHint }` from `BT_INGEST_LOCATION_HINT` only when set: `wrangler.jsonc` sets it to `enam` in staging's vars and adds `placement.hint` `aws:us-east-2` to staging's Smart Placement; production and previews carry neither. ADR-020's 2026-11-25 note says how to read the lines (`wrangler tail` or Workers Logs, by `kind`) and that production takes the hints only by a later change the owner approves.

**Acceptance criteria** (checks `scripts/verify-S220.sh` performs)

1. **Round trips are measured where they happen.** Each database scope of an ingest Durable Object cycle (one alarm or fetch that reads or writes Postgres) and of a cron tick logs one structured line with its kind and the number of database round trips it made and their total and largest time in milliseconds, through one counting wrapper around the connection (`inDatabaseScope`, `functions/src/adapters/postgres/connect.ts`), not per-call timers. A cron tick opens one `inDatabaseScope` per job in its own `waitUntil` (`functions/src/worker.ts:60-63` at HEAD: ingest start-up, the month refresh, the 7-day re-check, owed purges), so it logs one line per job, kind `cron` with the job named, not one per tick. The hub objects that read Postgres inside `inDatabaseScope` (`game-hub-object.ts`; S149's `day-hub-object.ts`, which re-reads its day on every renewal and push) log the same way with their own kinds (`hub`, `day-hub`), since they pay the same distance; a request's scope (`fetch`) passes no kind and logs nothing, so ordinary traffic adds no lines. Tests: a scope against PGlite making a known number of queries logs that count and a non-negative total; a scope making none logs zero; a scope with no kind logs nothing; a workerd test (`*.workerd.test.ts`) shows the line is written from the ingest Durable Object and from `scheduled()`.
2. **Staging places the ingest objects near the database; production doesn't, yet.** The ingest Durable Objects are got with a `locationHint` read from a Worker var (`BT_INGEST_LOCATION_HINT`, its value `enam`, the hint nearest us-east-2, per Cloudflare's list) set in `wrangler.jsonc`'s staging `vars` only; with no var the call passes no hint, as today. A hint takes effect only on the call that creates the object, and at HEAD two places get an ingest object (`ensureGameIngest`, `functions/src/game-ingest-object.ts:105`, and the hubs' lease, `ingestLease`, `functions/src/game-hub-object.ts:49`, which S149's day hub uses too), so whichever runs first would decide its place: both get it through one function that passes the hint (grep: `GAME_INGEST`'s `idFromName` is called in one place outside tests). A unit test shows the hint is passed when the var is set and not when it isn't, from both callers; the grader checks `wrangler.jsonc` sets the var for staging and not for production. If the Wrangler version in use supports a placement hint for the cron (`placement.hint`), staging sets it to a us-east-2 value too, with the same check; if not, the commit body says so.
3. **The comparison is recorded.** `docs/v3/ARCHITECTURE.md` gains a dated note under ADR-020 stating what is measured, where the log lines are read (`wrangler tail` or Workers Logs, by `kind`), that staging carries the hint and production not, and that production takes the hint only through a later change the owner approves once staging's numbers show it helps.
