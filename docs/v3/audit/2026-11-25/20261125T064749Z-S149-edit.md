**Gap:** Only a game page has a live connection: each in-window game's ingest object (`functions/src/game-ingest-object.ts`) writes Postgres, then publishes to that game's hub (`functions/src/game-hub-object.ts`), which pushes to viewers over `GET /api/v1/games/:gamePk/live` (S18; ADR-020). The scoreboard re-asks its day on the live cadence instead (`refetchInterval` in `web/src/api/schedule.ts`), so it has no live connection and can't show the Live marker. The owner wants it to have one (owner, 2026-11-16, told the polling scoreboard showed no Live marker: *"the scoreboard should have a live connection"*), opened only on a day with a game in its live window, the window game pages use, from 2 hours before first pitch to 3 hours after the game ends (`DEFAULT_CADENCE`, `packages/domain/src/window.ts`) (asked when, with that rule as the option's description: *"While a game is live"*), as one WebSocket per day from a hub per day (asked whether one socket per day or one per live game: *"One socket per day"*). ADR-020's amendment of 2026-11-16 records it.

**Impact:** Before S149, the scoreboard caught up with live scores every few seconds by asking again. S149 impact: while a game on that day is live, scores arrive on the scoreboard the moment BT has them, over one connection, and the scoreboard can say it is live.

**Source:** Feature: Live marker

**Baseline:** **S149** landed: the scoreboard has a live connection. `GET /api/v1/schedule/live?date=` (a second named streaming exception, its refusals `no-store` so the edge never keeps a "not live" answer) upgrades a day with a game in its live window, judged at request time by `scheduleDayWindowMode`, to the `day-hub:<date>` Durable Object (`DayHubObject` in `functions/src/day-hub-object.ts`; `DAY_HUB` bound at the top level and in every env, migration `v3`), which holds the day's viewers over hibernated one-way WebSockets on the generic `LiveHubState` and pushes the whole served day (S150's read-only `readScheduleDay`, never a write or an MLB fetch), newer versions only. While it has viewers it leases every in-window game of its date with that game's ingest object (`HubLeases`, re-read each renewal, so a night game joins and an ended one is let go); the ingest object publishes to it after each write and, new, after a mend (`ingestGame`'s `stateChanged`), `hubPublisher` routing `day-hub:` ids through `DAY_HUB`; and every schedule write (`storeSchedule`'s callers and the day read's refresh) calls the hub of each changed date with a game in its window before or after the write, once per refresh or fill (`DayHubCalls`, `IngestDeps.dayHubs`, absent on the Node server). The client's `useLiveDay` (`web/src/api/live-day.ts`) judges the cached day with `scheduleWindowMode` each minute and streams it through `LiveDayStream` on the game stream generalized as `LiveStream` (any newer day applied at once; a game still refetches on a gap); `useScheduleDay(date, streaming)` stops re-asking an in-window day, and the scoreboard's footer opens with S148's Live strip while the socket is open.

2. **Which games feed it.** A day hub registers a lease (`functions/src/services/hub-leases.ts`, generalized as needed) with the ingest object of every game on its date that is in its live window when its first viewer connects. On each lease renewal it re-reads the day, so a game that enters its window later (a night game, a doubleheader's second game) is registered then and a game whose window has ended is let go; it unregisters from all of them when its last viewer leaves. A day's schedule changes reach its hub too: when any write through `storeSchedule` (`functions/src/services/ingest.ts`) changes a stored day (its two calls in `ingest.ts`, the month fill in `functions/src/services/schedule-month.ts` whether the month route or S194's six-hourly refresh runs it, and backfill's day writes in `functions/src/services/backfill.ts`: the four call sites at `709864e1`, and any added later), or a schedule write's call to S150's switch (`switchGameState`, `functions/src/services/game-state.ts`) changes a game's state, the writer calls the hub of each date that changed (for a game's state, the date being written and the game's `game_states` official date before and after the write, when they differ), once per refresh or fill after its writes rather than once per game, and only for a date whose day has a game in its live window before or after the write (`scheduleDayWindowMode`, AC 5's rule), since no other day can have a socket open (so backfill's past days and a month fill's far days make no call); the hub pushes the day if it has viewers and otherwise ignores the call (on the local Node server, which has no hubs, the call is skipped), so a postponement or a new probable pitcher arrives while the socket is open and the scoreboard isn't polling. Each game's ingest object, after it writes a game, publishes that game (the `GameSnapshot` it already publishes) to every registered hub, game or day, as it does today for game hubs, and does the same after a feed write whose switch changes the game's row while its snapshot is unchanged (a mend, which ingest doesn't publish today); a day hub does what AC 3 says with it. So every day that lists a game in its window, a suspended game's original day included (its hub registered with the game's ingest object when its viewer connected), learns of the game's state through its lease, and no writer looks up which stored days list a game: nothing queries `schedule_days` documents by gamePk (the table is keyed by date alone, with no index into its document, `functions/src/adapters/postgres/schema.ts`). Unit tests: a game in its window at connect reaches the day hub; a game that enters its window after the hub registered reaches it after the next renewal; a game of another date never does; a doubleheader's two games both do; a schedule refresh that changes the day (a postponement) reaches the hub with no game update; so does a month fill (`schedule-month.ts`) that changes an in-window day; a fill or backfill that changes only days with no game in its window calls no hub; a feed mend that changes a game's row but not its snapshot reaches a registered day hub; a schedule write that changes a game's state calls only the hubs of the dates this AC names. A late game on the evening's MLB date is refreshed after midnight UTC only once issue #73 is fixed, which S149 depends on.
3. **The day hub only reads.** When a game's update reaches it (after the game's ingest has written the game and its shared state, S150), the day hub reads its day with S150's read-only `readScheduleDay` (the stored day joined to its games' states, never refreshed from MLB) and pushes that whole day, the shape `GET /api/v1/schedule?date=` serves, the `ScheduleDayResponse` shape, so every push is the whole day and a missed one is healed by the next. It writes nothing to Postgres and fetches nothing from MLB; which source feeds a game's score is S150's switch alone. On a viewer's first connect it sends the same read. Unit tests: a game's new score is in the next push; two games of the date updated together are both in the pushes that follow; a read that fails pushes nothing.
4. **Versioned (ADR-022).** A push's version is the served day's version (S150 AC 6: the stored day's served version, which only rises), and the client applies a push through `applyIfNewer` (`packages/domain/src/versioning.ts`), like a game's, so a duplicate or an older push changes nothing. A day push is the whole day, so the day stream applies any newer version at once, however far ahead (a game's stream keeps its rule of refetching on a gap, since a game push is too). Unit test: a push five versions ahead is applied with no refetch. A reconnect passes its last version (`?since=<version>`) and gets the full day if it is behind. Unit tests: a duplicate, an older and a newer push, client and hub sides.
5. **The route.** `GET /api/v1/schedule/live?date=<YYYY-MM-DD>` (a query parameter, like its sibling `GET /api/v1/schedule?date=`) upgrades to the day hub's WebSocket only while the day has a game in its live window, worked out at request time from the day's games and the clock with `scheduleDayWindowMode` (`functions/src/services/game-state.ts`), the function every stored and served day's `windowMode` comes from since S150: it runs the domain's `scheduleWindowMode` (`packages/domain/src/window.ts`, which applies `isGameInActiveWindow` to each game) over the day's games with each suspended game's `suspendedAt` added (#323) (ADR-025: one implementation of "the day has a game in its window"). It is not read from the stored `windowMode`. The day is read through the existing day read (as `GET /api/v1/schedule?date=` reads it, fetching a day BT doesn't hold yet; the socket's own pushes then use the read-only `readScheduleDay`, AC 3), and a day with no games answers as an out-of-window day, not as an error; otherwise it answers as `GET /api/v1/games/:gamePk/live` does for a game out of its window. **Notes:**

- **Why a day hub, not one socket per live game.** The owner chose one socket per day (2026-11-16). A busy day has about 15 live games, which would have been 15 sockets per scoreboard viewer, each pushing a whole game when the scoreboard needs only its row.
- **Before first pitch and after the last out** the scoreboard is connected, and shows the marker, for as long as a game on its day is in its live window (2 hours before first pitch to 3 hours after the game), the rule the owner chose.
- **The day of a game** is its official date in the schedule (`officialDate`), the date the scoreboard lists it under, so a game that runs past midnight stays on its day's hub.
- **The scoreboard's own judgement (AC 6) has no `suspendedAt`**, which the wire doesn't carry, so it uses `scheduleWindowMode` on the cached games alone. In the one case the two differ (a game suspended late, held in its window by `suspendedAt` after its first-pitch window has closed), the served day is still `active` and the scoreboard keeps polling it, with no socket and no marker; accepted, since it is rare and the scores still arrive.
- **Hide Scores** is unchanged: the pushed day is the same payload the HTTP route serves, and the scoreboard masks it as it masks a fetched one.
- **2026-11-24 backlog review: every writer of a stored day.** AC 2 named only "the cron's refresh", but stored days are written through `storeSchedule` from four call sites (two in `ingest.ts`, the month fill in `schedule-month.ts`, and backfill), and S194 (in flight, p68.5) adds a six-hourly refresh of this year's and next year's months through that same month fill. As written, a postponement the six-hourly refresh or a fan's calendar read found would change today's stored day without reaching an open scoreboard, which would keep showing the game as scheduled. AC 2 now names every `storeSchedule` write and calls a hub only for a day with a game in its live window before or after the write, so backfill's past days cost no Durable Object calls. The turn cap stays 20.
- **2026-11-24 (second) backlog review, after S150 shipped.** Two fixes against S150's code at `3eb722b7`. (1) AC 2 said a game's state change calls the hub of "every date whose stored day lists the game (a suspended game's two days)", but BT has no way to find those days but reading every stored day's document (`schedule_days` is keyed by date, no index into its JSONB), which a live game's every poll would run. Leases already reach every day hub watching a game, so the ingest object now publishes a mend to its registered hubs, and a schedule write calls only the dates it knows (the one it writes, the game's official date before and after). (2) AC 2 and AC 5 named `scheduleWindowMode`, but since S150 every stored and served day's `windowMode` comes from `scheduleDayWindowMode`, which adds a suspended game's `suspendedAt` (#323). Breaking case: a game with first pitch 19:05 suspended at 23:50 is in its window until 05:50 by `suspendedAt` but only until 01:05 by the clock alone, so between them the served day says `active` while the route refuses to upgrade. Both now use `scheduleDayWindowMode`. The Goal condition now matches the `/goal` line's exception for creating `scripts/verify-S149.sh`. The turn cap stays 20.
