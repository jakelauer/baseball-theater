**Gap:** MLB names a player of the game, with a stat summary and the win probability he added; BT doesn't keep it (owner, 2026-10-30: *"Also add stories to ingest all of this extra data."*).

**Impact:** Before S99, BT didn't know MLB's player of the game. S99 impact: BT keeps MLB's pick for each finished game — who, his line, and how much he swung the game — ready for a view to show.

**Source:** Feature: More MLB game data

**Baseline:** BT ingests MLB's player of the game (`www.mlb.com/apps/player-of-the-game/game/json/winners/{gamePk}.json`, `playerOfTheGameUrl`, recorded as `fixtures/raw/potg-823823.json` and bundled for `pnpm dev`): `parsePlayerOfTheGameResponse` (`packages/mlb-api/src/player-of-the-game.ts`), `MlbStatsClient.fetchPlayerOfTheGame` in the HTTP and fixture adapters, and `mapPlayerOfTheGame` project it onto the game payload as the optional `GameSnapshot.playerOfTheGame` (`media` / `fan` picks: `playerId`, `teamId`, `summary`, `winProbabilityAdded`; 823823's media pick is Ryan Zeferjahn, 666171, 40.7). The HTTP `fetchGame` asks it only for a game `playerOfTheGameExpected` (`packages/domain/src/player-of-the-game.ts`) says has one (final, game type R/F/D/L/W, season 2024 on), so a live poll never asks it, and under S216's `PLAY_METRICS_LIMIT_MS`, so a slow or hanging answer leaves the field off rather than holding the read. No view shows it yet.

**Fence widened to `web/src/api/generated/` (2026-11-02 backlog review, after S94's rule 10 stop at `3e3a4a2`).** A field added to the game payload regenerates `openapi/bt-api.v1.json`, and ADR-016's drift gate (`web/src/api/codegen.test.ts`, in `pnpm verify`) then fails until `web/src/api/generated/bt-api.v1.ts` is re-rendered from it (`pnpm api:types`). S93's identical change edited that file (`7e2e080`). Only the generated directory joins the fence: the field is optional, so no web code or test literal has to change; anything else under `web/src/` is still a rule 10 stop.

- **A new extra must not slow a game fetch or add a request to every poll (2026-11-25 backlog review, after S216).** Since S216, `HttpMlbStatsClient.fetchGame` (`functions/src/adapters/http/mlb.ts`) fetches the live feed, then its extras at once, and answers a cold read without the play metrics once they pass `PLAY_METRICS_LIMIT_MS` (750 ms, S216 AC 5; `functions/src/services/ingest.play-metrics.test.ts`). Joined to that `Promise.all` unbounded, a slow or hanging player-of-the-game request would hold every game read until it answered, and each live poll would call it again for a value that exists only once the game is final (and only for the game types and years the note above names). So the call either runs off that path or under the same limit, and AC 5's test adds: a player-of-the-game request that never resolves leaves `fetchGame` answering within `PLAY_METRICS_LIMIT_MS` with the field absent (review-class checklist items 3 and 7, partly present data and upstream request budget). The HTTP adapter already reaches one host besides statsapi by an absolute URL (`playMetricsUrl`, bdfed.stitch.mlbinfra.com), the precedent for mlb.com's feed.
