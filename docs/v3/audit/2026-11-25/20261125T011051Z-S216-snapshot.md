**Gap:** A cold read writes to Postgres, then reads its own write back, before it answers. Measured 2026-11-24 (`.run/reports/latency-1124.md`, a probe of the real Worker app on PGlite with MLB's recorded answers for 2021-06-15 replayed, every query counted and run one at a time as one `pg` `Client` does on Workers): a cold 15-game digest (`GET /api/v1/digest`, `getDayDigest`, `functions/src/services/digest.ts:17-18`) makes **112** database round trips, all serialized on the request's one connection. **48** of them are read-backs or repeat reads: `getOrRefreshGame` reads the ~380 KB snapshot it just wrote back through `readServedGame` (`functions/src/services/ingest.ts:371`, 2 per game), `storeGame` re-reads the snapshot `getOrRefreshGame` read a moment earlier (`ingest.ts:107`, repeating `:351`), and `storeSchedule` re-reads the stored day it already holds (`ingest.ts:155`, repeating `:325`) and then reads the whole joined day back (`ingest.ts:158`). **32** are writes awaited before the response (the state switch, `games.upsert`, `projections.upsert`, `schedules.upsert`: 12 MB uploaded for a 6.8 KB answer), and **32** are per-game reads (15 `games.getByPk`, 15 single-row `gameStates.getMany`, …) that one `IN (…)` query each could replace; `Promise.all` at `digest.ts:18` adds no database parallelism. A cold game makes 8 (3 of them read-backs or repeats), a cold day 7 (3). Everything the answer needs is already in memory after the write: `storeGame` holds the stamped snapshot and the switch's outcome row (`storedAfter`, `game-state.ts:101-116`), and `servedGame(snapshot, row)` and `joinScheduleDay` are pure. At staging's ~70 ms a round trip (its Worker in Seattle, Neon in us-east-2; B532 places it), that is ≈ 7.8 s of a cold digest's ~9 s (staging measured 8.4–12.3 s), and even with Smart Placement the round trips stay the largest cost the code controls. A cold game also waits on MLB's playMetrics, the slowest of its four calls (0.71–0.78 s, `fetchPlayMetrics`, `functions/src/adapters/http/mlb.ts:302,428`). The owner, 2026-11-24, first: *"Perhaps we're storing stuff in our DB, then fetching it, before returning it (as opposed to forming the data to be stored and returning it while we store it)?"*; then, asked whether to fix it as one story right after S212 ("answer from the data already built, batch the per-game reads, and do the writes after the response"), chose *"Yes, story after S212 (Recommended)"*.

**Impact:** Before S216, opening a day's best clips, a game or a day that BT hadn't stored yet made the server save everything and then read it all back before answering, one step at a time, which could take nine seconds or more. S216 impact: BT answers from what it just fetched, reads many games in one step, and saves in the background after answering, so those first views open several seconds sooner.

**Baseline:** An on-read refresh answers from the data it formed: `getOrRefreshGame`, `getScheduleRead` and the digest (`readDayAndGames`, `functions/src/services/ingest.ts`) serve `servedGame` of the snapshot they stamped over the row the switch stored, and the day `joinStoredScheduleDay` forms from the day, the served base the `schedules` upsert reports (`Promise<number | null>`) and the switch's rows, never reading back what they wrote; a refused write is reported and only then read. A day's games are read in one `games.getMany` and stored in one `games.upsertMany` / `projections.upsertMany` (new on both adapters, under the repository contract); the state row and snapshot stay awaited, while the projections, the request's one `purgeGameEdge` and a late playMetrics write (`PLAY_METRICS_LIMIT_MS` = 750 in `functions/src/adapters/http/mlb.ts`, `FetchedGame.playMetricsLate`) run after the response through the new `BackgroundWork` port (`packages/ports/src/background-work.ts`; Worker: `ScopedBackgroundWork` drained in `inDatabaseScope` under `ctx.waitUntil`; Node: `NodeBackgroundWork`). Counted on a 15-game past day: cold digest 144 → 6 round trips before its answer, 8 in all; cold game 9 → 4 / 6; cold day 24 → 4 / 5; stored digest 32 → 3.

The served base the formed day carries is the one the `schedules` upsert stored, not the one read before it: the upsert raises `served_base` when the refreshed day drops a game the stored day listed (`ScheduleRepository.upsert`'s comment), so the upsert reports the base it stored (its `RETURNING` or result), and a test refreshes a stored day whose new listing drops one game and gets the same version a fresh read returns. Tests: a cold game read, a cold day read and a cold digest each make **no** read of a row or snapshot the same request wrote, and no second read of a key the request already read (the double fails the test on either); each answer equals, field for field, what a fresh read of the stored data after the deferred writes flush returns (the same `servedGame` / `joinScheduleDay`, ADR-025). **The answer never carries a version the store hasn't accepted** (ADR-022: a client applies only a newer version, so a version it holds must be one the store holds). The writes that carry the answer's version, the state switch's row write, the snapshot upsert (`games`, or `schedules` for a day), stay **awaited** before the answer, version-guarded and batched (AC 2); only writes that carry no version of the answer are deferred (AC 3). When an awaited version-guarded upsert is refused because another writer stored that version or a newer one first, the write reports it (`RETURNING` or the repository's result) and only then is the stored row read back and answered, so the answer is the stored one. A test seeds a different stored version between the read and the write and gets the stored one, version and content; the no-read-back test above covers only the accepted awaited write.
2. **One batched read per day.** `GameRepository` gains `getMany(gamePks)` (both adapters, held to the repository contract, `functions/src/adapters/repository-contract.ts`), and the digest and day paths read every game's snapshot in one call and every game's state row in one `gameStates.getMany` call, not one per game. Multi-row upserts for games and projections write a day's games in one call each, and a multi-row version-guarded upsert reports, per key, which rows a newer stored version refused (AC 1's refused-write rule applies row by row). Tests: a cold 15-game digest makes exactly one `games.getMany` and one `gameStates.getMany` for its games (not 15 of either), and the contract test reads 0, 1 and 15 keys, missing keys left out.
3. **Writes that don't change the answer run after it.** A new port, `BackgroundWork` (`packages/ports/src/`), takes a promise to finish after the response: the Worker's adapter hands it to `ctx.waitUntil` (`functions/src/worker.ts`, inside the same `inDatabaseScope` so the connection stays open until the deferred writes settle), the Node server's (`functions/src/local-server.ts`) runs it and logs a failure, and the test double records it for a test to flush. Only a `cache`-window refresh made on read defers writes, and only writes that carry no version of the answer (AC 1): the projection upsert (`projections`), AC 5's playMetrics follow-up write, and S212's edge purges; the state row and the snapshot stay awaited. A request's purges are gathered into **one** deferred `purgeGameEdge` call (`functions/src/services/edge-purge.ts`: one `listGameListings` read and one purge request for every game and day the request stored), not one per `storeGame`, and the past-and-finished judgement that decides them (`storeGame`'s at `ingest.ts:142-146`, `storeSchedule`'s `wasPastFinishedDay` and `pastFinishedChangedGames` at `ingest.ts:205-244`) reads the snapshots and rows the request already holds, and reads only what it doesn't (a day read holds no game snapshots, so at most one deferred `games.getMany` for the games whose state it changed), never one read per game; the hand-written date and settledness pre-filters there (`ingest.ts:207-212`, `:233-238`), which exist only to skip those reads, go with them, so the judgement is `isPastFinishedGame` / `isPastFinishedDay` alone (ADR-025). On a path that defers nothing (the cron, game ingest, the recent-game re-check) the purge stays awaited after its write, as S212 shipped it. A deferred version-guarded write that a newer stored version refuses is logged and dropped, never written over the newer one, except AC 5's playMetrics follow-up, which retries once as AC 5 says; an active game's writes stay with the game-ingest object, which still writes Postgres before it publishes to the hub (ADR-020), and nothing in `functions/src/services/game-ingest.ts`'s write-then-publish order changes. The awaited writes keep the state row before the snapshot (S150's order, `ingest.ts:110-139`), versions are stamped before the write (ADR-022), and S212's edge purge runs after the write it follows, never before. Tests: before the flush the answer is complete, its state row and snapshot are already stored with the version it carries, and no projection write has run; after the flush the projection is stored; a deferred write refused by a newer stored version is logged and leaves the newer one; a deferred write that fails is logged and never fails the answered request; a game-ingest test asserts the store write still precedes the hub publish.

A cold game makes at most **4** before its answer and **6** in all (from 8: its `projections` upsert and its purge's `listGameListings` read are deferred); a cold day at most **4** and **5** (from 7: the purge's one `games.getMany`; with no game stored it purges only the day's URLs, which reads nothing); a stored, fresh digest at most **4** (from 32). 5. **playMetrics can't hold a cold game's answer.** `fetchGame` gives the playMetrics request a time limit of 0.75 s (one named constant in `functions/src/adapters/http/mlb.ts`, its comment giving the value and why: the probe's 0.71–0.78 s, the slowest of a game's four calls). When it runs out, the answer is built without playMetrics, as when the request fails today (`fetchPlayMetrics` answers null), and the same request keeps running in the deferred work (AC 3), whose write stores the game with playMetrics when it arrives (a new version, ADR-022). If a newer stored version refuses that write, the follow-up retries **once**: it reads the newer stored snapshot and, when it still lacks playMetrics, writes it with them as the next version; a second refusal is logged and dropped. So a past game is not left stored without playMetrics because of the limit unless two newer writes land during the follow-up. Because the answer without playMetrics may be a past, finished game's and so get S212's long edge lifetime, that follow-up write, once stored, asks S212's purge port (`EdgeCachePurger`) for the game's URL and its day's schedule and digest URLs, after the write. Tests with a fake MLB whose playMetrics answers after 2 s on fake timers: the game answers within the limit with no playMetrics; after the flush the stored game has them and the memory purger was asked for exactly the game's URL and its day's schedule and digest URLs, after the write; a playMetrics answer inside the limit is in the answer and purges nothing; a follow-up refused once by a newer stored version (seeded during the flush) retries over it and stores the newer content with playMetrics, and a second refusal is logged and leaves the stored game alone.
