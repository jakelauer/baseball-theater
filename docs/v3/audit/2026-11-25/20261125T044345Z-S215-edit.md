**Gap:** Nobody can try a patron's view of BT before a release. A signed-in account's tier comes from its stored `entitlements` row (`UserProfile.entitlements`, built by `entitlementsForTier` in `packages/domain/src/entitlements.ts`), which is `none` for every new account (`signIn`, `functions/src/services/accounts.ts`), and no Patreon link exists yet to change it. Staging signs everyone in as one shared test account (S143, `mockSignInAllowed` in `functions/src/worker-app.ts`), so on `stage.baseball.theater` every tier-gated feature (S211's stats sites, the paid tier of S91 and S190, the AI outputs of S178) can only ever be seen as a non-patron. The session copies the entitlements at sign-in (`BtSession.entitlements`), `GET /api/v1/me` answers them (`toMeResponse`, `packages/domain/src/api-routes.ts`), and the web bundle is the same file on staging and production (no per-environment build variable), so a staging-only control has to be switched on by the server. The owner, 2026-11-24: *"Stage needs a special stage-only feature which allows the user to select their backer tier, for testing purposes. This functionality must not be available or visible in production."*

**Impact:** Before S215, the test site could only show BT as someone with no Patreon pledge, so nothing meant for patrons could be checked before it reached fans. S215 impact: on the test site, a signed-in tester picks any backer tier (or none, or their real one) in Settings and sees BT exactly as that patron would; on the real site the choice doesn't exist at all.

**Source:** Feature: Modern membership

**Baseline:** On staging a signed-in tester can now choose the backer tier BT treats them as, and production refuses it on the server. `effectiveEntitlements` (`packages/domain/src/entitlements.ts`) is the one rule for the entitlements a session and `GET /api/v1/me` hand out (`accountEntitlements`, `functions/src/services/accounts.ts`): the chosen tier where `tierOverrideAllowed` (`functions/src/worker-app.ts`: `BT_TIER_OVERRIDE` `"1"`, set in `wrangler.jsonc`'s `env.staging` only, and the mock sign-in wired) and the stored tier elsewhere, where the override is never read. The override lives behind `UserRepository.getTierOverride`/`setTierOverride` in its own `tier_overrides` table (migration `0005_tier_overrides`, personal under `BT database: users`, in the download and deletion), never the `entitlements` row or Patreon. `GET`/`PUT /api/v1/me/tier-override` answer `no-store`, 404 off staging, and `PUT` answers a new session token; Settings' Account frame shows the plain "Testing only (staging): backer tier override" radio group (`web/src/pages/settings/TierOverrideControl.tsx`, `useTierOverride` in `web/src/api/tierOverride.ts`) only on a 200, keeping the new session through the session's `keepSession`.

**Acceptance criteria** (checks `scripts/verify-S215.sh` performs)

1. **One rule for the effective tier** (ADR-025). One named, tested function in `packages/domain/src/entitlements.ts`, `effectiveEntitlements(real: Entitlements, override: PatronTier | null, overrideAllowed: boolean): Entitlements`, answers `entitlementsForTier(override)` when `overrideAllowed` is true and `override` is not null, and `real` otherwise. Every place that hands out entitlements calls it and nothing else: the session issued at sign-in (`signIn`), `GET /api/v1/me` (`toMeResponse`'s caller) and the override route's answer (AC 4). Where `tierOverrideAllowed` (AC 2) is false the stored override is never read: `signIn` and `GET /api/v1/me`, which every app load asks, make no `getTierOverride` call in production (a test with a spying user repository under production's config asserts zero calls), so the testing control costs production no query. Unit tests: each of the five tiers `PatronTier` defines (`none`, `Backer`, `Pro Backer`, `Star Backer`, `Premium Sponsor`) as an override when allowed gives exactly `entitlementsForTier` of it; a null override gives `real`; any override when not allowed gives `real`. The grader checks that `packages/domain/src/entitlements.ts` exports the function and that no file under `functions/src/` or `web/src/` calls `entitlementsForTier` except the new-account default in `accounts.ts`, tests (`*.test.ts(x)`) and the shared adapter contracts (`*-contract.ts`, e.g. `functions/src/adapters/repository-contract.ts` and `storage-contract.ts`, which build fixture users with it).
2. **Switched on by deploy-time config only.** One function, `tierOverrideAllowed(env: WorkerEnv): boolean`, beside `mockSignInAllowed` in `functions/src/worker-app.ts`, is true only where the env's vars set `BT_TIER_OVERRIDE` to `"1"` **and** `mockSignInAllowed(env)` is true (so an env naming a Logto tenant, which production does, never honours it even if the var were copied there). `wrangler.jsonc` sets `BT_TIER_OVERRIDE: "1"` in `env.staging`'s `vars` and nowhere else (the grader parses `wrangler.jsonc` and checks `env.production`, `env.preview` and the top level lack it). No request header, query string, cookie, body field or client flag can switch it on; the local Node server (`functions/src/local-server.ts`) leaves it off, so a test proves it there with a fake env. Unit tests: staging's vars → true; production's vars (Logto set) with `BT_TIER_OVERRIDE: "1"` added → false; preview's vars → false; staging's vars without the var → false.
3. **Stored per user, server-side, apart from the real tier.** The override is one nullable `PatronTier` per BT user ID behind the user repository port (`packages/ports/src/auth.ts`: `getTierOverride(uid)`, `setTierOverride(uid, tier | null)`), with memory and Postgres adapters held to the repository contract (`functions/src/adapters/repository-contract.ts`), in a new table from a new migration (not a column of `entitlements`). Setting it never writes the `entitlements` row (`setEntitlements` is not called; a contract test sets an override and reads the real tier back unchanged) and never calls Patreon (no Patreon client is wired to it). The table's `uid` references `users.uid`. It is personal data under ADR-028's existing **BT database: users** row (its **What** lists entitlements; the override is the tester's chosen entitlement tier), so no new inventory row: it is labelled in the data classification manifest (`functions/src/services/data-classification.ts`, whose test fails on an unlabelled table) as `{ kind: "personal", deletedBy: USERS_STORE }`, and the user repository's `exportFor` includes it and its `deleteFor` removes it (`USERS_STORE` in `functions/src/services/personal-data.ts`, whose registry export and deletion walk); the repository contract's export and deletion cases assert both with an override set.
4. **The route, 404 off staging.** `GET /api/v1/me/tier-override` answers `{ "tier": PatronTier | null, "realTier": PatronTier }` and `PUT /api/v1/me/tier-override` takes `{ "tier": PatronTier | null }` (`null` means "use my real Patreon tier"; `"none"` means "not a patron"), stores it and answers the same shape plus a newly issued session token (`SignInResponse`'s `token`), whose entitlements come from AC 1, so the session and every server check that reads it use the chosen tier at once. Both are signed-in only (401 otherwise, as `GET /api/v1/me`), a tier that isn't a `PatronTier` is 400 `invalid_tier`, and both are in the route table, the OpenAPI spec (`openapi/`) and the generated web types, additive (`pnpm api:breaking` exits 0). Where `tierOverrideAllowed` is false both answer **404** exactly as an unknown route does. Both answers carry `Cache-Control: no-store` (a signed-in, per-user answer, never kept by the edge cache S212 relies on). Tests run the real Worker (`*.workerd.test.ts`, `functions/vitest.workers.config.ts`) under each config:
    - production's config: `GET` and `PUT` → 404; a user with a stored override row (seeded straight into the repository) → `GET /api/v1/me` answers their real tier's entitlements, and a fresh sign-in's session carries the real tier;
    - staging's config: `PUT { "tier": "Star Backer" }` → 200; `GET /api/v1/me` then answers `entitlementsForTier("Star Backer")`, and the returned token's session (verified) carries the same; `PUT { "tier": null }` → back to the real tier; `PUT { "tier": "Gold" }` → 400;
    - preview's config: 404.
5. **The Settings control, staging only, labelled as a test.** On the Settings page (`web/src/pages/SettingsPage.tsx`), a signed-in user sees a plain control built from Mantine's existing components (no new styling, no design: the owner's exemption above) offering "Use my real Patreon tier", "Not a patron" and each of the four backer tiers, under a visible label reading "Testing only (staging): backer tier override", which says it changes only what this test site shows and never the real tier or Patreon. The page asks `GET /api/v1/me/tier-override` through one named query hook (`web/src/api/`) and renders the control **only** on a 200 answer: on 404, on a failed request and while loading it renders nothing and leaves no empty space. Choosing a tier sends `PUT`, keeps the returned session (the session provider's existing keep path) and refetches `GET /api/v1/me`, so every client check that reads `me.entitlements` sees the chosen tier. RTL tests: a 200 answer shows the control with the current choice selected; a 404 renders no control and no label text (`queryByText` of the testing label is null); choosing "Pro Backer" sends the `PUT` and the page then reads `me.entitlements.tier` as `Pro Backer`; choosing "Use my real Patreon tier" sends `{ "tier": null }`.
