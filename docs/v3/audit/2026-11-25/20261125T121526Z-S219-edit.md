**Gap:** S161's win-probability fill runs in `pnpm db:migrate`, before the Worker deploys, and records the edge purges it owes as paths alone (`/api/v1/…`), since the migrate step doesn't know the app's origin; the Worker's cron sends them under its origin (`retryOwedEdgePurges`, `functions/src/services/edge-purge.ts`: `owed.url.startsWith("/") ? origin + url : url`). A Worker from before S161 doesn't: between the migration and the deploy, or after rolling back to a release from before S161, its cron lists those rows with the full-URL ones (`listDue`, `functions/src/adapters/postgres/repos.ts`: `retry_at IS NULL OR retry_at <= now`, oldest first) and sends them as they are; Cloudflare most likely refuses that batch, and the failure defers the real full-URL owes listed with them (`defer`). After a rollback that repeats every tick until the 30-day give-up. Enhancement #572, raised by S161's database reviewer, suggested storing full URLs, keeping path-only rows out of full-URL batches, or marking them so older code skips them; the owner, asked in `/pending` (2026-11-25) *"Which of these four enhancements should become stories?"*, chose *"All four (Recommended)"*.

**Impact:** Before S219, rolling the site back past S161 could hold up corrections to cached pages, because the old code would send the edge a batch it rejects. S219 impact: older code never sends those entries, and the current code still clears them, so real corrections reach the edge on time.
