**Gap:** BT knows each player only by MLB's id (MLBAM, e.g. `matchup.batter.id`, the box score's person ids). That id opens the player's page on MLB.com and on Baseball Savant, which MLB runs and keys by the same id, but FanGraphs and Baseball-Reference key their player pages by ids of their own, and BT has no way from one to the other: the recorded fixtures carry no cross-reference (`fixtures/raw/people-823823.json` has none). The owner asked (2026-11-23) that *"Patrons should have the ability to choose from the other providers"* when a player's name opens their stats, so BT needs those ids.

**Impact:** Before S209, BT could send a fan only to MLB's own sites for a player's stats. S209 impact: BT knows each player's FanGraphs and Baseball-Reference ids too, and builds the link to the player's page on all four sites, so a player's name can open whichever one the fan prefers.

2. **One function per link** (ADR-025). `packages/domain` exports `StatsProvider` (`"mlb" | "fangraphs" | "bbref" | "savant"`) and `playerProfileUrl(provider, ids)`, which builds the player's page URL from MLBAM for MLB.com and Savant and from the provider's own id for FanGraphs and Baseball-Reference, answering `null` when that id is unknown. 3. **Stored, resolved lazily, and served.** The ids live in one table behind a port (`PlayerIdRepository` in `packages/ports`, a Postgres adapter with one migration and an in-memory double, one contract test on PGlite): `person_id` primary key, `checked_at` (nullable), `fangraphs_id` and `bbref_id` (nullable), with an index on `(checked_at NULLS FIRST)`. They are resolved lazily (ARCHITECTURE §3), never by scanning every game BT holds in one go (S122 backfills every game since 1901, and the cron runs every minute under the Worker's subrequest limit):
    - **Ingest adds players.** On a game's first write, or a write whose roster differs from the stored one (not every live snapshot), ingest inserts the game's players (`INSERT … ON CONFLICT DO NOTHING`, `checked_at` null).
    - **The resolve step.** A step the existing cron runs selects exactly `<cap>` rows (a named constant) `WHERE checked_at IS NULL OR (fangraphs_id IS NULL AND bbref_id IS NULL AND checked_at < now - <interval>)` (the interval a named constant of at least a week) `ORDER BY checked_at NULLS FIRST LIMIT <cap>`, asks the source for them (when MLB is the source: in batches through the batched `people?personIds=…` call, `fetchPlayers` in `functions/src/adapters/http/mlb.ts`, with the hydrate of AC 1, at most ⌈cap / batch size⌉ calls; when the Chadwick register is, from the register as AC 1 reads it, and if one run can't read the whole register to find them, the story stops and reports under rule 10, as AC 1 already allows for memory) and writes what it finds with `checked_at` set; the rest stay `checked_at IS NULL` for the next run. This step keeps no last-run time.
    - **The seeding pass.** Games already stored before this story are seeded by the same cron step, after the resolve step: one SQL statement takes the next page of stored games by keyset, `WHERE (official_date, game_pk) > <cursor> ORDER BY official_date, game_pk LIMIT <seed page>` (`official_date` is indexed; the seed page a named constant counted in games, apart from the resolve cap), pulls only person ids out of each page's stored snapshot in SQL (`jsonb_path_query` over `$.plays[*].matchup.batter.id`, `$.plays[*].matchup.pitcher.id` and the box score's `$.boxscore.teams.*.batting[*].id`, plus `pitching[*].id` where S205 has stored it), inserts them `ON CONFLICT DO NOTHING`, and moves a single-row cursor `(official_date, game_pk)` to the page's last game in the same transaction, so no `games.document` reaches the Worker; an empty page means it is done, and it does nothing after.
    - **Tests:** a game's first write inserts its players once, and a later snapshot with the same roster inserts nothing; with more players waiting than the cap, after run 1 the unresolved count is the number waiting less the cap, with no more than ⌈cap / batch size⌉ calls, and run 2 resolves the rest; a run with nothing waiting makes none; a player with no cross-reference is selected again only after the interval; two seeding runs over more stored games than the seed page seed every player once, a run after completion does nothing, and the seeding query selects no `document` column into the Worker (a test on the SQL it runs).

    `GET /api/v1/players/:personId/profiles` reads that table: it answers the four URLs (`null` for a site whose id is unknown, including a checked player with no cross-reference), and 404 for a person with no row; it is in `ApiRoutes` (law L4) and the OpenAPI spec (additive, `pnpm api:breaking` exits 0, `web/src/api/generated/` regenerated). An answer from a checked row is cacheable at the edge for a day; a 404, or a row not yet checked, is sent with a short lifetime (minutes) so it updates once the job resolves it. Route tests: a known player, a player with no cross-reference, an unknown id (404). For law L3, the classification manifest (`functions/src/services/data-classification.ts`) labels the repository `none` (public facts about players) under its in-memory double's class and its Postgres adapter's class, and gives the ids table and the seeding cursor's table each their own `postgresTables` entry.
