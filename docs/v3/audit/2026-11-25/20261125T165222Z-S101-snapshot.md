**Gap:** MLB lists the uniform assets each team wore in a game; BT doesn't keep them (owner, 2026-10-30: *"Also add stories to ingest all of this extra data."*).

**Impact:** Before S101, BT didn't know what either team wore. S101 impact: BT keeps each game's uniforms ("Marlins Home White Jersey"), ready for a view to use.

**Source:** Feature: More MLB game data

**Baseline:** BT ingests the uniforms each team wore (`/api/v1/uniforms/game?gamePks=`, recorded as `fixtures/raw/uniforms-823823.json`, bundled for local dev, scanned by `pnpm mlb:scan-drift`), typed in `packages/mlb-api/src/uniforms.ts` and parsed with zod (`parseGameUniformsResponse`), fetched through `MlbStatsClient.fetchGameUniforms` in the fixture and HTTP adapters and projected by `functions/src/mappers/uniforms.ts` onto `GameSnapshot.uniforms` (each side's assets: code, name, kind; spec and generated web types regenerated additively). `fetchGame` never asks it: `ingestGame` (every one-game write: the ingest object's poll, the cron tick, the day seed, the re-check, the backfill) and the cold read (`readGames`, beside the fetch for a game not stored yet) ask it through `withAskedUniforms` only while none is stored and when the game is first stored or its status changes (`uniformsDue`), bounded by `PLAY_METRICS_LIMIT_MS` through `askWithinLimit`, the bounded ask S99's `askPlayerOfTheGame` now shares; every game write keeps a stored value through `keepStoredExtras`, the one keep that also holds S99's side-by-side pick, so a refresh without uniforms neither drops them nor stamps a new version. A game stored before S101 whose status no longer changes never gets the field (the gap S99 accepted, #619). No view shows it yet.

So the call either runs off that path or under the same limit, and AC 5's test adds: a uniforms request that never resolves leaves `fetchGame` answering within `PLAY_METRICS_LIMIT_MS` with the field absent (review-class checklist items 3 and 7, partly present data and upstream request budget).
