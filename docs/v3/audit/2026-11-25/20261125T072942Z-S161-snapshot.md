**Gap:** S107's ratified Win Probability slot (shell-scoreboard A7, `A7.md:5`, `:21`, `:48`, `:50`) draws a line on every live row (the line so far) and every final row (the whole game). The schedule payload (`ScheduleDayPayload["games"]`, read as `ScoreboardGame` in `web/src/components/scoreboard/ScoreboardModule.tsx:19`) carries no win probability, and `winProbabilitySeries` (`packages/domain/src/win-probability.ts:28`) needs a game's `plays` and `playMetrics`, which a schedule read doesn't load: they live in each game's stored snapshot (`games`), not in the stored day (`schedule_days`). S108 AC 2 asked only for the current home value, which leaves no line on a live row and nothing at all for a final one.

**Impact:** Before S161, the scoreboard's data couldn't say how a game's odds swung. S161 impact: each live or finished game on the scoreboard carries its win-probability line, so the slot (S108) can draw it without a request per game.

**Baseline:** Each game the schedule serves carries its win-probability line: `scoreboardWinProbability` (`packages/domain/src/win-probability.ts`, built only on `winProbabilitySeries`) gives `{ points, current }` or null; the game's feed write (`storeGames` in `functions/src/services/ingest.ts`, and the late-playMetrics follow-up as a line-only write) hands it to `switchGameState`, which stores it on the game's `game_states` row (`win_probability`, migration `0006`) whichever source holds the row, keeps it on a schedule write, and stamps a new state version when it alone changes; `joinScheduleDay` serves it as `winProbability` (null pregame, for a moved listing, or with no row), so `readScheduleDay`, `GET /api/v1/schedule?date=` and the day hub carry it with no game read. Games stored before S161 get theirs from `fillWinProbability` (`functions/src/adapters/postgres/win-probability-fill.ts`), which `migrateDatabaseAt` runs after migrating: batched, idempotent and resumable.
