**Gap:** A cold read writes to Postgres, then reads its own write back, before it answers. Measured 2026-11-24 (`.run/reports/latency-1124.md`, a probe of the real Worker app on PGlite with MLB's recorded answers for 2021-06-15 replayed, every query counted and run one at a time as one `pg` `Client` does on Workers): a cold 15-game digest (`GET /api/v1/digest`, `getDayDigest`, `functions/src/services/digest.ts:17-18`) makes **112** database round trips, all serialized on the request's one connection. **48** of them are read-backs or repeat reads: `getOrRefreshGame` reads the ~380 KB snapshot it just wrote back through `readServedGame` (`functions/src/services/ingest.ts:371`, 2 per game), `storeGame` re-reads the snapshot `getOrRefreshGame` read a moment earlier (`ingest.ts:107`, repeating `:351`), and `storeSchedule` re-reads the stored day it already holds (`ingest.ts:155`, repeating `:325`) and then reads the whole joined day back (`ingest.ts:158`). **32** are writes awaited before the response (the state switch, `games.upsert`, `projections.upsert`, `schedules.upsert`: 12 MB uploaded for a 6.8 KB answer), and **32** are per-game reads (15 `games.getByPk`, 15 single-row `gameStates.getMany`, …) that one `IN (…)` query each could replace; `Promise.all` at `digest.ts:18` adds no database parallelism. A cold game makes 8 (3 of them read-backs or repeats), a cold day 7 (3). Everything the answer needs is already in memory after the write: `storeGame` holds the stamped snapshot and the switch's outcome row (`storedAfter`, `game-state.ts:101-116`), and `servedGame(snapshot, row)` and `joinScheduleDay` are pure. At staging's ~70 ms a round trip (its Worker in Seattle, Neon in us-east-2; B532 places it), that is ≈ 7.8 s of a cold digest's ~9 s (staging measured 8.4–12.3 s), and even with Smart Placement the round trips stay the largest cost the code controls. A cold game also waits on MLB's playMetrics, the slowest of its four calls (0.71–0.78 s, `fetchPlayMetrics`, `functions/src/adapters/http/mlb.ts:302,428`). The owner, 2026-11-24, first: *"Perhaps we're storing stuff in our DB, then fetching it, before returning it (as opposed to forming the data to be stored and returning it while we store it)?"*; then, asked whether to fix it as one story right after S212 ("answer from the data already built, batch the per-game reads, and do the writes after the response"), chose *"Yes, story after S212 (Recommended)"*.

**Impact:** Before S216, opening a day's best clips, a game or a day that BT hadn't stored yet made the server save everything and then read it all back before answering, one step at a time, which could take nine seconds or more. S216 impact: BT answers from what it just fetched, reads many games in one step, and saves in the background after answering, so those first views open several seconds sooner.

**Acceptance criteria** (checks `scripts/verify-S216.sh` performs)

Every count below is taken through one counting repository double (a test helper under `functions/src/test/` that wraps the memory repositories, or a counting PGlite wrapper, and counts each repository call that would be one database round trip), with a fake MLB answering the 2021-06-15 fixtures or a 15-game fixture day, and the deferred work (AC 3) flushed only where a test says so.

1. **Answer from the data formed, with no read-back.** `getOrRefreshGame` answers `servedGame(snapshot, outcome.row)` from the snapshot it stamped and the switch's outcome row instead of `readServedGame` (drops `ingest.ts:371`); `storeGame` takes the stored snapshot its caller already read (drops `ingest.ts:107`); `storeSchedule` takes the stored day and `servedBase` its caller already read and builds the served day with `joinScheduleDay` from the switch's outcome rows (drops `ingest.ts:155,158`). Tests: a cold game read, a cold day read and a cold digest each make **no** read of a row or snapshot the same request wrote, and no second read of a key the request already read (the double fails the test on either); each answer equals, field for field, what a fresh read of the stored data after the deferred writes flush returns (the same `servedGame` / `joinScheduleDay`, ADR-025). **The answer never carries a version the store hasn't accepted** (ADR-022: a client applies only a newer version, so a version it holds must be one the store holds). The writes that carry the answer's version, the state switch's row write, the snapshot upsert (`games`, or `schedules` for a day), stay **awaited** before the answer, version-guarded and batched (AC 2); only writes that carry no version of the answer are deferred (AC 3). When an awaited version-guarded upsert is refused because another writer stored that version or a newer one first, the write reports it (`RETURNING` or the repository's result) and only then is the stored row read back and answered, so the answer is the stored one. A test seeds a different stored version between the read and the write and gets the stored one, version and content; the no-read-back test above covers only the accepted awaited write.
2. **One batched read per day.** `GameRepository` gains `getMany(gamePks)` (both adapters, held to the repository contract, `functions/src/adapters/repository-contract.ts`), and the digest and day paths read every game's snapshot in one call and every game's state row in one `gameStates.getMany` call, not one per game. Multi-row upserts for games and projections write a day's games in one call each. Tests: a cold 15-game digest makes exactly one `games.getMany` and one `gameStates.getMany` for its games (not 15 of either), and the contract test reads 0, 1 and 15 keys, missing keys left out.
3. **Writes that don't change the answer run after it.** A new port, `BackgroundWork` (`packages/ports/src/`), takes a promise to finish after the response: the Worker's adapter hands it to `ctx.waitUntil` (`functions/src/worker.ts`, inside the same `inDatabaseScope` so the connection stays open until the deferred writes settle), the Node server's (`functions/src/local-server.ts`) runs it and logs a failure, and the test double records it for a test to flush. Only a `cache`-window refresh made on read defers writes, and only writes that carry no version of the answer (AC 1): the projection upsert (`projections`), AC 5's playMetrics follow-up write, and S212's edge purges; the state row and the snapshot stay awaited. A deferred version-guarded write that a newer stored version refuses is logged and dropped, never written over the newer one, except AC 5's playMetrics follow-up, which retries once as AC 5 says; an active game's writes stay with the game-ingest object, which still writes Postgres before it publishes to the hub (ADR-020), and nothing in `functions/src/services/game-ingest.ts`'s write-then-publish order changes. The awaited writes keep the state row before the snapshot (S150's order, `ingest.ts:69-78`), versions are stamped before the write (ADR-022), and S212's edge purge runs after the write it follows, never before. Tests: before the flush the answer is complete, its state row and snapshot are already stored with the version it carries, and no projection write has run; after the flush the projection is stored; a deferred write refused by a newer stored version is logged and leaves the newer one; a deferred write that fails is logged and never fails the answered request; a game-ingest test asserts the store write still precedes the hub publish.
4. **The bound.** A cold 15-game digest makes at most **7** round trips before its answer (the stored-day read, the switch read, the switch write, `schedules.upsert`, `games.getMany`, `gameStates.getMany` where the switch read's rows can't be reused, the awaited `games` upsert) and at most **9** in all once the deferred writes flush, down from **112**, the count the same test measures on HEAD after S212 merges (S212 changes these paths; the grader runs the test red on that HEAD first and records the number). A cold game makes at most **4** before its answer and **5** in all (from 8); a cold day at most **4** and **5** (from 7); a stored, fresh digest at most **4** (from 32). The tests `expect` each bound (`toBeLessThanOrEqual`), so `pnpm verify` fails if one is exceeded; the grader runs them. The worker's red-first run confirms the bounds are reachable before they are fixed; under rule 7 a bound may be changed before S216 ships only to what that run shows is reachable, never loosened past it, with the reason recorded.
5. **playMetrics can't hold a cold game's answer.** `fetchGame` gives the playMetrics request a time limit of 0.75 s (one named constant in `functions/src/adapters/http/mlb.ts`, its comment giving the value and why: the probe's 0.71–0.78 s, the slowest of a game's four calls). When it runs out, the answer is built without playMetrics, as when the request fails today (`fetchPlayMetrics` answers null), and the same request keeps running in the deferred work (AC 3), whose write stores the game with playMetrics when it arrives (a new version, ADR-022). If a newer stored version refuses that write, the follow-up retries **once**: it reads the newer stored snapshot and, when it still lacks playMetrics, writes it with them as the next version; a second refusal is logged and dropped. So a past game is not left stored without playMetrics because of the limit unless two newer writes land during the follow-up. Because the answer without playMetrics may be a past, finished game's and so get S212's long edge lifetime, that follow-up write, once stored, asks S212's purge port (`EdgeCachePurger`) for the game's URL and its day's schedule and digest URLs, after the write. Tests with a fake MLB whose playMetrics answers after 2 s on fake timers: the game answers within the limit with no playMetrics; after the flush the stored game has them and the memory purger was asked for exactly the game's URL and its day's schedule and digest URLs, after the write; a playMetrics answer inside the limit is in the answer and purges nothing; a follow-up refused once by a newer stored version (seeded during the flush) retries over it and stores the newer content with playMetrics, and a second refusal is logged and leaves the stored game alone.
6. **Comments are true** (ADR-025): `getOrRefreshGame`'s, `getOrRefreshSchedule`'s, `storeGame`'s, `storeSchedule`'s, `getDayDigest`'s, `fetchGame`'s, the new port's and its adapters' comments say what they now do, and ADR-021 or ADR-022 in `docs/v3/ARCHITECTURE.md` gains a dated note that on-read refreshes answer from formed data and write after the response. `pnpm comments:stale`'s list is re-read before finishing.
