**Gap:** BT asks MLB for a schedule month only when someone opens it, and nothing durable records that a month was checked. An unchanged refresh writes nothing (ADR-022), so stored days keep an old `fetchedAt`, and the only record of the last check is each Worker isolate's in-memory `RefreshCoordinator`. So every new isolate treats every in-window month as stale and fetches it again from MLB: about 15 MB, about 1 s of CPU and 30 database reads, and warm 2026-04 requests on staging still took 2.6–5.8 s after B410 (#403, #410). A month answer, once cached at the edge, also can't be cleared when its data changes, so its lifetime has to stay short. And a month from a past year, whose schedule no longer changes, is still cached on the same short ladder. The owner directed the fix (2026-11-23): *"What I'd recommend is a CRON refresh for the remainder of the season every 6 hours or so that busts the cache, and to make that cache long-lived, like 30 days."*, then *"48 hours would be long enough if we have the CRON shorter than that"*, then *"Oh, also - schedule months from past years should be cached for an entire year. The cron should include the whole schedule (past and future) for the current calendar year (the entire year)."*, then *"in fact, for prior years, I'd make the cache as long as possible, like 100 years"*. After B399 shipped without it: *"it looks like B399 didn't include the cron thing"*.

**Impact:** Before S194, opening the calendar on a month could wait seconds while BT asked MLB for the whole month again, and a past year's months were fetched from BT's servers again every few hours or days. S194 impact: BT keeps this year's and next year's schedule fresh on its own every six hours, so the calendar's months come straight from the cache and still show schedule changes within hours, and a past year's months are kept at the edge for as long as the cache allows.

**Source:** Feature: Calendar date picker

**Baseline:** A durable record per schedule month (`schedule_months`, migration `0001_schedule_months`) and the existing per-minute cron now keep every month of the fill window fresh: `refreshDueScheduleMonth` (`functions/src/services/schedule-refresh.ts`) checks one due month a tick against MLB through the month route's own fill (`fillScheduleMonth`), so each month is checked about every 6 hours at no more than 480 MLB requests a day, and the month route asks MLB for a stored month only when its record says the refresh fell behind (`scheduleMonthCheckStale`). `GET /api/v1/schedule/month-versions/:year` names each complete month's version (`scheduleMonthVersion`), and the web asks for months with `?v=`, which the edge keeps 48 hours, or `PAST_YEAR_MONTH_EDGE_TTL_S` for a past year; the baseball-data copy never copies `schedule_months`.

1. **A durable "checked at" per month.** `ScheduleRepository` (`packages/ports/src/repositories.ts`) gains a stored record for each schedule month (`YYYY-MM`) with two times: `checkedAt`, when BT last checked the month against MLB, and `claimedAt`, when a refresh last claimed it.
    - Both adapters implement it: memory, and Postgres with a migration under `functions/src/adapters/postgres/`.
    - Taking a claim is one conditional write: it succeeds only when the month is unclaimed or its claim is older than the lease. The lease is 5 minutes, one named constant in `packages/domain`.
    - Recording a check only moves `checkedAt` forward (the newer of the stored and the given time), so a fill that finishes late never moves it back.
    - Contract test cases in `functions/src/adapters/postgres/repos.contract.test.ts` cover: a month never recorded reads as none; recording a check and reading it back; an older check leaving a newer `checkedAt` as it was; a claim inside the lease refused to a second claimant and granted after the lease.
    - `DATA_CLASSIFICATION` (`functions/src/services/data-classification.ts`) lists the new table and its columns, and its test passes.
    - The baseball-data copy (`functions/src/services/baseball-copy.ts`) never copies the table: a new `CopyRule` for it, tested in `baseball-copy.test.ts`. Another database's checks describe data this one doesn't hold, and the target's own refresh rebuilds the table.
2. **One fill, used by the route and the refresh** (ADR-025). One function in `functions/src/services/` does a month's fill, and both `getScheduleMonth` and AC 4's refresh call it:
    - it asks MLB for a span of the month with `fetchScheduleRange`;
    - it stores each returned day through `storeSchedule`, stamped with `fetchedAt` = now and `windowMode` from `scheduleDayWindowMode`, as the month route does today;
    - it records a check only when the span was the month's whole fillable range, MLB answered and every day was stored. A refresh that found nothing changed records a check too, since that is the point of the record.
   Tests in `functions/src/services/schedule-month.test.ts`:
    - a day the refresh stores reads back with the `windowMode` that `scheduleDayWindowMode` gives;
    - a fill of only the missing days (`rangeToAsk`'s gap span) leaves `checkedAt` as it was;
    - a fill whose MLB request fails records no check.
3. **The route trusts the refresh.** `getScheduleMonth` asks MLB on a read for a fully stored in-window month only when the month has no `checkedAt`, or its `checkedAt` is older than the refresh interval (6 h, one named constant in `packages/domain`) plus a 30-minute margin. Freshness is the refresh's job, so a day that changed a minute ago (today's games move the month's `lastChangedAt` every tick) no longer makes a read stale. A month with missing days still fills those days on read, as today. Tests in `functions/src/services/schedule-month.test.ts`, each with a fresh `RefreshCoordinator` (a new isolate):

    - the same month checked 7 h ago makes one fill of its whole fillable range;
    - the same month never checked, with every `fetchedAt` older than its ADR-021 lifetime, makes one fill.
4. **The scheduled refresh.** One service function refreshes at most one due month per call.
    - **Which months:** every month of `scheduleFillWindow` by MLB's today (`mlbToday`), January of the current year through December of next year, each asked whole, past days included.
    - **When a month is due:** it has no `checkedAt`, or its `checkedAt` is at least the refresh interval old, and its claim can be taken (AC 1).
    - **Which due month:** one never checked first, else the oldest `checkedAt`; on a tie, the earliest month.
    - **What it does:** it claims the month, then fills it through AC 2's function.
   Tests in `functions/src/services/schedule-refresh.test.ts` (a new file), against a counting fake MLB:

    - at 03:00 UTC on January 1 it still picks from the previous year's window (MLB's today is December 31);
    - a month checked less than 6 h ago is never picked;
    - a month claimed by a first, unfinished call is skipped by a second call;
    - an MLB failure records no check, and the same month isn't asked again inside the lease;
    - a store failure rejects;
    - with no records to start, one call at each minute 0 through 359, every call succeeding, asks for each of the window's 24 months exactly once.

7. **Changes reach the edge through a versioned URL.** A new route, `GET /api/v1/schedule/month-versions/:year`, takes any year the month route answers (1901 through next year). For each month of that year whose stored answer is complete (`monthComplete`), it gives a `version`.
    - The version is a content hash (`contentHash`, `packages/domain/src/content-hash.ts`) of the whole month answer, exactly as the month route sends it, so a field added to the answer at any level changes the version. It is computed by one function both routes call (ADR-025), from one repository read and no MLB request.
    - Any change to what the answer says changes its version: a refresh, a backfill re-storing a day, or a later story adding a field. A live game's state, which moves a day's `lastChangedAt` but not its count or teams, leaves it as it was.
    - The versions route is edge-cached for `CACHE_LIFETIME_FLOOR_MS`, with ADR-021's `stale-while-revalidate`, for every year.
   `GET /api/v1/schedule/month/:month` accepts `?v=<version>`. When `v` equals the version of the answer it is about to send, that URL's content can never change, so:
    - a month of the current or next year is cached for 48 h (`s-maxage=172800`, ADR-021's default cap, no reason needed). The owner said 48 h is enough with the refresh more frequent than that.
    - a month of a past calendar year (before MLB's today's year) gets `public, s-maxage=2147483647, stale-while-revalidate=<floor>` and no `max-age`: the edge only, as ADR-021's standings amendment says, and the 2026-11-23 exception this pull request adds to ADR-021 allows. `2147483647` is `PAST_YEAR_MONTH_EDGE_TTL_S`, one named constant whose comment gives the value and why (see **Notes**).
    - When `v` differs (an old version, or one this isolate can't see yet), the answer is cached for the floor only, so a wrong version never holds data for a long lifetime.
    - Without `v`, the route behaves as AC 8 says.

    - a refresh that changes a day's count changes the version of every month whose answer changes, and no other (a month of the other year keeps its version);
    - a refresh that changes nothing leaves every version as it was;
    - a change to a game's state alone leaves the version as it was;
    - re-storing a past year's day with a different count (a backfill) changes that month's version.

That answer is one shared query per year (`fetchScheduleMonthVersions` in `web/src/api/client.ts`) with a `staleTime` of `CACHE_LIFETIME_FLOOR_MS`, matching the edge. **Notes:**

- From enhancement [#403](https://github.com/jakelauer/baseball-theater/issues/403), suggested by B399's implementer, and #410's findings (the per-isolate record). The owner's words are quoted under **Gap**.
- **Why one month a minute, not a 6-hour slot.** The owner said a refresh "every 6 hours or so". Asking all 24 months in one tick would be up to 120 MLB requests (about 4 MB each) and 24 months of per-day writes in one invocation. That risks the Worker's CPU limit (#403 measured about 1 s of CPU per month) and a long Postgres burst. One due month per minute tick spreads the same 6-hour cycle over the existing `* * * * *` cron. It also needs no second cron expression, so `wrangler.jsonc` stays out of the fence. That file is both a reviewer path and a sensitive path in `scripts/claude-review/plan-review.py`, so touching it would make this story a barrier under `/run-backlog`. Its comment ("the cron ensures one game-ingest object…") stays true, if incomplete.
- **Why a versioned URL, not purge-by-URL.** Workers Cache is per data centre with tiered upper tiers, so `caches.default.delete` in one colo clears nothing elsewhere. Cloudflare's purge-by-URL API would clear every colo, but it needs a zone ID and an API token with cache-purge rights as new Worker secrets. That means a change to `functions/src/deploy/bootstrap.ts` and `.github/workflows/deploy.yml` (CI changes ask the owner first), and the owner has to create the token. A version in the URL needs none of that: a change the refresh stores changes the month answer's content hash, so the versions answer names a new URL within the floor (5 min plus 5 min stale). A change then reaches fans within about 6 h 10 min. The extra versions request is small, edge-cached and loaded with the month before the calendar opens.
- **The past-year lifetime.** The owner asked for "as long as possible, like 100 years". 100 years is 3,155,760,000 s, which is over 2^31−1 (2,147,483,647). RFC 9111 §1.2.2 tells a cache that gets a delta-seconds value larger than it can represent to treat it as 2^31, and Workers Cache says it "follows the semantics defined in RFC 9111" (https://developers.cloudflare.com/workers/cache/). Cloudflare's docs state only minimum edge TTLs per plan (Free 2 h, Pro 1 h, Business and Enterprise 1 s), with no maximum (https://developers.cloudflare.com/cache/how-to/edge-browser-cache-ttl/). So `PAST_YEAR_MONTH_EDGE_TTL_S` is **2147483647** (about 68 years), the largest value every 32-bit signed parser accepts. Nothing in Cloudflare's docs clamps it below a year. Even so, a cached object that isn't requested is "eventually removed to make room for newer, more popular content" (https://developers.cloudflare.com/cache/concepts/retention-vs-freshness/), so a rarely opened old month may still reach the Worker now and then. That costs one database read, never an MLB request. The same Workers Cache page documents `ctx.cache.purge({ tags })`. If that clears every data centre from `scheduled()`, it could replace AC 7's versioned URL, but it is not verified here, and switching would be a re-scope for the owner to approve.
- **Order with other items.** S191 (pull request #396, `doing`) adds `inSeasonTeamIds` to each day, worked out from the year's days, so a change in one month can change other months' answers. The version is a hash of the answer itself, so either order works: every month whose answer changes gets a new version and URL, and no long-lived answer is left in an old shape. S150 (#282) and #435 (batched schedule reads and writes) both rewrite `storeSchedule`, which this story calls but doesn't change. `claims.ts claim` orders the shared hot files. #435 would cut each tick's database time, and so would #408 (Hyperdrive query caching on, which can make a version-guarded write read a stale row).
- **Refresh-on-read follows the record, not the ladder.** ADR-021 applies its ladder twice: to the edge's lifetime and to refresh-on-read. For in-window months, AC 3 replaces the second with the refresh's record. This pull request's ADR-021 bullet says so. LOOP §7's checklist item 6 ("freshness from `cacheLifetimeMs` by last change, not by 'past vs current'") may want the same exception noted at the next rules pull request.
- **No screen change.** The calendar draws the same answer; only how fresh it is and how it is fetched change, so there is no `**Design:**` line.
