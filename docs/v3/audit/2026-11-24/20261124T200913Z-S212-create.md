**Body**

<!-- bt-body:begin -->
**Gap:** A past day's scoreboard still waits on MLB whenever the edge has no copy of it. `GET /api/v1/schedule?date=` calls `getOrRefreshSchedule` (`functions/src/services/ingest.ts`), which judges the stored day by `needsRefresh` on its `fetchedAt` and `lastChangedAt` (ADR-021's ladder). `storeSchedule` writes a day only when its version changes (ADR-022), so when S194's month refresh (`refreshDueScheduleMonth`, `functions/src/services/schedule-refresh.ts`, through `fillScheduleMonth`, `schedule-month.ts`) re-checks an unchanged month, every day keeps its old `fetchedAt`; only `recordScheduleMonthCheck` notes the check, and the day read doesn't look at it. The one other record of a check, `RefreshCoordinator.lastRefreshedAt`, lives in one Worker isolate's memory and is lost in the next. So a finished in-window day looks stale on a new isolate, and an edge miss asks MLB again: about 790 ms of server time measured on staging for 2026-09-03 (from a Zen profile: the page's request at +35 ms after the click, the service worker hop about 60 ms, the server about 790 ms). The game read (`getOrRefreshGame`) and the day digest (`GET /api/v1/digest`, `getDayDigest`, 9–12 s cold on staging, enhancement #516) use the same refresh-on-read. The headers don't hold past data long either: `edgeCacheControl` (`functions/src/handlers/cache-control.ts`) sends `public, s-maxage=<the ladder, at most 86400 for a day>, stale-while-revalidate=300` with no `max-age`. Cloudflare honours them (`cf-cache-status: HIT`), but its cache is per data center, so each data center's miss or expiry makes a fan wait, and nothing clears an edge copy when its data does change. The owner, 2026-11-24, first: *"when I was talking about caching, I meant we should set headers that will be respected by the cloudflare edge cache"*; then, after we found that past days still pay an MLB call on an edge-cache miss: *"Yes, I agree, that's how it should work. 99.9% of the time, viewing past days will be serving unchanging data. I can't think of any reason for that data to change besides historical stat changes, which are quite rare. I was hoping that the 6hrly cron job would result in both a fresh set of data AND an updated edge cache"*.

**Impact:** Before S212, opening an earlier day's scores or a finished game could stall for most of a second, or many seconds for the day's best clips, while BT asked MLB again for data that hadn't changed. S212 impact: finished days and games come straight from BT's own copy, kept at Cloudflare's edge for weeks, and the six-hourly refresh clears that copy only when something really changed, so past days open fast and still pick up rare corrections.

**Acceptance criteria** (checks `scripts/verify-S212.sh` performs)

1. **One rule for "past and finished"** (ADR-025). One named, tested function in `packages/domain` says whether a stored day is past and finished: its date is before MLB's today (`mlbToday`), its served `windowMode` is `cache`, and it is settled (`isScheduleDaySettled`). One more, beside it, says the same of a game: its served state is settled (`isSettledGame`), its `windowMode` is `cache`, and its official date is before MLB's today. The read paths (AC 2), the headers (AC 3) and the purge (AC 4) all call these two and nothing else. Unit tests cover: yesterday's all-final day is past; today's all-final day is not; a past day still holding a suspended game that hasn't moved is not; a past day stored `active` (a late game still in its trail) is not; at 03:00 UTC MLB's today is still the previous date.
2. **No MLB call on read for stored past data.** Each test below uses a counting fake MLB and a fresh `RefreshCoordinator` (a new isolate), with the stored rows' `fetchedAt` and `lastChangedAt` far older than any ladder lifetime:
    - `getOrRefreshSchedule` on a stored past, finished day makes **zero** MLB requests and returns the stored, joined day;
    - `getOrRefreshGame` on a stored past, finished game makes **zero** MLB requests;
    - `getDayDigest` on a stored past, finished day whose games are all stored makes **zero** MLB requests;
    - a day or game that isn't stored at all is still asked of MLB once, as today;
    - today's day, a future day, and a past day that isn't finished (AC 1) keep today's rule (`needsRefresh`): a stale-stamped one still makes one MLB request;
    - `?refresh=1` (`force`) still asks MLB, as today.
   Tests in `functions/src/services/ingest.test.ts` (or a new colocated file) and `functions/src/services/digest.test.ts`.
3. **Long edge lifetimes for past, finished responses.** `GET /api/v1/schedule`, `GET /api/v1/games/:gamePk` and `GET /api/v1/digest` answer past, finished data (AC 1; for the digest, its day and every one of its games) with exactly `public, max-age=<PAST_BROWSER_MAX_AGE_S>, s-maxage=<PAST_EDGE_TTL_S>, stale-while-revalidate=<PAST_STALE_S>`, three named constants in `functions/src/handlers/cache-control.ts` whose comments give their values and why:
    - `PAST_EDGE_TTL_S` is 2592000 (30 days, ADR-021's hard cap; the 2026-11-24 amendment states the reason);
    - `PAST_STALE_S` is 86400 (one day);
    - `PAST_BROWSER_MAX_AGE_S` is 3600 (one hour): a browser's copy can't be purged, so it stays short, as ADR-021's standings amendment requires.
   Any other response of these routes keeps exactly the header it gets today (`edgeCacheControl`: `no-store` in the window, the ladder outside it). Tests on the header strings in the routes' tests (`functions/src/handlers/`): one per route for past data, and today's day, a live game and a digest holding one unfinished game each keeping today's header.
4. **The cron purges the edge copy on a real change.** A new port, `EdgeCachePurger` (`packages/ports/src/`), takes a list of absolute URLs to purge. Adapters:
    - a Cloudflare adapter under `functions/src/adapters/cloudflare/` that calls Cloudflare's purge-by-URL API (`POST /client/v4/zones/<zone>/purge_cache` with `files`) with an API token and zone ID read from two Worker secrets, `BT_CF_PURGE_TOKEN` and `BT_CF_ZONE_ID`; its tests run against a fake `fetch`, never the network;
    - a memory double under `functions/src/adapters/memory/` that records what it was asked to purge;
    - with either secret or `BT_APP_ORIGIN` missing, the Worker uses a no-op purger that logs once per run that it purged nothing, and every write still succeeds; a purge request that fails is logged and never fails the write.
   The URLs are built from `BT_APP_ORIGIN` exactly as the web client asks for them: `/api/v1/schedule?date=<date>`, `/api/v1/digest?date=<date>` and `/api/v1/games/<gamePk>`.
   When the cron's writers (S194's month refresh through `fillScheduleMonth`, the day-before fetch of `refreshTodaysWindow`, and game ingest through `ingestGame`) store a past, finished day or game (AC 1) whose served version changed (ADR-022), the purger is asked for that day's schedule and digest URLs, or that game's URL and its day's schedule and digest URLs. Tests with the memory double:
    - a month refresh that changes one past day purges exactly that day's two URLs;
    - a month refresh that changes nothing purges **nothing**;
    - a change to today's or a future day purges nothing (its edge lifetime is already short);
    - a game ingest write that changes a past, finished game purges its game URL and its day's two URLs; an unchanged poll purges nothing;
    - with no credentials the write succeeds and nothing is sent; a purger that rejects leaves the write stored.
   Refilling the purged URLs (asking the edge for them again) is not required.
5. **Dead read-path code narrowed, no further.** `needsRefresh` and `RefreshCoordinator.lastRefreshedAt` stay for what still uses them (today's and future days, unfinished days, the month view's fill); their comments say they no longer decide a past, finished read. No other refactor: the grader's fence check holds the diff to the scope files.
6. **ADR-021 says so.** `docs/v3/ARCHITECTURE.md` ADR-021's 2026-11-24 amendment, and ADR-002's note pointing at it, already added by the pull request that adds this story, describe this. AC 3's headers match it (the grader greps the amendment for the owner's words *"I was hoping that the 6hrly cron job would result in both a fresh set of data AND an updated edge cache"* and for `S212`).

**Notes:**

- **Owner prerequisite: the purge credentials.** The purge needs a Cloudflare API token with the Zone → Cache Purge permission on the `baseball.theater` zone (which holds `stage.baseball.theater` and `next.baseball.theater`) and that zone's ID, as Worker secrets `BT_CF_PURGE_TOKEN` and `BT_CF_ZONE_ID` on staging and production. Creating the token is the owner's step. Every Worker secret today is pushed from GitHub secrets by each deploy (`WORKER_SECRETS` in `functions/src/deploy/bootstrap.ts`, mapped in `.github/workflows/deploy.yml`, "so GitHub is their one source and none is set once by hand"); adding these two there changes a CI workflow, which needs the owner's go-ahead and is outside this story's fence, so it is a follow-up the owner decides. Until the secrets reach the Worker, AC 4's no-op purger runs, and a rare correction to a past day waits out the 30-day edge lifetime (or reaches a fan's browser within an hour of the edge's copy expiring).
- **Why purge-by-URL.** S194's notes found that Workers Cache is per data center, so `caches.default.delete` clears one colo only, while Cloudflare's purge-by-URL API clears every one. S194 also noted that the Workers Cache docs mention `ctx.cache.purge({ tags })`; whether it clears every data center without a token was not verified. If the worker finds Cloudflare's docs say it does, using it instead is an adapter change behind the same port, but it drops the owner prerequisite, so the worker stops and asks before switching.
- **Earlier years.** S194's refresh covers January of this year through December of next year. A stored day of an earlier year is never re-checked by the cron after this story, and never by a read; the owner's words expect that ("I can't think of any reason for that data to change besides historical stat changes, which are quite rare"). The backfill (`functions/src/services/backfill.ts`) runs outside the Worker and purges nothing; a backfill correction to an edge-cached day shows once its edge copy expires.
- **The digest's cold cost.** AC 2 removes the digest's MLB calls for stored games only. A day whose games were never stored still fetches each one on its first read; that is enhancement #516, not this story.
- **No screen change**, so there is no `**Design:**` story. The month route (`GET /api/v1/schedule/month/:month`) keeps S194's versioned URLs and isn't purged.
