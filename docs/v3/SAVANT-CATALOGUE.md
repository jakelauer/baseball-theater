# Baseball Savant player data catalogue

What player data Baseball Savant (`baseballsavant.mlb.com`) publishes, batters and pitchers alike, what each set holds, how it can be fetched, what BT already gets from MLB's feeds or S103's game feed, and what each would let BT show. Written by **S104** (owner, 2026-11-27: _"S104 should search baseball savant for what else could be fetched for players and report back"_). It extends [SAVANT-DATA](./SAVANT-DATA.md), which describes the game feeds BT ingests and the seven player-season ideas recorded on 2026-10-30; each of those seven is a row below.

**Terms of Use.** S103 read MLB's [Terms of Use](https://www.mlb.com/official-information/terms-of-use), linked from Savant's footer, on 2026-11-27 ([SAVANT-DATA § Terms of use](./SAVANT-DATA.md#terms-of-use)): they forbid using "automated scripts to collect information from" MLB's digital properties, and reproducing, distributing or displaying them "without first obtaining the written permission of MLB". The owner's answer to that finding, _"go ahead with the MLB Savant stories"_ (2026-11-27), let S103–S105 go ahead under the same exposure BT already carries for MLB's own feeds. Ingesting any set below would be the same kind of automated collection and display, so a story that ingests one rests on that answer or a new one.

**This story fetched nothing by code.** No BT code, script, fixture or test reads Savant. To write this page the agent opened each page and download once by hand on 2026-11-27 (one request each, as a browser's Download CSV button makes; 2026 regular season, read after it ended, so every number below is final for 2026). Nothing was saved to the repository. One page asset host (`builds.mlbstatic.com`) was not reachable from the agent's network, so Savant's game-feed page scripts were not read.

How to read the table:

- **Grain** names who a row covers (batters, pitchers, runners, fielders, catchers). A set Savant publishes for pitchers only (pitch movement, spin, arm angle, the old S104's pitcher yearly averages) is grouped with the batter side of the same thing, so no row is pitcher-only.
- **Reachability**: every set was a plain URL with no login and no key. A leaderboard's page takes the same query string plus `&csv=true` to return CSV. None is a documented API; all can change without notice (as [SAVANT-DATA](./SAVANT-DATA.md) says of the game feeds).
- **Update cadence**: Savant's pages don't say how often they refresh, except pitch tempo ("This metric is updated weekly"). Season-to-date sets change as games are played; since the season was over when read, nothing was seen changing. "Season to date" means that, not a measured cadence.
- **BT already has** names the BT field or feed that holds the same thing today: MLB's live feed (per pitch `pitchData` / `hitData`, the box score's `seasonStats`), S93's play metrics and S103's `GameSnapshot.savant`. BT has no player page and no season-level Statcast data.
- Row counts are what the 2026 download returned with the page's default minimum ("q" is Savant's qualified minimum).

### Pitch-arsenal-stats

- `/leaderboard/pitch-arsenal-stats?type=pitcher&year=2026&min=1&csv=true` returned 3,737 rows for 830 pitchers; `type=batter`, 5,485 rows for 659 batters (a row is a player and a pitch type; the table's counts are at `min=10`). The two CSVs together are about 1.2 MB.

- Near miss: pitch movement (775 four-seam rows at `min=1`) and arm angle (829 rows at `min=1`). No break metric is in MLB's `/api/v1/metrics` list, but movement is one download per pitch type, and BT can average the live feed's break itself (the report's opinion).
- Small samples need a floor before they are shown; 25 PA was suggested (the agent's suggestion, not measured).
- Neither report records a comparison of Savant's pitch-type key with the live feed's `pitchType.code`.

### Percentile rankings

- The CSV (`/leaderboard/percentile-rankings?type=batter&year=2026&csv=true`, or `type=pitcher`; about 43 KB a side) holds only the 1–100 numbers (20 metric columns for batters), not the values ranked. The player page's embedded `statcast` array has one record a season with each value beside its rank (`xwoba: ".381"` next to `percent_rank_xwoba: 94`, plus `percent_rank_xwoba_unrounded` and an `is_qualified` flag), for about 70 metrics.
- The formula: `percentile = round(100 × players strictly below ÷ (pool size − 1))`, with 0 shown as 1 (SQL's `PERCENT_RANK`: the field names suggest it and the numbers below match it). Tied players share a percentile. Rank ÷ count lands one off for about a fifth of players.
- Qualification: the page says 2.1 PA per team game for batters, 1.25 for pitchers. The lowest qualified batter had 342 PA and the highest unqualified 339 (the line is 340.2). 246 of the CSV's 611 batters have the main percentiles.
- The pool differs by metric, and some values are rounded before ranking. Batters only; each value source is named, but the report does not record the minimum each was fetched at:

| Metric | Value source | Pool that reproduces Savant | Exact matches |
| --- | --- | --- | --- |
| xwOBA, xBA, xSLG | Savant expected statistics CSV | 246 qualified | 246/246 each |
| Average exit velocity, hard-hit % | Savant exit velocity CSV | 246 qualified | 246/246 each |
| Barrels (`brl`, the barrel count) | Savant exit velocity CSV | 246 qualified | 246/246 |
| Max exit velocity | Savant exit velocity CSV | All 656 batters with a batted ball | 612/612 (as the report gives it) |
| BB % | MLB `stats=season` (BB ÷ PA, rounded to 0.1) | 246 qualified | 246/246 |
| K % | MLB `stats=season`, lower is better (inverted) | 246 qualified | 242/246, the rest within 1 |
| Swing length | Savant bat tracking CSV, rounded to 0.1 ft | 209 bat-tracking qualifiers (603+ swings) | 209/209 |
| Bat speed | Savant bat tracking CSV, rounded to 0.1 mph | 209 | 208/209 |
| Squared-up rate | Savant bat tracking CSV, per swing, rounded to 0.1 % | 209 | 204/209 |
| Sprint speed | Savant sprint speed CSV | All 612 runners | 612/612 only if ties at the CSV's one decimal are broken by hidden decimals; from the CSV alone 175, up to 4 off |
| Barrel % | Savant exit velocity CSV | 246 qualified | 193/246, 239 within 1, worst 5 off: not resolved |

- The 209 bat-tracking qualifiers here and the table's 208 batters at `minSwings=q` differ by one; the table's 208 was read a day earlier, and the difference is not explained.
- MLB's Stats API as a stand-in: for K % and BB %, yes (above). For expected stats, no: its `expectedStatistics` xwOBA equals Savant's for 55 of the 246, up to .015 apart, and percentiles computed from it match Savant's for 87 of 246, are within 2 for 215 and up to 16 off. Its xBA differs slightly from Savant's too (Judge .261 against .258), cause unknown.
- Not verified: every pitcher metric, xISO, xOBP, whiff %, chase %, arm strength and OAA; why barrel % misses; whether Savant rounds half-up everywhere.

### Batting stance

- `/visuals/batting-stance` embeds a `vizData` array, 95 fields a row, one row per batter per side (a switch hitter has two). At the page's default, qualified batters, it returned 231 rows for 209 batters; with the page's `minSwings=1` parameter, 709 rows for 640 batters, every one with foot data (the report names the parameter, not the full query string). About 2.5 MB of HTML. Depth and distance off the plate alone are also in the swing-path CSV (659 batters, about 130 KB, no HTML).
- All of it is season averages (the page filters by date range, month, pitcher's hand and two-strike counts); none is per pitch, and Savant's per-pitch CSV has no batter-position column.

| Field | Meaning | Unit and origin |
| --- | --- | --- |
| `avg_batter_y_position` | Depth in the box: how far behind the plate's front edge the batter's hips are (Savant's centre of mass is the midpoint of the hips) | Inches; median 28.4, range 9.4 to 35.8 |
| `avg_batter_x_position` | Distance off the plate, from its inside edge | Inches; median 27.4, range 16.9 to 34.6 |
| `avg_foot_sep0` | Distance between the feet | Inches; median 30.1, range 7.9 to 44.6 |
| `avg_foot_angle0` | Open or closed stance | Degrees; median −9.9, range −66 to +8.8. Negative = open is the agent's reading, not stated |
| `avg_{r,l}{bigtoe,smalltoe,heel}_{x,y}{0,1,2}` | Foot points, below | Feet; x from the plate's centre in the catcher's view (right-handed batters negative); y from the plate's back tip, positive toward the pitcher |
| `avg_intercept_*` | Average point where the bat is nearest the ball, against the plate and against the batter | Inches and feet |
| `*_scaled` | The same points in the page's drawing pixels | Not used |

- **Foot points**: six a moment (the big toe, small toe and heel of the right and of the left foot), each an x and a y, at three moments, 0, 1 and 2: 18 points in 36 fields if every combination exists (the report gives the pattern, not a field list). The moments are unlabelled; 0 is the stance and 2 shows the stride (the front foot about 19 in further forward) is the agent's reading.
- **In BT's plate frame** (feet, x from the plate's centre in the catcher's view, y from the back tip toward the pitcher, the front edge at 17 ÷ 12; that this is Savant's foot frame is the agent's reading of `packages/domain/src/catcher-view.ts`): the foot points need no conversion, and the hips are at `x = side × (8.5 + avg_batter_x_position) ÷ 12` (side −1 right-handed, +1 left-handed) and `y = (17 − avg_batter_y_position) ÷ 12`.
- **Hip check**: the report says the hips computed this way "sit within about 1.5 to 1.8 in of the middle of the four toe and heel points on average (spread 2.5 in) across the 231 rows". Which four of the six points a moment it means, and at which moment, it does not say. Its 231 rows are taken to be the default qualified page's, not the 709 at `minSwings=1` (the agent's inference from the equal counts).
- **Against BT today**: `catcherViewBatter` (`packages/domain/src/catcher-view.ts`) puts one image with its feet 38.5 in from the plate's centre, level with the middle of the plate, for every batter. Real batters stand 25 to 43 in from the centre (median 36) and a median 11 in behind the back tip, so BT's batter is about 20 in too far forward for a typical hitter (computed from the rows above; the agent's reading).

## Owner question

**Which of Savant's player data sets should BT ingest?** BT has no player view yet, so every choice below needs a feature in FEATURES (rule 19). Every option also adds UI, so each needs a ratified design before its UI story builds (rule 18): option 2 a new screen, options 1 and 3 new pieces on Live, Plays and Box, which go through a ratified design amendment as a new screen would. Each chosen set becomes its own story. The sets are not all fetched the same way, so each option says how its rows are read (checked again on 2026-11-27): a leaderboard is one CSV a season for every player at once, which a nightly read during the season would cover; a per-player JSON call is one request a player, made when a view needs him; the Player page is HTML to parse; leverage is JSON read play by play during a game. You can also choose none for now, or a different mix.

1. **Season context beside the game (Recommended).** Rows: Percentile rankings; Expected statistics; Pitch arsenal and pitch shape. BT could show: next to the batter and pitcher in Live, Plays and Box, each one's season percentiles and expected stats, and each pitch beside the pitcher's season norm for that pitch type (what the old S104 planned), batters and pitchers alike. Fetched as: Percentile rankings and Expected statistics, a season CSV each for batters and another for pitchers; Pitch arsenal and pitch shape, six season CSV leaderboards (pitch movement and spin direction one download per pitch type) plus the yearly averages JSON, one call for any number of pitchers (a game's pitchers at once). All of it is read once a night for every player, except the yearly averages call per game: the smallest set that puts every play in season context.
2. **A player card.** Rows: Player page; Percentile rankings; Hot and cold zones; Rolling average; Sprint speed. BT could show: a card opened from any player's name with his percentile bars, hot and cold zones, a recent-form trend line and his speed. Fetched as: the Player page, an HTML page a player (1.3 MB) with its data in a script, the most fragile read here; Hot and cold zones and Rolling average, JSON calls a player (zones one call for each hand he faces); Percentile rankings and Sprint speed, a season CSV each for every player. Needs a new screen, designed and ratified first, and per-player calls when a card opens.
3. **Moment-by-moment highlights.** Rows: Exit velocity and barrels; Sprint speed; Home runs; Outs above average and fielding run value; Leverage and drama index. BT could show: on a play, "his hardest-hit ball this year", "a top-5% sprint", "a no-doubter", "a 4-star catch", and how much the moment mattered (leverage). Fetched as: Exit velocity and barrels, Sprint speed, Home runs and Outs above average, season CSVs for every player (the 4-star catch from that row's catch-probability CSV); Leverage and drama index, the `/scoreboard-data?date=` JSON for every game on a date, read play by play during a game. No new screen, but its pieces on each play are new UI, so it needs a ratified design amendment first, as option 1 does.

### The owner's answer (2026-11-28)

The owner chose a different mix from the three options, after two more research passes (2026-11-28, [§ Follow-up research](#follow-up-research-2026-11-28) above) checked each row against MLB's free Stats API and other free sources and looked closer at percentile rankings, swing path and batting stance. First, the criteria every set must meet: _"I am only interested in data I can get 1) for every player, 2) which isn't available from other free sources, 3) which is a) reasonably useful to show users as is, or b) is reasonably useful to show in combination with another stat we can already easily get from mlb, or c) is usable to mathematically calculate something that is reasonably useful to show people."_

Then, on percentile rankings: _"percentile rankings for qualified players is worth getting, but if we can compute it from the other stats we already get that's another story. On each pitcher's and batter's results by pitch type: _"I LOVE the idea of pitch 1, especially the putaway pitch thing, the BAA for a given pitch, etc as long as it's not repetitive for every single batter. Chosen, each its own story (rule 19's feature, rule 18's ratified design for its UI):

- **Pitch arsenal and pitch shape**, its results by pitch type (`pitch-arsenal-stats`, `type=pitcher` and `type=batter`: average, slugging, whiff %, strikeout %, put-away %, run value for each pitch type), for pitchers and batters alike; shown so it doesn't repeat for every batter.
- **Percentile rankings** for qualified players, fetched from Savant's CSV rather than computed (the research found Savant ranks each metric against its own pool of players, rounds values first, and two metrics still didn't reproduce: [§ Percentile rankings](#percentile-rankings)).
- **Batting stance and positioning**, shown as the batter's full stance (feet, width, open or closed), drawn in 3D, from prebaked assets or by 3D-to-2D projection, not only where he stands in the box.
- **Swing path and attack angle**: an idea only, kept in the GitHub milestone "Ideas" (unscheduled and aspirational, there to document possible ideas).

Not chosen now: every other row (the agent's reading).
