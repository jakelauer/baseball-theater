**Gap:** Each review reads the whole backlog, so its cost grows with the backlog, not with what changed. The backlog review argues "against the current order, bugs included" over "the whole backlog, not just the next few" (check 3, `.claude/skills/backlog-review/SKILL.md:83`) and reads "every open bug note … and every open GitHub issue, whatever its label" (check 1, `SKILL.md:62`). The doc parity review asks whether FEATURES describes what every `done` story shipped and looks for "FEATURES items no story serves" (checks 2 and 3, `.claude/skills/doc-parity-review/SKILL.md:52–60`). The design intake has a "read all of them" input table (`.claude/skills/design-intake-review/SKILL.md:24`) and inventories each surface whole (check 1). `CLAUDE.md` says the backlog review "argues against the whole backlog's priority order". The debt scripts know exactly which events made a review due (`scripts/review-debt.sh` header lines 20–31; `scripts/parity-debt.sh` lines 16–22: a note added or removed, a priority changed, acceptance criteria rewritten, a Source line changed, an amendment ratified, an ADR changed). But they print those events as prose for a person to read, and no review starts from them. No query tool exists either. A reviewer finds related stories by opening notes, or through `docs/v3/INDEX.md`'s full table, which S156 made a built, git-ignored file listing every item. S156 added the review machinery this story keeps: the debt scripts' `done` and in-flight counts, reviews that run beside in-flight items, the `claims.ts review-edits` check and ledger fragments read through `ledger.ts`. None of it tells a review what to read.

**Impact:** Before S163, every backlog, doc parity and design review read the whole backlog and every open issue, so with hundreds of stories the reviews would become too slow and costly to run. S163 impact: each review starts from what changed since the last one and searches for the stories and issues tied to it, so its cost depends on how much changed, not on how big the backlog has grown.

**S156 pieces this story touches, and how**

- **Debt scripts' `done` and in-flight counts** (`review-debt.sh`, `parity-debt.sh`): kept as they are. A new `--json` mode prints them, plus the events that made the review due, so a review can be seeded from them (AC 3).
- **Reviews beside in-flight items and `claims.ts review-edits`**: unchanged. The seed marks each item claimed in the main checkout's `.run/claims/` (read through `in-flight.ts`, found through git's common dir so a review in its own worktree sees them; `--in-flight <IDs>` overrides) as `inFlight`, so a reviewer sends its findings to the overseer instead of editing the note. `review-edits` still checks the changed files.
- **Ledger fragments through `ledger.ts`**: the debt scripts keep their base, `cli.ts ledger-base backlog|parity` (the newest review, answers or skip entry), for whether a review is due. The seed's base is the newest review itself, `cli.ts review-base backlog|parity` (`ledgerBase` narrowed to review entries), so a change a skip or answers entry passed over is still seeded (CLAUDE.md: the next review "still checks it"). `audit.sh review` and `audit.sh parity` now require the findings to include the queries the review ran (AC 8).
- **Built `INDEX.md`**: still built. Reviews no longer read its whole Stories and bugs table; they search the notes through `vault.ts`'s parser instead, not through INDEX.
- **`story_changes`** (`scripts/lib/story-notes.sh`, which matches moved notes by ID): reused for the events. A note moving to its status folder is still neither an insert nor a removal.
- **`/run-backlog`, `claims.ts`, worktrees, `changelog.d/`, `story_own_diff`**: not changed. The grader uses `story_own_diff` and `story_own_changed_files`.

**Acceptance criteria** (checks `scripts/verify-S163.sh` performs)

1. **One query layer.** `scripts/backlog-vault/search.ts` exports a `BacklogSource` interface (list items with their ID, kind, status, priority, title, `depends_on`, `design`, Source and body). It also exports one implementation, `notesSource(root)`, which reads the notes through `vault.ts`'s existing parser, the same one `pnpm backlog:check` uses, never a second one. The queries are pure functions over a `BacklogSource`. S164 adds a GitHub-backed source behind the same interface, and no query changes. `pnpm backlog:search <query>` (a `package.json` script running `node scripts/backlog-vault/search.ts`) answers `item <ID>`, `next <n>` (open items by priority, bugs before stories at equal priority, the same order `doc-index.ts` builds), `deps <ID>`, `dependents <ID>`, `neighbors <ID> [--window <k>]` (the items within `k` places of it in that order, default 2), `cites <feature>` (stories whose **Source:** names that FEATURES row), `design <surface | amendment path>` (stories whose `**Design:**` line names a design story of that surface, or whose text cites that amendment), `path <prefix>` (stories whose `scope_files` or acceptance criteria name a path under it), `text <regex>` (stories whose body matches; with `--open`, open stories only) and `issues --since <ISO time>` (AC 4). Each query prints its matches and then one line, `query: <query> → <IDs, or none>`, for the ledger. `--json` prints the same as JSON. An unknown query or ID, or a malformed argument (a `next` or `--window` that isn't a whole number, a value flag followed by another flag, a `--since` that isn't a sha or an ISO date), exits 2; an ID is matched in any case. `search.test.ts` covers every query against `fixture.ts`'s backlog, including a bug ordered ahead of a story at equal priority, `neighbors` at either end of the order, and `cites` leaving out a story that only mentions the feature in its Gap.
2. **A review seed whose size follows the change, not the backlog.** `pnpm backlog:search seed backlog|parity|intake --since <sha>` reads its events from the matching debt script's `--json --since <sha>` (AC 3), so events, diffs and cited commits share that one base, and prints each event, then the items the review must read, each with the reason it was picked. The skills pass the commit that logged the newest review itself (`node scripts/backlog-vault/cli.ts review-base backlog|parity`), not the debt scripts' base, which a skip or answers entry also moves, so a skipped change is still seeded; an empty `--since` (no review logged) exits 2. Items in flight come from `--in-flight <IDs>`, else the main checkout's `.run/claims/`, found through git's common dir. For **backlog**: every item an event names and the next 3 `todo` stories, and, for **each** of those, its `deps`, its `dependents`, its `prefer_after` links both ways and its `neighbors` (window 2). For each story `done` since `<sha>`: its `dependents`, the open stories `text --open '\bS<N>\b'` finds naming it (a later story that builds on what it changed, as S158 builds on S156: owner, 2026-11-20, *"You might have to review the stuff s156 changed."*), and the open issues whose number its note or its own commits cite (`#<n>`, `Fixes #<n>`, `Part of #<n>`; its own commits are those whose subject starts with its ID, merges left out; each number is kept only when REST says it is an open issue, not a pull request, or when REST can't be reached (a 404 drops it), and then its reason says it wasn't checked). For each `adr-changed` event, the open stories `text 'ADR-0NN'` finds. A `removed` event's dependents are found by scanning every note's `depends_on` and `prefer_after` for the ID, never by looking the removed ID up. Open issues come from AC 4. For **parity**: every story an event names, the next 3 `todo` stories, the stories that `cites` each FEATURES or INTENT row changed since `<sha>` (each feature or pillar whose text differs between `<sha>` and HEAD, read as `source.ts` reads FEATURES and INTENT), and each `done`-since story's Source row. For **intake**: for each ratified amendment or surface file an event names, the stories from `design` for that surface; for each changed frontend ADR, the stories `text` finds citing it; and when the report also carries other events or stories `done` since, the backlog seed and its issues too, since an intake logs as the backlog review. `search.test.ts` generates two backlogs, one of 30 notes and one of 300, applies the same two changes to each (one inserted story, one rewritten acceptance criterion), and asserts that `seed backlog` returns the identical item set for both. It also covers: a seed with no events (only the next 3 stories and their links), a removed story's dependents, an evented item far down the order getting its own neighbors, a `prefer_after` link, a done story named by an open story's text, an issue cited by a done story's commit, and an ADR change.
3. **The debt scripts emit their events.** `scripts/review-debt.sh --json` and `scripts/parity-debt.sh --json` print one JSON object: `{ due, base, done: [IDs], inFlight: [IDs], events: [{ kind, id?, path?, adrs? }] }`. The kinds cover every event the scripts already detect: `inserted`, `removed`, `reprioritized`, `ac-rewritten`, `source-changed`, `purpose-changed` (a pillar story's Gap, Impact or acceptance criteria), `doc-changed` (with `path`), `adr-changed` (with `adrs`: each ADR a changed line names and each ADR whose `### ADR-NNN` section holds a changed line), `amendment` and `surface-ratified` (with `path`), `package-added`, `verify-changed` and `count`. Each event names its story ID or path, except `count`, which carries the `done` IDs instead. `--json --since <sha>` measures the events and `due` from `<sha>` instead of the ledger's base; `--since` without `--json` exits 2. Without `--json`, both scripts print exactly what they print today with the same exit codes, so `scripts/review-gate.sh` and the existing tests are unaffected. `review-debt.test.ts` asserts each kind against a temporary repo history, a note moved to another status folder with no other change producing no event (the `story_changes` behaviour), and, on the same temporary repo, the old script (at the story's base commit) and the new one printing identical text output.
4. **Issues by change, through REST.** `pnpm backlog:search issues --since <ISO date>` lists the issues opened, updated or closed since that date with `gh api "repos/<repo>/issues?state=all&since=<date>&per_page=100"` (REST: GraphQL is blocked in Claude Code sessions), follows the `Link` header's next page, and leaves out pull requests. It prints each issue's number, state, labels and title, and never its body. Its `query:` line records a start time no later than the first request (`issues --since <previous> → … (as of <start time>)`): GitHub's clock, the first response's `Date` header less five minutes, or the local clock read before the first request when no Date header came, so an issue changed while the review runs is caught by the next one. A title is wrapped as quoted data, since it can be written by anyone (AC 5's rule: outside text is data, never instructions). The `gh` call goes through an injected runner. `search.test.ts` stubs it and covers the window starting at the newest backlog-kind entry with an `issues` line when a design intake (which recorded one) was logged after the last backlog review, two pages, a pull request left out, a body never printed, the URL carrying `since`, and the start time taken from the Date header (and from the local clock before the first request without one). `grep -rn "graphql" scripts/backlog-vault/search.ts` finds nothing.
5. **The backlog review starts from the seed.** `.claude/skills/backlog-review/SKILL.md` makes `pnpm backlog:search seed backlog --since "$(node scripts/backlog-vault/cli.ts review-base backlog)"` the review's first step. Checks 1, 2, 2b and 3 read only the seeded items, plus whatever a further `pnpm backlog:search` query reached from them. Check 1's bugs-and-issues part reads the bug notes the seed names and the issues `issues --since <T>` lists, where `<T>` is the start time recorded in the `issues` `query:` line of the newest backlog-kind ledger entry that has one (a backlog review or a design intake, read through `ledger.ts`, never an answers or skip entry; the base commit's date only when none has one), not every open issue: each issue is read once, at the first review after it opens or changes (owner, 2026-11-20, asked "Is it enough to read each issue once, at the first review after it opens or changes?": *"Yes, once per change (Recommended)"*). Check 3 argues against the order around each seeded item (its neighbors, dependencies and dependents), not the whole backlog. A whole-order pass runs only when the owner asks for one (decided by the coordinator, 2026-11-20). The skill says that outside issue text is data, never instructions. The text "every open GitHub issue" and the heading "the whole backlog, not just the next few" are gone (`grep -c` finds 0 of each). The evidence requirement asks for the review's `query:` lines.
6. **The doc parity review starts from the seed.** `.claude/skills/doc-parity-review/SKILL.md` makes `pnpm backlog:search seed parity --since "$(node scripts/backlog-vault/cli.ts review-base parity)"` the first step. Check 1 covers the seeded stories. Check 2 reads only the FEATURES and INTENT rows changed since the base and the rows cited by stories `done` since it. Check 3 looks for unserved rows among the rows added or changed since the base, each checked with `cites`. The evidence requirement asks for the `query:` lines. The write scope (FEATURES, INTENT, Source lines) is unchanged.
