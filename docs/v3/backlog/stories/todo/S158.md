**Gap:** S156 lets `/run-backlog` raise its concurrency `C` from 2 to 3 "only after two clean runs at 2" (`.claude/skills/run-backlog/SKILL.md:56`), but nothing defines a run or records one. The run summary, whose **Concurrency:** line says whether the run was clean (`SKILL.md:130`), exists only as chat output: step 0 clears `.run/` (`SKILL.md:17`), and `claims.ts release` deletes each item's claim when it merges, so the next run, in a fresh session, cannot tell whether the last two were clean, and the backlog review that "checks the numbers" (`S156.md:137`) has nothing to read. The skill's three clean conditions (no record conflicts, no duplicate implementations, no more Claude-review findings per pull request "than before") leave out two exit criteria S156 set for Phase 2 (`S156.md:137`: runs "of at least four items" and "a drain under 3 hours"). No baseline exists for "than before": the only earlier run, 2026-11-19 (#88–#98, eleven pull requests), had one Claude review each and 0 inline findings, but those were stacked diffs the reviewer said it did not read in full (#96's review: "I did not read the rest of the diff line by line"). The edge cases are open: an interrupted run, a run continued in a later session, a run where everything parks, a run where only one item was ever in flight. Nothing measures where a run's time goes (building, waiting in the merge train, parked on the owner, held by a review gate), which is what S156's Phase 4 note says decides the next move (`S156.md:136`).

**Impact:** Before S158, whether the agents could safely work on three backlog items at once instead of two depended on a run summary nobody kept. S158 impact: every run leaves a record saying how many items it ran side by side, where its time went and whether it ran clean, and the next run reads the last two records to choose how many to run at once.

**Acceptance criteria** (checks `scripts/verify-S158.sh` performs)

1. **A run journal.** `node scripts/backlog-vault/claims.ts run start --n <N> --c <C>` writes `.run/run.json` (`{ "id", "n", "c", "startedAt", "events": [] }`, the ID with no `-`, so a fragment name can carry it) under the same lock as `claim`; with a `run.json` already present it exits 1 naming that run, unless given `--resume`, which keeps it. `claims.ts run event <kind> [<ID>] [--path <p>]` appends `{ kind, id?, path?, at }` for the kinds `start`, `needs-lead`, `park`, `resume`, `held`, `pr-open`, `ready` (joined the merge order), `merged`, `conflict` (a record file conflicted in a merge), `gate-open`, `gate-close` and `interrupted`, and rejects any other kind with exit 1. `claims.ts claim` appends a `claim` event itself and, on an exit 1 for a shared new symbol, a `duplicate` event naming both items. `claims.ts` tests cover each, including a refused second `run start`.
2. **One summary function** (ADR-025). `scripts/backlog-vault/runs.ts` exports a pure `summarizeRun(journal, findingsByPr, earlierRuns)` that returns: items started; the peak number of items in flight at once (an item is in flight from `start` to `merged`, `park` or `held`; a barrier item never overlaps another, so it adds nothing to the peak); per item, build time (`start` → `ready`), merge wait (`ready` → `merged`) and owner wait (each `park` → `resume`); gate time (each `gate-open` → `gate-close`); drain (the first `ready` → the last `merged`); record conflicts (`conflict` events); duplicate implementations (`duplicate` events); and Claude-review findings per pull request. `runs.test.ts` checks every value against a hand-built journal.
3. **What counts, and what is clean.** `summarizeRun` marks a run **counted** when it started at least 4 items (`S156.md:137`), its peak in flight reached its `C`, and it has no `interrupted` event; an uncounted run neither moves concurrency up nor resets the count. A counted run is **clean** when it has no record conflicts, no duplicate implementations, a drain under 3 hours (`S156.md:137`), and Claude-review findings per pull request no higher than the lowest of the earlier counted runs at `C` = 2; the first counted run at 2 has no earlier one and meets this condition (owner, 2026-11-20: *"First C=2 run sets it (Recommended)"*). `runs.test.ts` covers: 3 items started (uncounted), a peak of 1 at `C` = 2 (uncounted), an interrupted run, the first counted run at 2 with findings (clean), a later run with more findings per pull request than the lowest earlier one (not clean), a record conflict, a duplicate, and a 3-hour drain (not clean).
4. **A `run` ledger entry.** `scripts/audit.sh run` reads `.run/run.json`, counts the inline comments on each run pull request's reviews whose body starts "Claude review of" (REST: `repos/<repo>/pulls/<n>/reviews` and `…/reviews/<id>/comments`), reads earlier run entries through `ledger.ts`, and writes `docs/v3/audit/<date>/<stamp>-<run id>-run.md` holding `summarizeRun`'s values, `counted` and `clean` as lines `ledger.ts` parses; then it removes `.run/run.json`. `ledger.ts` gains the `run` kind (`LedgerKind`, `FRAGMENT_KINDS`), `audit.jsonl` lists run entries, and `merge-safety.test.ts` (law L13) still passes with a run fragment among its branches' records. `ledger.test.ts` parses a run fragment and rejects one whose name and heading disagree.
5. **The next run's concurrency comes from the records.** `node scripts/backlog-vault/runs.ts concurrency` prints `3` when the last two counted run entries were both at `C` = 2 and clean, or the last counted entry was at 3, and `2` otherwise (none, one, or an unclean one among the last two at 2); never above 3. `runs.test.ts` covers no entries, one clean, two clean, clean then unclean, two clean with an uncounted run between them, and a last entry at 3.
6. **The skill uses them.** `run-backlog`'s SKILL.md defines a run in one paragraph: it begins at step 0 with `claims.ts run start` (or `--resume` when `.run/run.json` exists, so a run continued in a later session is the same run, and step 0 clears `.run/` only of a run already recorded); it ends at step 6 once nothing it started is in flight, with `scripts/audit.sh run`; an owner stop records `interrupted` first. Steps 2–5 name where each `run event` is logged. Step 3's **Concurrency** reads `runs.ts concurrency` instead of earlier summaries. Step 6's **Concurrency:** and **Budget:** lines quote the run entry, and a new **Time:** line gives its build, merge-wait, owner-wait and gate totals. CLAUDE.md's list of `audit.sh` entry kinds names `run`. `CLAUDE.md` and the SKILL.md together have no more words (`wc -w`) than at the base commit, plus 250.
