**Gap:** The owner asked for a Download button on the video player (owner, 2026-11-12: *"video player needs a palette of helpful clickables (copy link, direct link, download, share)"*), then had it taken out (owner, same day: *"Remove the download button for now, but make a story to do the service worker in the future"*). A browser ignores `download` on a link to another site's file, so a plain link to MLB's MP4 only opens it; PR #58 built Download as such a link, so it opened the file like Direct link does, and the other way to save a cross-origin file, fetching the whole clip into the page first, holds a condensed game (hundreds of MB) in memory and can crash a phone's tab. The app already has a service worker (S73, ADR-023), and a service worker can answer a same-site request by passing MLB's file through as an attachment as it arrives, with no size limit and no server cost, since the bytes still come straight from MLB.

**Impact:** Before S151, saving a video meant opening it with Direct link and saving it from the browser's own player. S151 impact: Download saves any MP4 clip, a condensed game included, straight to the device.

**Acceptance criteria** (checks `scripts/verify-S151.sh` performs)

1. The service worker answers a same-site download route (for example `/download/clip?url=<MLB MP4>&name=<file name>`) by fetching the MP4 and passing its body through unread, with `Content-Disposition: attachment` naming the file after the clip's title, so nothing holds the whole file in memory, and MLB's `Content-Length` passed through so the browser shows progress. The file name is never the caller's choice as given: it is cut down to a safe ASCII slug that always ends `.mp4`, with the title in RFC 5987 `filename*=UTF-8''…` form, and no CR, LF or quote can get into the header (unit tests of the handler with a fake `fetch`: the response streams the upstream body and carries both headers; a title like `Acuña's homer` doesn't throw; `name=x.exe` saves as `x.mp4`).
2. The route serves only `https` MP4s on MLB's clip hosts (today `mlb-cuts-diamond.mlb.com`, `bdata-producedclips.mlb.com`, `darkroom-clips.mlb.com`, as the recorded content shows); any other host, scheme or file, or a malformed `url`, answers 400 and fetches nothing, so the route is never an open proxy. One named function in `packages/domain` (beside `video-quality.ts`, reusing what `fileQuality` knows of MP4s) decides "an MLB clip MP4", and both this route and AC 4's check call it (ADR-025) (tests).
3. The route isn't swallowed by the app shell's navigation fallback (`navigateFallbackDenylist` in `web/src/pwa/options.ts`, or the route registered first), and the service worker's precache list stays as it is (test of the options or the built worker).
4. The player's palette (`PlayerActions`) shows **Download** again, as a link to the route for the clip's MP4 (`fileUrl`, `fileQuality`), only while the worker controlling the page answers for that route: the page asks it (a `postMessage` ping the new handler answers, checked again on `controllerchange`), since an older worker still in control under the update prompt (`registerType: "prompt"`) would answer the route with the app shell. With no controller (a first visit before the worker takes over, a private window that refuses it), an older one, or an HLS stream it shows none, and Copy link, Direct link and Share are unchanged (RTL for each case).
5. This file's S151 **Status** (story heading and top table) is `done`.
