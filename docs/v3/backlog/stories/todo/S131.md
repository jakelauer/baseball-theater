**Gap:** The owner wants a fan-facing change log for every release, its bucketing approved by them each time (owner, 2026-11-08: *"The change log and bucketing need to be manually approved by me for each release"*; asked how, *"Draft, you approve in session"*). Today the only record is `CHANGELOG.md`, written per story for anyone, including dev-only changes, and nothing ties a release to an approved summary: a release can publish with no notes at all, and no build knows which release it is.

**Impact:** Before S131, a release went out with no fan-facing summary and nobody had signed off on how its changes were described. S131 impact: every release has one short list of what changed for fans — big additions, their own items, and one "fixes and polish" line — that the owner approved before it went out, and production refuses a release without it.

**Source:** Feature: Update / change log UX

**Acceptance criteria** (checks `scripts/verify-S131.sh` performs)

1. `packages/domain` defines a release's notes (`ReleaseNotes`) and one parser for them (`parseReleaseNotes`): `version` (`vMAJOR.MINOR.PATCH`, each part a number with no leading zero, so `v3.01.0` is rejected rather than read as `v3.1.0`); an optional `date` (a real calendar date, `isCalendarDate`); `headline`, the really big additions, which the change log page shows under its gold "Major Feature" header (S133, S134; the update notice shows no addition since the owner's answers of 2026-11-10, evening) (each a title and one sentence); `items`, every change that gets its own entry (each a `kind` — `feature`, `enhancement`, `performance` or `fix` (owner, 2026-11-10: *"maybe feature, enhancement, bug fix, are the big three"*; 2026-11-16, asked whether to add a fourth and which: *"Performance"*) — a title and one sentence); an optional `fixesAndPolish`, the one sentence that stands for all the minor fixes; and an optional `approval` (a real calendar date and the owner's words, quoted). An entry is in `headline` or `items`, never both. The parser returns the notes or every problem it found, by field (unit tests: a valid file; a bad version, including a leading zero; an impossible date; an unknown `kind`; an empty title or sentence; an approval with no quote; the same title in `headline` and `items`; notes with nothing in any bucket, which are rejected; notes holding only `fixesAndPolish`, which are valid, as a fixes-only release's are; `v3.0.0`, whose zero parts are valid).
2. `packages/domain` has one exported check of a release version (`parseReleaseVersion`, the same rules as AC 1's `version`; `parseReleaseNotes` uses it), one comparison of release versions (`compareReleaseVersions`, numeric per part, so `v3.10.0` is newer than `v3.9.0`) and one answer to "which is the newest approved release in these notes" (`currentRelease`: the newest **approved** notes among those given, ignoring drafts; since #47 it is not the build's own label, which is its pull request's milestone, S135 AC 1) (unit tests, including `parseReleaseVersion` on `v3.01.0`, `3.1.0` and an empty string, `v3.10.0` newer than `v3.9.0`, a newer draft that is ignored and no approved notes at all).
3. `pnpm release:check <version>` first checks its argument with `parseReleaseVersion` (AC 2) and exits nonzero on a tag that isn't a valid version (`3.3.0`, `v3.01.0`). For a valid version below v4.0.0 it then exits 0 without reading `releases/` and prints that pre-launch releases carry no fan-facing notes (AC 6), so a pre-launch release such as v3.3.0 still deploys. For v4.0.0 and later it exits 0 only when `releases/<version>.json` exists, parses (AC 1), is approved (date and a non-empty quote) and its `version` matches the file name; otherwise it exits nonzero and prints each problem (tests over temporary directories: missing file, draft, mismatched version, valid, a `v3.3.0` tag with no file, which passes; `v4.0.0` with no file fails; `3.3.0` and `v3.01.0`, which fail).
4. The production deploy job (`.github/workflows/deploy.yml`, `production`) runs `pnpm release:check` with the release's tag (`github.event.release.tag_name`) after its Install step and before it builds anything, so a release from v4.0.0 on whose notes aren't approved in the tagged commit fails before deploying, while a pre-launch release passes (AC 3) (grep, read inside the `production:` job's block only: the file has a "Build the web app" step in four jobs, so a whole-file grep would pass with the check in the wrong one).
5. `CLAUDE.md`'s release rule says the coordinator drafts `releases/<version>.json` from the `changelog.d/` fragments of the milestone's merged pull requests (the entries step (4)'s `pnpm changelog:build` assembles into `CHANGELOG.md` on the release commit's tree, rule 16, a run the rule keeps), bucketed as FEATURES' change log page says (big additions in `headline`; very impactful fixes, new settings, new features and significant design changes as their own `items`, each a feature, an enhancement, a performance change or a bug fix; minor fixes and polish in `fixesAndPolish`), shows the draft to the owner, writes the owner's in-session approval into `approval` quoted, lands it in `stage` through a pull request, and publishes only a commit where `pnpm release:check <version>` exits 0 and whose milestone pull requests the notes all describe (one that merged into `stage` after the draft is either drafted in and re-approved, or left out by releasing the commit where the notes landed and moving it to the next milestone); never writing an approval the owner didn't give in the current session; and it replaces the sentence that held each release's fan-facing notes in its GitHub Release until S131 (grep).
