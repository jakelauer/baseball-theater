**Gap:** Every pull request's checks rebuild and retest everything from scratch, and the slowest two jobs set the wait (measured on six pull request runs, 2026-11-19): `design-specs` takes 5–9 minutes, about 4 of them reinstalling the Playwright browser (`playwright install --with-deps chromium`, 247 s in one run), which `flows` repeats; `verify` takes about 7.5 minutes, one 408 s step (`pnpm verify`) of which the `functions` package's tests with coverage are about 5 minutes, run in full even when a pull request touches only `web/` or docs. Nothing is cached between runs but pnpm's package store. The owner asked for it (owner, 2026-11-19: *"Can we get scoped build caching somehow so we can avoid a full rebuild for PR checks"*), and chose, offered four speed-ups, all four: a prebuilt browser image, skipping unchanged packages, splitting the functions tests, and ESLint and tsc caches. The aim is to build only what a change touches (owner, same day: *"The point would be to only build the stuff that changes"*): asked whether `stage` should rerun everything after a merge, *"Stage reruns everything (Recommended)"*; asked whether the browser jobs should run only the specs a change could affect, *"Yes, scope them too"*.

**Impact:** Before S152, every pull request waited about 9 minutes for its checks, however small the change. S152 impact: a change to one part of the app reuses the passing results of the parts it doesn't touch, the browser is kept between runs instead of reinstalled, and the slowest tests run in parallel, so most pull requests finish their checks in a few minutes.

**Acceptance criteria** (checks `scripts/verify-S152.sh` performs)

1. **No browser reinstall.** `flows` and `design-specs` restore Playwright's browser folder (`~/.cache/ms-playwright`) with `actions/cache`, keyed on the `@playwright/test` version the lockfile resolves, and download the browser (`playwright install chromium`) only on a cache miss; the system libraries it needs (`playwright install-deps chromium`) are installed every run. (Playwright's container image is not used: the e2e web server starts the app with `pnpm dev`, which runs `docker compose`, and the image has no Docker.) Grader: parses `ci.yml` and `pnpm-lock.yaml`; a cache key that doesn't name the lockfile's version, or an unconditional browser download, fails.
2. **Per-package task caching.** A `turbo.json` defines each package's `typecheck`, `build` and `test:coverage` tasks, each depending on its workspace dependencies' tasks (`^`), with each package's coverage output among its `outputs`, and global inputs covering every file outside the packages that any package's build or tests read: at least `pnpm-lock.yaml`, `tsconfig.base.json`, `eslint.config.js`, `.nvmrc`, `.jscpd.json`, `.size-limit.json`, `wrangler.jsonc`, `fixtures/**`, `openapi/**`, `tools/**` and `.github/workflows/**` (functions' and web's tests read the fixtures, the OpenAPI spec, `wrangler.jsonc` and the workflows). The grader proves the scoping offline (`TURBO_TELEMETRY_DISABLED=1`, `--no-update-notifier`, turbo from the lockfile) with `turbo run test:coverage --dry=json` before and after a throwaway edit: a file under `web/src/` changes `web`'s hash and leaves `functions`' and `packages/domain`'s unchanged; a file under `packages/domain/src/` changes `domain`'s, `functions`' and `web`'s; `pnpm-lock.yaml`, `tsconfig.base.json` or a file under `fixtures/` changes every package's; the edits are reverted and the tree left as it was. Every environment variable a task reads to change what it runs (AC 4's) is declared in that task's `env` in `turbo.json`, so it is part of the cache key and reaches the task in turbo's strict mode (grader: each such name appears there). Root lint (`pnpm backlog:check && eslint .`) stays one root task, sped up by AC 5's ESLint cache rather than replayed.
3. **CI reuses it, and `stage` never does; the truth gate keeps its shape.** `pnpm verify`'s script stays `pnpm build && pnpm dup:check && pnpm test:coverage && pnpm size`, and `build` and `test:coverage` call `turbo` underneath, so the chain `scripts/backlog-vault/verify-chain.ts` follows still reaches every check (laws L5, L7, L9, P8). CI's `verify` job still runs `pnpm verify` (law P11; `scripts/backlog-vault/ci-law.test.ts`), with the unchanged `ci-passed` line `test "$VERIFY $FLOWS $DESIGN $LIGHTHOUSE" = "success success success success"`, one job-level `if:` in the `verify` job and its Markdown format step. On a pull request, `verify` restores Turborepo's cache with `actions/cache` (a key unique to the run, restore keys falling back to the newest cache from `stage`), so a package whose hash is unchanged replays its passing result and coverage output. On a push to `stage` or `main` every task runs fresh (`--force`, no cache read) and saves the cache, so a wrong cache hit can't reach `stage` unnoticed. `pnpm test:backlog` passes (the law tests).
4. **Split functions tests.** On a pull request, `verify` skips `functions`' `test:coverage` entirely, both its Node half and its workerd half (an environment variable its script reads), and at least two shard jobs, placed after `flows` in `ci.yml`, run them (`vitest --shard=<i>/<n>`) with the coverage floors off for a shard run (an environment variable `functions/vitest.config.ts` reads), then merge their coverage (`vitest --merge-reports` or equivalent) and check `functions/vitest.config.ts`'s floors on the merged result, so the floors mean what they mean today. `functions`' workerd tests (`vitest.workers.config.ts`) run once, in one of those jobs (grader: `vitest.workers.config.ts` is run by exactly one CI job on a pull request). `ci-passed` requires the shard and merge jobs with a check of its own beside the unchanged line above, and accepts them skipped exactly when the change is docs-only (`changes` says `code=false`). Locally, `pnpm verify` still runs `functions`' whole suite in one go.
5. **Browser specs scoped to the change.** Every spec under `e2e/flows/` and `e2e/design/` declares only its direct targets, `web`, `functions` or both (a spec names `web` alone only when every API request it makes is mocked with `page.route`; one that reaches the fixture-backed API names both), and a selector in `e2e/` (for example `e2e/select-specs.ts`), a pure function of the changed-file list (`git diff --name-only <base sha>...<head sha>`, the base being `github.event.pull_request.base.sha` as the `changes` job uses, fetched in those jobs), the package directories and the workspace dependency graph, picks the specs to run. A changed file under a package directory selects every spec whose targets are that package or depend on it through the graph (so a spec never lists the packages its targets use). Any other changed path selects every spec unless it is on the selector's explicit list of paths no browser run reads: `docs/v3/` except `docs/v3/visual/` and `docs/v3/design-checks/` (which `e2e/design/helpers.ts` reads), `.claude/`, and Markdown files outside those two; everything else, including `e2e/`, `scripts/`, `compose.yaml`, `wrangler.jsonc`, the root `package.json`, `fixtures/` and `docs/v3/visual/`, runs them all. On a pull request `flows` and `design-specs` pass the selected spec files to `playwright test` directly (never alongside a fixed `flows/` or `design/` path, which Playwright would add to the list), keeping today's `--workers=4` and `--repeat-each=2` where they apply and running `e2e/design/harness.spec.ts` in both jobs as today, and with none selected they skip their steps with step-level `if:` so the job still ends `success` (`ci-passed` needs `success`; a job-level `if:` would leave it skipped); on a push to `stage` or `main` they run every spec. Grader: every spec file declares its targets, and only `web` or `functions`; given a change only in `packages/ports/` the selector selects every spec whose target depends on `@bt/ports` and no other, given `web/src/` every spec naming `web`, and given `pnpm-lock.yaml`, `scripts/backlog-vault/design-reference.ts`, `compose.yaml`, a file in `e2e/` or a file in `docs/v3/visual/` every spec, given only `CHANGELOG.md`, or only `docs/v3/AUDIT.md`, `docs/v3/audit.jsonl`, `docs/v3/INDEX.md` and `docs/v3/BACKLOG.md`, none, and given those plus a file in `web/src/` exactly the specs naming `web`; every spec naming only `web` calls `page.route` for `/api/`; `ci.yml` runs the selector on pull requests only, with the spec list in place of the fixed path and step-level skips.
6. **ESLint and tsc caches.** ESLint runs with `--cache` (its `.eslintcache` added to `.gitignore`), and each package's `typecheck` passes `--incremental` with a `--tsBuildInfoFile` on its command line in its `package.json` (`*.tsbuildinfo` is already git-ignored); CI keeps both between runs with `actions/cache` or as Turborepo outputs. The grader checks the flags and the ignore entries.
7. **Measured on real runs.** The story is committed as a parked checkpoint and its pull request opened; it is finished only after two runs on that pull request: one changing only `web/` (functions' tests replayed from the cache, named from the run's `turbo` summary) and one changing `functions/` (the shards' times), and the browser jobs' selected specs in each. Their job times, beside the 2026-11-19 baseline in the Gap, go in this story's notes in the commit that flips it to `done`, with its ledger entry. The grader checks the notes name both runs' URLs and times.

**Notes:**

- **Why `stage` runs everything (AC 3, AC 5; owner, 2026-11-19: *"Stage reruns everything (Recommended)"*).** A cache key that misses an input would replay a stale pass. Pull requests take the speed; every merge to `stage` reruns the whole suite with no cache read, so such a miss shows on the next `stage` run instead of shipping. The `changes` job's docs-only skip stays as it is, and the new jobs skip with it.
- **The browser image the owner picked.** Offered "Prebuilt browser image", the owner chose it; the pre-PR review found the image can't run the e2e web server (it needs Docker), so AC 1 caches the downloaded browser instead, which removes the same reinstall. The owner is told when the story is opened.
- **The reviewer.** `ci.yml`, every `package.json` and `functions/vitest.config.ts` are on `is_reviewer_path` (`scripts/claude-review/plan-review.py`) and get a full Claude review every round; `turbo.json` is not on it, and adding it is outside this story's fence (the owner is asked whether to add it). Batch fixes into one push (CLAUDE.md).
- **`pnpm verify` runs through `turbo` underneath** (AC 3), a change to how the truth gate runs, which is a drift event: the backlog review after this story checks it (CLAUDE.md).
- **Other workflows:** `deploy.yml`'s builds are not in scope; a later story can reuse the cache there.
