**Gap:** Every pull request's checks rebuild and retest everything from scratch, and the slowest two jobs set the wait (measured on six pull request runs, 2026-11-19): `design-specs` takes 5–9 minutes, about 4 of them reinstalling the Playwright browser (`playwright install --with-deps chromium`, 247 s in one run), which `flows` repeats; `verify` takes about 7.5 minutes, one 408 s step (`pnpm verify`) of which the `functions` package's tests with coverage are about 5 minutes, run in full even when a pull request touches only `web/` or docs. Nothing is cached between runs but pnpm's package store. The owner asked for it (owner, 2026-11-19: *"Can we get scoped build caching somehow so we can avoid a full rebuild for PR checks"*), and chose, offered four speed-ups, all four: a prebuilt browser image, skipping unchanged packages, splitting the functions tests, and ESLint and tsc caches. The aim is to build only what a change touches (owner, same day: *"The point would be to only build the stuff that changes"*): asked whether `stage` should rerun everything after a merge, *"Stage reruns everything (Recommended)"*; asked whether the browser jobs should run only the specs a change could affect, *"Yes, scope them too"*.

**Impact:** Before S152, every pull request waited about 9 minutes for its checks, however small the change. S152 impact: a change to one part of the app reuses the passing results of the parts it doesn't touch, the browser is kept between runs instead of reinstalled, and the slowest tests run in parallel, so most pull requests finish their checks in a few minutes.

**Acceptance criteria** (checks `scripts/verify-S152.sh` performs)

1. **No browser reinstall.** `flows` and `design-specs` restore Playwright's browser folder (`~/.cache/ms-playwright`) with `actions/cache`, keyed on the `@playwright/test` version the lockfile resolves and the runner's image (`runner.os` and `ImageOS`, so a new `ubuntu-latest` downloads afresh), and download the browser (`playwright install chromium`) only on a cache miss; the system libraries it needs (`playwright install-deps chromium`) are installed every run. (Playwright's container image is not used: the e2e web server starts the app with `pnpm dev`, which runs `docker compose`, and the image has no Docker.) Grader: parses `ci.yml` and `pnpm-lock.yaml`; a cache key that doesn't name the lockfile's version, or an unconditional browser download, fails.
2. **Per-package task caching.** A `turbo.json` defines each package's `typecheck`, `build` and `test:coverage` tasks, each depending on its workspace dependencies' tasks (`^`), with each package's coverage output among its `test:coverage` `outputs` and `web`'s build output (`dist/**`) among its `build` `outputs` (law L5's `pnpm size` reads `web/dist/assets/index-*.js`, so a replayed `web#build` that restored no `dist/` would leave `pnpm size` nothing to measure in a fresh checkout), and global inputs covering every file outside the packages that any package's build or tests read: at least `pnpm-lock.yaml`, `tsconfig.base.json`, `eslint.config.js`, `.nvmrc`, `.jscpd.json`, `.size-limit.json`, `wrangler.jsonc`, `fixtures/**`, `openapi/**`, `tools/**`, `.github/workflows/**` and `scripts/preview-pr-open.sh` (functions' and web's tests read the fixtures, the OpenAPI spec, `wrangler.jsonc` and the workflows; `functions/src/deploy/deploy-workflow.test.ts` runs `scripts/preview-pr-open.sh`). The grader also checks `web#build`'s outputs name `dist/**`. The grader proves the scoping offline (`TURBO_TELEMETRY_DISABLED=1`, `--no-update-notifier`, turbo from the lockfile) with `turbo run test:coverage --dry=json` before and after a throwaway edit: a file under `web/src/` changes `web`'s hash and leaves `functions`' and `packages/domain`'s unchanged; a file under `packages/domain/src/` changes `domain`'s, `functions`' and `web`'s; `pnpm-lock.yaml`, `tsconfig.base.json` or a file under `fixtures/` changes every package's; the edits are reverted and the tree left as it was. Every environment variable a task reads to change what it runs (AC 4's) is declared in that task's `env` in `turbo.json`, so it is part of the cache key and reaches the task in turbo's strict mode (grader: each such name appears there). Root lint (`pnpm backlog:check && eslint .`) stays one root task, sped up by AC 6's ESLint cache rather than replayed.
3. **CI reuses it, and `stage` never does; the truth gate keeps its shape.** `pnpm verify`'s script stays `pnpm build && pnpm dup:check && pnpm test:coverage && pnpm size`, and `build` and `test:coverage` call `turbo` underneath, so the chain `scripts/backlog-vault/verify-chain.ts` follows still reaches every check (laws L5, L7, L9, P8). CI's `verify` job still runs `pnpm verify` (law P11; `scripts/backlog-vault/ci-law.test.ts`), with the unchanged `ci-passed` line `test "$VERIFY $FLOWS $DESIGN $LIGHTHOUSE" = "success success success success"`, one job-level `if:` in the `verify` job and its Markdown format step. On a pull request, `verify` restores Turborepo's cache with `actions/cache` and saves it at the end (a key unique to the run, which GitHub scopes to that pull request; restore keys that reach the pull request's own newest cache first, then the newest from `stage`), so a package whose hash is unchanged since that pull request's last run or since `stage`'s replays its passing result and its outputs. On a push to `stage` or `main` every task runs fresh (`--force`, no cache read) and saves the cache, so a wrong cache hit can't reach `stage` unnoticed. Everywhere else `pnpm verify` reads no cache either: the root scripts' `turbo` calls run every task unless an environment variable that only `ci.yml`'s pull-request `verify` step sets turns reading on, so a local `pnpm verify`, `scripts/audit.sh story` (whose ledger entry says the gate ran) and `deploy.yml`'s `pnpm verify` (outside this fence) run every task as today. Grader: the root `build` and `test:coverage` scripts' `turbo` calls don't read the cache unless that variable is set (from their text: `--force`, or Turborepo's write-only cache setting, unless it is set), and `ci.yml` sets it only in a step that runs on `pull_request`. `pnpm test:backlog` passes (the law tests).
4. **Split functions tests, only when the change reaches them.** On a pull request whose change reaches `functions` (AC 5's selector rule applied to the package: a changed file in `functions/` or in a package it depends on, or any changed path outside the package directories that isn't on AC 5's list of paths no browser run reads, none of which `functions`' tests read either), `verify` skips `functions`' `test:coverage` entirely, both its Node half and its workerd half (an environment variable its script reads), and at least two shard jobs, placed after `flows` in `ci.yml`, run them (`vitest --shard=<i>/<n>`) with the coverage floors off for a shard run (an environment variable `functions/vitest.config.ts` reads), then merge their coverage (`vitest --merge-reports` or equivalent) and check `functions/vitest.config.ts`'s floors on the merged result, so the floors mean what they mean today. `functions`' workerd tests (`vitest.workers.config.ts`) run once, in one of those jobs (grader: `vitest.workers.config.ts` is run by exactly one CI job on a pull request). On a pull request whose change doesn't reach `functions` (only `web/` files, say), `verify` leaves `functions`' `test:coverage` to Turborepo with the variable unset, so it replays `stage`'s passing run when its hash matches and runs in full when it doesn't, and the shard and merge jobs skip their steps with step-level `if:` and end `success`; on a push to `stage` or `main` `verify` runs the whole suite (AC 3) and the shard and merge jobs skip their steps the same way. `ci-passed` requires the shard and merge jobs with a check of its own beside the unchanged line above, and accepts them skipped exactly when the change is docs-only (`changes` says `code=false`). Grader: the decision is a pure function of the changed-file list and the workspace graph (shared with AC 5's selector, not a second copy of its path lists): given only `web/src/` it says no, given `packages/domain/src/`, `functions/src/`, `fixtures/` or `scripts/preview-pr-open.sh` it says yes. Locally, `pnpm verify` still runs `functions`' whole suite in one go.
5. **Browser specs scoped to the change.** Every spec under `e2e/flows/` and `e2e/design/` declares only its direct targets, `web`, `functions` or both (a spec names `web` alone only when it answers every API request itself: it routes all of `**/api/**`, directly with `page.route` or through `stubApi` in `e2e/design/helpers.ts`, so a request it forgot to mock fails the spec instead of quietly reaching `functions`; one that reaches the fixture-backed API names both), and a spec that declares no targets, or one the selector doesn't know, is selected on every run (a later story's new spec, such as S125's `e2e/design/S125.spec.ts`, is never silently skipped), and a selector in `e2e/` (for example `e2e/select-specs.ts`), a pure function of the changed-file list (`git diff --name-only <base sha>...<head sha>`, the base being `github.event.pull_request.base.sha` as the `changes` job uses, fetched in those jobs), the package directories and the workspace dependency graph, picks the specs to run. A changed file under a package directory selects every spec whose targets are that package or depend on it through the graph (so a spec never lists the packages its targets use). Any other changed path selects every spec unless it is on the selector's explicit list of paths no browser run reads: `docs/v3/` except `docs/v3/visual/` and `docs/v3/design-checks/` (which `e2e/design/helpers.ts` reads), `.claude/`, and Markdown files outside those two; everything else, including `e2e/`, `scripts/`, `compose.yaml`, `wrangler.jsonc`, the root `package.json`, `fixtures/` and `docs/v3/visual/`, runs them all. On a pull request `flows` and `design-specs` pass the selected spec files to `playwright test` directly (never alongside a fixed `flows/` or `design/` path, which Playwright would add to the list), keeping today's `--workers=4` and `--repeat-each=2` where they apply and running `e2e/design/harness.spec.ts` in both jobs as today, and with none selected they skip their steps with step-level `if:` so the job still ends `success` (`ci-passed` needs `success`; a job-level `if:` would leave it skipped); on a push to `stage` or `main` they run every spec. Grader: every spec file declares its targets, and only `web` or `functions`; given a change only in `packages/ports/` the selector selects every spec whose target depends on `@bt/ports` and no other, given `web/src/` every spec naming `web`, and given `pnpm-lock.yaml`, `scripts/backlog-vault/design-reference.ts`, `compose.yaml`, a file in `e2e/` or a file in `docs/v3/visual/` every spec, given only `CHANGELOG.md`, or only `docs/v3/AUDIT.md`, `docs/v3/audit.jsonl`, `docs/v3/INDEX.md` and `docs/v3/BACKLOG.md`, none, and given those plus a file in `web/src/` exactly the specs naming `web`, and given only `packages/ports/` a spec with no declaration (handed to the selector as input, no file written) is selected; every spec naming only `web` routes `**/api/**` (`page.route` or `stubApi`); `ci.yml` runs the selector on pull requests only, with the spec list in place of the fixed path and step-level skips.
6. **ESLint and tsc caches.** ESLint runs with `--cache --cache-strategy content` (a fresh checkout gives every file a new modification time, so the default `metadata` strategy would treat every file as changed and the restored cache would save nothing) and a fixed `--cache-location` (its `.eslintcache` added to `.gitignore`), and every `tsc` call a package's `typecheck` **and** `build` scripts make passes `--incremental` with the same `--tsBuildInfoFile` on its command line in its `package.json` (`pnpm verify` runs each package's `build`, whose `tsc -p tsconfig.json --noEmit` is the typecheck it actually runs; no package's `typecheck` is in the verify chain; `*.tsbuildinfo` is already git-ignored); CI keeps both between runs with `actions/cache`, restored before `pnpm verify` (not as Turborepo outputs: lint is a root task outside Turborepo, and a task's outputs are restored only on a cache hit, when its `tsc` doesn't run). The grader checks the flags on both scripts of every package, the ignore entries and the cache steps.
