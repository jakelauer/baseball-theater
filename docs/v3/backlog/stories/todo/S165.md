**Gap:** After S164, the repository records each story's text (the `migration`, `create`, `edit` and `snapshot` fragments), and GitHub owns each item's state. `pnpm backlog:check` holds the parts of law L9 a commit can answer, and `audit.sh apply` brings issue bodies in line with the records after they merge. Several things are still missing:
- Nothing compares the live issues with the records, or a story's label with its open or closed state. A body changed on GitHub without a record (by the owner, a collaborator or an issue's filer) goes unnoticed.
- The design gate ("a UI story waits for its ratified design") needs its design stories' state, which GitHub now owns. S164 took it out of the commit check and nothing enforces it.
- The owner can't change a story's text on GitHub and have it recorded.
- An issue someone else files has no label. S164's trusted-ID rules keep it out of the backlog, but nothing tells the owner it exists or marks it as waiting, and no rule says what agents do with its text, which anyone can write.
- The issues have no `area:*` labels, and done stories have no milestones.
- A review running beside in-flight items could record an edit to one of them, since S164 left those guards here.
- The two CI jobs that run `pnpm backlog:check` (ci.yml:108, the docs job; ci.yml:182–196, both `pnpm verify` steps) can't read issues: their token has no `issues: read` and they run no sync.

**Impact:** Before S165, a story's text changed on GitHub, a status gone wrong, or a screen started before its design was agreed went unnoticed, and an issue someone else filed sat unseen. S165 impact: every check run compares the stories on GitHub with their agreed text and flags what changed without a record or broke the order. The owner can change a story on GitHub and have it recorded. Issues others file are labelled for the owner's decision, and nothing is built from one until the owner accepts it.

**Acceptance criteria** (checks `scripts/verify-S165.sh` performs)

1. **The live check.** `pnpm backlog:check --live` reads the cache (after `pnpm backlog:sync`) and the text records, both in the tree it runs in and on `origin/stage` when that ref exists (`git ls-tree` / `git show`, no checkout). It checks L9's live parts.
   - **Status label agrees with state.** An open item labelled `status:done` or `status:superseded`, a closed item labelled `status:todo`, `status:doing` or `status:blocked`, or two `status:` labels fail, naming the item. Two exceptions are reported as warnings: a **pending label** (an item closed by its merged pull request's `Closes #N` or `Fixes #N` that doesn't yet have `status:done`, a warning for up to 24 hours after the merge, and a failure after that), and an accepted bug **closed by its own filer**.
   - **No unlogged body edit.** A story's body (a bug's fields block only) is compared with its text records:
     - **Pass:** it matches the newest record.
     - **"Recorded, not yet applied: run `scripts/audit.sh apply`" (no failure):** it matches an earlier record, and the issue has no trusted `Applied <ID> edit <hash>` comment (posted by S164's `apply`) for any newer record. A comment counts only when the owner or the coordinator's token wrote it, the same trust rule as story IDs. A newer record that was applied and is no longer the body means someone changed it on GitHub.
     - **Fail, as an unlogged edit:** anything else, including the owner reverting a body to an older version after the newer one was applied (its `Applied` comment exists).
     - A recorded `create` with no issue yet is also "not yet applied".
   - **Bugs:** a bug's free-text symptoms are never compared. A bug with no create record and no fields block is unaccepted, and passes. A bug with a fields block but no create record fails, since its fields were never recorded. An outsider filer editing their own symptoms or closing their own bug is reported, not failed.
   - **The design gate.** An open UI story labelled `status:doing` whose design stories' issues aren't all closed `completed` with `status:done` fails, naming the design story.
   - Without `--live`, `pnpm backlog:check` stays as S164 left it: no cache, no network. The live check never fails on a `triage` issue.
   - **Tests:** `live-check.test.ts` covers:
     - each label/state mismatch;
     - a pending `status:done` inside and outside its window;
     - an unlogged body edit;
     - a body not yet applied;
     - a recorded create with no issue;
     - the owner reverting a body after the newer one was applied (fails), and the same revert followed by a label change (still fails);
     - an unaccepted bug with no record and no fields block (passes), and a bug with a fields block but no record (fails);
     - a live body newer than the branch's own records that matches a record on `origin/stage` (passes);
     - the same body with no `origin/stage` ref (fails, naming the item and saying to merge `stage`);
     - a bug whose filer edited its symptoms (reported), one whose filer closed it (a warning) and one whose fields block changed (fails);
     - an `Applied` comment written by an outsider, which doesn't count (the body fails as unlogged);
     - the design gate passing and failing.
2. **Adopting the owner's edits.** `scripts/audit.sh edit <ID> --adopt --reason <text>` records an item's live body (a bug's live fields block) as an `edit` fragment, with the newest record's hash as `from`, the body GitHub returns and its hash, and nothing to apply, and posts the `Applied` comment for that record, so the live check sees it as applied. The reason quotes the owner. It is also the recovery when `apply` finds the body changed in between (S164 AC 6). `audit-edit.test.ts` covers an adopt that posts its `Applied` comment and turns a failing `--live` check green, and an adopt refused when GitHub already matches the newest record.
3. **Triage, from the coordinator's session.**
   - **Labelling:** `pnpm backlog:sync` stays read-only. `pnpm backlog:triage`, run only from the coordinator's session (never in CI, whose token is read-only), adds the `triage` label directly on GitHub to every open issue not filed by the owner or the coordinator's token that isn't a trusted story or bug (S164's rules). Every open issue not filed by the owner or the coordinator's token that isn't a trusted story or bug is treated as `triage` everywhere, labelled yet or not.
   - **A `triage` issue** is never in the **Next** line, never claimable (`claims.ts claim` exits 1) and never built. It is listed in INDEX's **Triage** section by number and quoted title only, never its body.
   - **Acceptance:** the owner gives an issue a priority and a Source (rule 19). The coordinator then writes a new story through `scripts/audit.sh create`, in its own words, quoting the outside text only as data, with a link back. `apply` creates it after its pull request merges, and the triage issue is closed with a comment (`POST …/issues/<n>/comments`) naming the new one. The filer therefore can't later edit an accepted story's text (decided by the coordinator, 2026-11-20). An outside bug report is accepted in place instead, by labelling it `bug` and recording its fields block (`audit.sh create B<N> --issue <n>`).
   - **Tests:** `triage.test.ts` covers an outside issue labelled, an owner-filed issue left alone, an unlabelled outside issue refused by `claim`, an outside issue titled `S12: x` never taking ID S12, an outside bug accepted in place, and INDEX printing no body text.
4. **Areas and milestones, on GitHub.** One pure `areaOf(scope_files)` maps a story's recorded `scope_files` to `area:web`, `area:api`, `area:ingest`, `area:design` or `area:process`, and `pnpm backlog:areas` (coordinator's session) sets those labels directly. A `done` story's milestone is the first published release whose commit contains its shipping commit (`git merge-base --is-ancestor`), or none for work shipped before the first release, set the same way. Neither is a ledger record. `areas.test.ts` covers each area, a story spanning two (the first by scope order), and a done story with and without a containing release.
