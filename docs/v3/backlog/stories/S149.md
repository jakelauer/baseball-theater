**Gap:** Only a game page has a live connection: each in-window game's ingest object (`functions/src/game-ingest-object.ts`) writes Postgres, then publishes to that game's hub (`functions/src/game-hub-object.ts`), which pushes to viewers over `GET /api/v1/games/:gamePk/live` (S18; ADR-020). The scoreboard re-asks its day on the live cadence instead (`refetchInterval` in `web/src/api/schedule.ts`), so it has no live connection and can't show the Live marker. The owner wants it to have one (owner, 2026-11-16, told the polling scoreboard showed no Live marker: *"the scoreboard should have a live connection"*), opened only on a day with a game in its live window (asked when: *"While a game is live"*), as one WebSocket per day from a hub per day (asked whether one socket per day or one per live game: *"One socket per day"*). ADR-020's amendment of 2026-11-16 records it.

**Impact:** Before S149, the scoreboard caught up with live scores every few seconds by asking again. S149 impact: while a game on that day is live, scores arrive on the scoreboard the moment BT has them, over one connection, and the scoreboard can say it is live.

**Acceptance criteria** (checks `scripts/verify-S149.sh` performs)

1. **The day hub.** A Durable Object class (`DayHubObject`, named `day-hub:<YYYY-MM-DD>`) holds the scoreboard's viewers for one date over hibernated, one-way WebSockets, as `GameHubObject` does for a game (ADR-020). `wrangler.jsonc` binds it (`DAY_HUB`) in every environment and adds it in a new `migrations` entry (`new_sqlite_classes`), leaving the existing entries as they are (grep). Unit tests with the fake Durable Object storage (`functions/src/services/fake-durable-storage.ts`): a connect gets the day's latest state; a publish reaches every open socket; the last viewer leaving ends its lease.
2. **Ingest publishes to the day.** After writing Postgres, a game's ingest object also publishes to the hub of the game's official date, registered by the same lease rules as a game hub (`functions/src/services/hub-leases.ts`): it registers on its first viewer, renews, unregisters on its last, and is dropped when its lease expires or its publishes keep failing. Write first, publish second, so no viewer sees an unsaved update. What the day hub pushes is that day's scoreboard as `GET /api/v1/schedule/:date` answers it (the `ScheduleDayResponse` shape), read from Postgres, so every push is the whole day and a missed one is healed by the next. Unit tests: a game's update reaches its date's hub and not another date's; a doubleheader's two games reach the same hub; a write that fails publishes nothing.
3. **Versioned (ADR-022).** Every push carries a version that only grows for that day (one function in `packages/domain`, tested), and the client applies a push only if it is newer than what it holds, so a duplicate or an out-of-order push changes nothing. A reconnect passes its last version (`?since=<version>`) and gets the full day if it is behind. Unit tests: a duplicate, an older push and a newer push, client and hub sides.
4. **The route.** `GET /api/v1/schedule/:date/live` upgrades to the day hub's WebSocket only while the day has a game in its live window (the day's `windowMode` is `active`, the rule game pages use) and otherwise answers as `GET /api/v1/games/:gamePk/live` does for a game out of its window. It is listed with the game route in `STREAMING_ROUTE_EXCEPTIONS` (`functions/src/handlers/api.ts`) and named in `packages/domain/src/api-routes.ts`, and the published spec (`openapi/bt-api.v1.json`, `pnpm api:spec`) describes it as the game route is described. A `*.workerd.test.ts` runs the real Worker in workerd: a socket to an in-window day receives the day after a game's ingest writes; a request for a day out of its window doesn't upgrade.
5. **The scoreboard connects.** While the shown day's `windowMode` is `active`, the scoreboard opens one socket to its day (a `useLiveDay` hook in `web/src/api/`, reusing `LiveGameStream`'s reconnect, backoff, `?since=` and polling fallback rather than a second copy; `web/src/api/live-stream.ts`), writes each applied push into the day's cache through `writeScheduleDay`, and stops re-asking on the live cadence while the socket is open, as `web/src/api/game.ts` does for a streaming game. It opens no socket for a day out of its window, and closes it when the shown day changes or the page unmounts. Unit tests with the stream's fake socket: an in-window day connects and a push updates the scoreboard; an out-of-window day doesn't connect; switching days closes the old socket; a dropped socket falls back to polling as a game's does.
6. **The marker.** If S148 has shipped, the scoreboard shows its Live marker exactly while the day's socket is open, where S147's ratified amendment places it (RTL: open shows it; closed, reconnecting, polling and an out-of-window day don't). If S148 hasn't shipped, S148's AC 3 covers the scoreboard instead, and this AC passes on the grep that S148's marker component doesn't exist yet.

**Notes:**

- **Why a day hub, not one socket per live game.** The owner chose one socket per day (2026-11-16). A busy day has about 15 live games, which would have been 15 sockets per scoreboard viewer, each pushing a whole game when the scoreboard needs only its row.
- **The day of a game** is its official date in the schedule (`officialDate`), the date the scoreboard lists it under, so a game that runs past midnight stays on its day's hub.
- **Hide Scores** is unchanged: the pushed day is the same payload the HTTP route serves, and the scoreboard masks it as it masks a fetched one.
