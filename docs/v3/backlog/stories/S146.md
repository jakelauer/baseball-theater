**Gap:** Whether staging deploys is decided by a path list: `scripts/ci-changes.sh` calls any `*.md`, `docs/` or `.claude/` change docs and everything else code (owner, 2026-11-07: *"Things like this shouldn't trigger CI."*; staging stopped deploying docs-only pushes on 2026-11-11). A list says nothing about what the build actually reads. A change to a script, a test or a fixture the app never bundles still rebuilds, migrates and redeploys staging, and the list must be kept by hand. The owner asked for the decision to come from the build's inputs instead (2026-11-11): *"ultimately it'd be nice if this used some kind of hashing or something rather than directory allow/blocklists … What I'd like is for something to check the inputs to the build at build time or prior to it (ideal) or for the build output hash to be compared to the last deployed output hash (less ideal, only works if the build output is deterministically identical with identical inputs)"*, then *"yeah, I like your plan"* to recording what the build reads and checking those files' hashes before the next build.

**Impact:** Before S146, staging rebuilt and redeployed after almost any change, even one that changed nothing the site is built from (a test, a script, a fixture), and which changes counted was a hand-kept list. After S146, each deploy records exactly which files went into it, and the next one skips the build and the deploy when none of them changed, so staging only redeploys when what it serves could actually be different.

**Source:** Pillar: Delightful — deploys run only when what they build from changed, so changes reach staging without churn from edits that change nothing it serves; the same reason S89 cites for faster checks. Asked "Can the input-hash story cite the Delightful pillar (as S89 did), or Dependable?" Approved by owner 2026-11-11: "delightful"

**Acceptance criteria** (checks `scripts/verify-S146.sh` performs)

1. **Recording the inputs.** A `pnpm build:inputs record <out>` command (its code under `functions/src/deploy/`) writes, after a build, a JSON record of every file that build read, each with its git blob hash at the built commit:
    - every module the web build bundled, taken from Vite's own module graph (a plugin in `web/vite.config.ts` that writes the list it reports, never a hand-kept list of folders);
    - every module the Worker bundle read, taken from the bundler's own metafile (`wrangler deploy --dry-run --metafile`);
    - a short, named list of inputs outside those graphs: `pnpm-lock.yaml`, every workspace `package.json`, `.nvmrc`, `wrangler.jsonc`, the TypeScript, Vite and Wrangler configs and every repository file those configs import (`web/vite.config.ts` imports `web/src/pwa/options.ts`), `web/index.html`, every file under `web/public/` (copied, not imported), every migration the deploy applies, and `.github/workflows/deploy.yml` with the scripts its deploy steps run and every repository file those scripts import, taken from a bundler's graph of those entries (for example an esbuild metafile of `functions/src/scripts/deploy-bootstrap.ts`, `db-migrate.ts` and `db-reapply-deletions.ts`), not a hand list.
    - the build's inputs that aren't files: the release label `BT_RELEASE` (`scripts/build-release.sh`, read by `web/vite.config.ts`), so moving a merged pull request to another milestone changes the record. The commit in the version line is not an input: a skipped deploy keeps the version line's older commit, and README says so.

   Files under `node_modules/` and virtual modules (ids starting `\0` or `virtual:`) have no git blob and are left out: `pnpm-lock.yaml` stands for the dependencies. Unit tests (`functions/src/deploy/`) show, against a fixture repository: a file the build imports is recorded; a Markdown file and a test file are not; a file under `web/public/`, a migration, `web/index.html` and a file a config imports are; a `node_modules` path and a virtual module are left out without failing; a file only `deploy-bootstrap.ts` imports (such as `functions/src/deploy/bootstrap.ts`) is recorded, so an edit to it alone makes `check` fail; and `check` given a different `BT_RELEASE` than the record's fails.
2. **Checking the inputs.** The check runs with plain `node` and no installed dependencies (Node 24 runs TypeScript with only `node:` imports), so it can run before `pnpm install`: `node functions/src/deploy/build-inputs.ts check <record>` (also `pnpm build:inputs check <record>`, each given the build's `BT_RELEASE`) exits 0 and prints `unchanged` only when the record parses, its `BT_RELEASE` is the one given, and every file it lists has the same blob hash at HEAD. It exits nonzero, naming the first difference, for: no record, a record it can't parse, a listed file whose hash changed, a listed file that was deleted, and a record made by a different version of the command. Unit tests cover each case. A new source file can only enter a build through an import added to a recorded file, so that edit changes a recorded hash; a test shows adding an import to a recorded file makes `check` fail.
3. **Deploying from it.** In `.github/workflows/deploy.yml`, the `staging` job and the `preview` job each fetch the record of their environment's last successful deploy before installing or building (if the record is an Actions artifact, the `staging` and `preview` jobs gain `actions: read` and `preview-teardown` gains `actions: write`, which deleting one needs; a job that gains a `permissions:` block keeps every scope its steps use today, since a job block replaces the workflow's: staging's `contents: read`, `pull-requests: read` and `issues: read` for `scripts/build-release.sh merged`, and the preview's `pull-requests: write` for its comment and `issues: read` for `build-release.sh pr`), and skip install, build, migrations and deploy when `check` prints `unchanged`. This is an extra skip inside the jobs: the docs-only gate and its law P11 test (`scripts/backlog-vault/ci-law.test.ts`, outside this story's fence) stay as they are, so verify still runs only for code. A record is stored only after its deploy step succeeds, so a failed or cancelled deploy never leaves one, and it names the commit it deployed: staging deploys when the commit it serves (`bt-commit.txt`) isn't that record's commit, so a `wrangler rollback` or an older run landing last is never left in place. Staging's served-commit check still runs, so an older run never deploys over a newer one. A skipped preview still posts its comment, saying the preview from the recorded commit still serves this one; a preview's record names the pull request's head sha for that comment, not `GITHUB_SHA`, GitHub's test merge commit no one can look up. A record is only trusted while its Worker exists: `preview-teardown` deletes the pull request's record along with its Worker, and a failed deletion fails the teardown job rather than being swallowed; a `reopened` event always deploys, so a reopened pull request never gets a "still serves" comment for a deleted preview. A manual run of Deploy for `stage` with a `force` input deploys staging whatever the record says (for a rotated secret or variable, which changes no file), and README names it: the workflow gains a `workflow_dispatch` trigger with that input, the `changes` job answers `code=true` for it (as it does for a release, so `verify` runs), and the staging job's `if:` admits that event as well as a push; without both, a forced run on a `stage` whose head already passed would be stopped by `code=false` before the record is read. The `production` job always deploys. A test in `functions/src/deploy/` reads `deploy.yml` and pins all of this, the jobs' permissions included.
4. **Documented.** README's deploy section says a staging or preview deploy is skipped when the recorded inputs of its last successful deploy are unchanged, and where the record is kept; `deploy.yml`'s comments say the same, and both name the input check where they say what decides a staging deploy: grep finds `build:inputs` in `deploy.yml`'s staging and preview jobs and in README's Staging bullet. A docs-only push still deploys nothing, so the existing wording about it stays; but `wrangler.jsonc`'s staging comment ("Every push to stage that changes code … at stage.baseball.theater") and `deploy.yml`'s matching header line stop being true when a code push with unchanged inputs deploys nothing, so both are reworded to name the input check (grep finds `build:inputs` near each).
    - **The release rule.** CLAUDE.md's release rule, prepare step (1), lets a release target a `stage` commit later than the one staging serves when staging skipped it because its inputs were unchanged: the release commit is the served commit or a later `stage` commit that `pnpm build:inputs check` (given that commit's `BT_RELEASE`) finds `unchanged` against staging's record, as well as a later docs-only one, since such a commit differs from the served build only in its version line's commit (owner, 2026-11-16, asked whether a release may target such a commit or only the one staging serves: *"(a) Release may target Y"*). grep finds `build:inputs` in CLAUDE.md's release rule.

**Notes:**

- **Why inputs, not output hashes.** The owner ranked hashing the build output below checking its inputs, since it "only works if the build output is deterministically identical with identical inputs", and it still pays for every build. Vite's output isn't promised to be byte-identical across runs.
- **What keeps the list honest.** Only the short list in AC 1's third bullet is kept by hand: things the bundlers never see. Everything the app imports comes from the bundlers' own graphs. If a deploy step starts reading a new kind of file, that list gains it in the same change.
- **Where the record lives.** Not prescribed. A GitHub Actions artifact per environment (`build-inputs-staging`, `build-inputs-preview-<n>`) found through the Actions API, or a file served beside `bt-commit.txt`, both work. Whichever is chosen must not be readable as "unchanged" when the last deploy failed, or after its Worker was deleted (AC 3).
- **Previews.** A preview Worker is per pull request, so its record is per pull request too; the first push to a pull request always deploys.
- **2026-11-11 pre-PR review.** AC 3 first said staging's decision would no longer read the path list, which would have meant dropping the gate law P11's test pins, a file outside the fence and a law the owner owns; the input check is now an extra skip inside the jobs. It also added: the check running before install (AC 2), `node_modules`, virtual modules, `index.html` and config imports (AC 1), a deploy when staging serves another commit or by a `force` run (AC 3), and AC 4's grep patterns.

- **2026-11-16 backlog review.** Each change from an input that broke the story as written: (a) an edit to `functions/src/deploy/bootstrap.ts` alone (imported by `deploy-bootstrap.ts`, which writes the Worker config and secrets) was recorded by nobody, so `check` said `unchanged` and the new config never deployed: AC 1 now takes the deploy scripts' imports from a bundler's graph. (b) Moving a merged pull request to another milestone changes the built label (#47) with no file change: `BT_RELEASE` is now in the record. (c) A `force` run had no trigger and would have been stopped by `code=false` and the staging job's push-only `if:`: AC 3 now names both. (d) A job-level `permissions:` block listing only `actions: read` drops the scopes `build-release.sh` and the preview comment use: AC 3 keeps them. (e) The preview's "still serves" comment would have named `GITHUB_SHA`, the test merge. (f) `wrangler.jsonc`'s staging comment becomes untrue: the file joins the fence. **Open with the owner:** the release rule's Prepare step (2) requires `scripts/ci-changes.sh push <served> <release>` to print `code=false`. After S146, a push that changes only a test (`code=true`, inputs unchanged) leaves staging serving the older commit, so that release can't be prepared until some later push changes a build input. Whether the rule should also accept "the input check against staging's record prints `unchanged`" is the owner's call (CLAUDE.md is outside this fence); until answered, S146 must not ship.
