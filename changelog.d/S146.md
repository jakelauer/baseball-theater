title: Staging redeploys only when what it serves could change
---

- **Before, staging rebuilt and redeployed after almost any change, even one that changed nothing the site is built from, such as a test, a script or a fixture the app never uses. Now each deploy records exactly which files went into it, and the next one skips the build and the deploy when none of them changed, so staging and pull-request previews only redeploy when what they serve could actually be different.** Details: **S146** — `pnpm build:inputs record` (`functions/src/deploy/build-inputs.ts`) lists every file a build read (Vite's module graph through a plugin in `web/vite.config.ts`, the Worker's `wrangler --metafile`, an esbuild graph of the deploy scripts, and a short named list: lockfile, package and TypeScript configs, `web/index.html`, `web/public/`, migrations, the workflow) with git blob hashes and `BT_RELEASE`; `deploy.yml` stores it as an Actions artifact after each successful staging or preview deploy, and `build:inputs check` (plain `node`, before install) skips install, build, migrations and deploy when it prints `unchanged`. A manual **Deploy** run with `force` deploys staging anyway; production always deploys; the release rule's prepare step may target a later commit the check finds unchanged.
